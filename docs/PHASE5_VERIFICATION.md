# Phase 5 Verification Checklist

Verifies Phase 5 (Locations and dungeon play) per [PLAN.md §23](PLAN.md#23-delivery-phases), following the exit review in [§23.1](PLAN.md#231-phase-exit-review). Phase 5 also pulled a minimal slice of the knowledge domain forward from Phase 7 to satisfy its own exit criteria — see "Preceded by a scope decision" below and [DATABASE_MODEL.md §26](architecture/DATABASE_MODEL.md#26-reconciliation-notes-phase-5) for the full account. This document covers both the original build (revisions 038–042) and a pre-merge exit review that found seven further gaps, closed by revisions 043–047 — see "Exit review corrections" below.

## Exit Criteria

- [x] A party can enter and navigate a multi-room dungeon — `campaign.character_location_history` records arrival/departure per timeline under the full ADR 0010 interval contract (revision 043), with the open (`departed_at_world_time_id IS NULL`) row as current location. `tests/scenario/test_dungeon_navigation.py::test_a_party_can_enter_and_navigate_a_multi_room_dungeon` proves this at the level the exit criterion actually describes: a campaign, a party, a party membership, and a three-room dungeon, with the character moving room to room and the resulting history and current location verified — not a bare character with no party involved.
- [x] Hidden connections remain distinct from party knowledge — `world.area_connections.is_hidden` (and the equivalent column on features/hazards/interactables) is a structural fact with no party reference anywhere in its table; discovery is recorded separately in `knowledge.party_discoveries`, scoped per party. `test_knowledge_domain.py::test_a_hidden_connections_own_row_never_reveals_party_knowledge` asserts both structurally (`world.area_connections` has no `discover`/`known`-named column) and behaviorally (two parties on the same timeline have independent discovery records for the same connection, which itself stays `is_hidden = true` throughout); the navigation scenario above checks the same thing in context.
- [x] Actions can alter dungeon state — all five typed state tables (`campaign.location_state`, `.area_connection_state`, `.area_feature_state`, `.hazard_state`, `.interactable_state`) support in-place transitions, exercised by `test_dungeon_timeline_state.py` (e.g. a connection moving from locked to open, a hazard from armed to disarmed) and now correctly maintain `updated_at` on every change (revision 046, `test_dungeon_state_updated_at.py`).

All verified against the deployed AWS `dev` RDS instance, per [§23.0](PLAN.md#230-aws-verification-policy): upgrade to `head` through all 10 revisions (038–047), a downgrade/upgrade round trip covering them, `alembic check` clean, and the full test suite (1040 tests — 13 unit, 1026 database, 1 scenario) passing, including a from-scratch `upgrade head` against a fresh ephemeral database.

## Preceded by a scope decision

PLAN.md's Phase 5 deliverable list names "discovery records" and its exit criteria require hidden connections to stay distinct from party knowledge, but the documented shape of discovery (`knowledge.party_discoveries`, DATABASE_MODEL.md §15) is tied to `knowledge.knowledge_items` — a table DATABASE_MODEL.md's own implementation order (§23) places in Phase 7, after locations, interactions/events, and quests. This was surfaced and discussed with the user before writing schema (matching the process CLAUDE.md §7 asks for) rather than resolved unilaterally. The decision: pull the minimal slice of the knowledge domain forward — `knowledge.knowledge_items`, `knowledge.entity_knowledge`, `knowledge.party_discoveries`, plus the two lookups they need — using their documented Phase 7 shape, rather than invent a smaller Phase-5-only table Phase 7 would need to reconcile later. `knowledge.knowledge_versions`, `.information_transfers`, `.expertise_domains`/`.character_expertise`, and `.public_knowledge` remain genuinely deferred to Phase 7. See DATABASE_MODEL.md §26 for the full reconciliation note, including the simplified single-subject shape used on `knowledge.knowledge_items` in place of the plural "subject entities" DOMAIN_MODEL.md §15.1 describes.

## Bugs and Gaps Found

1. **A trigger function's error message masked a CHECK constraint.** `knowledge.enforce_party_discovery_world()` originally looked up a recipient's world unconditionally; when both `party_id` and `knower_entity_id` were `NULL` (violating `ck_party_discoveries_exactly_one_recipient`), the `BEFORE INSERT` trigger ran first and raised its own "mixes worlds" error before the `CHECK` constraint got a chance, since PostgreSQL evaluates `BEFORE ROW` triggers before per-row constraints. Fixed by having the trigger return early when both recipient columns are `NULL`, letting the `CHECK` constraint report the more specific error. Found by `test_a_discovery_needs_exactly_one_recipient`.
2. **Two `TEXT` column defaults needed an explicit cast in `tables.py`.** `knowledge.knowledge_items.sensitivity` and `knowledge.entity_knowledge.awareness_level` both declare a string `server_default`; PostgreSQL normalizes a literal-string default on a `TEXT` column to include `::text` in `information_schema.columns.column_default`, so `tables.py` had to declare `text("'public'::text")` / `text("'aware'::text")` rather than the bare literal to match, caught by `test_metadata_server_default_matches_live_schema` (the same test class that caught a Phase 4 corrections-pass bug in `rules.default_canon_status_id()`).
3. **A `Column(...)` comment was declared in the migration but not mirrored in `tables.py`.** `world.area_connections.is_one_way` had its `COMMENT ON COLUMN` in the migration but the corresponding `tables.py` `Column()` call had no `comment=` argument, caught immediately by `alembic check` before any test ran.
4. **A flaky test, found by re-running the full suite rather than trusting one green run.** `test_a_valid_transition_between_adjacent_non_overlapping_locations_is_accepted` (added in this exit-review pass) ordered its result rows with `ORDER BY arrived_at_world_time_id` — a `UUID` primary key with no relationship to chronological order (`gen_random_uuid()` output is random, not sequential), so the assertion's row order depended on UUID-generation luck rather than the actual sequence of events. Passed on first write, failed on a later full-suite run once the random UUIDs happened to sort the other way. Fixed by ordering on `location_period` instead, which sorts by the range's actual lower bound. A reminder of exactly why the exit review's "do not rely only on the existing green CI run" instruction matters — this bug would have shipped invisibly in a single "run once and move on" pass.

None of these were schema-design defects — three were test/tooling-parity bugs caught before they could hide a real one (the same class of finding every prior phase's verification pass recorded), and one was a test itself asserting on a non-deterministic ordering.

## Exit review corrections (2026-08-03)

A review of the branch before merge found seven blocking gaps across integrity, mutation safety, and completeness that the original exit criteria above didn't happen to exercise. Closed by five forward-only revisions (043–047); revisions 038–042 were not touched.

1. **Character-location temporal integrity** — `campaign.character_location_history` had same-world checks but not the rest of the ADR 0010 interval contract `campaign.party_memberships` already implements: no overlap prevention beyond "one open row," no ordering check, and endpoints that discarded a client-supplied range only by accident (there wasn't one to discard). **Fix:** revision 043 reused the party-memberships pattern exactly — required `arrived_at_world_time_id`, a trigger-derived `location_period INT8RANGE`, `EXCLUDE USING gist (timeline_id, character_id, location_period WITH &&)`, and endpoint `ON DELETE RESTRICT` instead of `SET NULL`. **Tests:** `test_character_location_temporal_integrity.py`, 26 cases covering every scenario the review listed (closed history, adjacent transition, open current location, wrong-world arrival/departure, equal/reversed endpoints, overlapping closed/open/mixed periods, update-introduced overlap, and that `core.world_times`/`core.entities`/`campaign.timelines` immutability (revision 030) already prevents a referenced scope row from being mutated out from under existing history).
2. **Dungeon structural mutation safety** — revision 039's rules validated only at insert time (or, for dungeon areas, only from the `dungeon_areas` side). **Fix:** revision 044 made connection endpoints and feature/hazard/interactable area assignments immutable via the existing `core.enforce_immutable_columns()` (no new mechanism), and added a cycle-of-any-length guard plus a dungeon-parent revalidation trigger to `world.locations` for the columns that must legitimately stay mutable. **Tests:** `test_dungeon_structural_mutation_safety.py`, 14 cases (immutable endpoints individually and both-together-cross-world, immutable area assignments including cross-world, non-identity columns staying mutable, reparenting a dungeon area to a non-dungeon/clearing its parent both rejected, valid reparenting accepted, two-node and three-node cycles rejected, valid non-cyclic reparenting accepted, direct self-parenting via UPDATE rejected).
3. **Knowledge event timestamps** — `learned_at_world_time_id`/`discovered_at_world_time_id` were unchecked. **Fix:** revision 045 extended (`CREATE OR REPLACE`) the two existing trigger functions rather than adding new ones. **Tests:** `test_knowledge_event_timestamp_validation.py`, 9 cases (accept/reject/update for both columns, immutability of a referenced world time proven in this context specifically, and a regression check that the malformed-recipient early return still lets the CHECK constraint fire).
4. **Dungeon-state `updated_at`** — declared but never maintained on all five revision-040 tables. **Fix:** revision 046 attaches `core.set_updated_at()`, same construction and naming as everywhere else. **Tests:** `test_dungeon_state_updated_at.py`, 5 cases (one per table), using the deliberately-wrong-value-gets-overridden pattern from `test_core_lookups_and_security.py` rather than a sleep-and-compare (which would pass against a broken trigger too, since `now()` is transaction-start time).
5. **Completeness — `realm`** — DOMAIN_MODEL.md §9.1 names it, revision 038 omitted it. **Fix:** revision 047 registers it the same way the other six no-subtype-table location kinds are registered. **Test:** `test_locations.py::test_a_realm_location_can_be_created`.
6. **Completeness — conditional routes** — named in this phase's own deliverable list, not built. **Fix:** revision 047 adds `is_conditional`/`condition_description` to `world.area_connections` — the descriptive half only. Evaluation is explicitly deferred, not silently dropped: PLAN.md's Phase 6 first-time obligations now name the missing dependency (interaction/check resolution, and quest state for quest-gated conditions) and what Phase 5 does/doesn't support. **Tests:** `test_dungeon_structures.py::test_a_connection_can_be_marked_conditional_with_a_description`, `::test_a_connection_defaults_to_unconditional`.
7. **Completeness — knowledge Phase 5/7 boundary** — documentation only; nothing to fix in schema. DATABASE_MODEL.md §15 now states explicitly that temporal validity of knowledge items and real discovery source/provenance are NOT built and remain Phase 7's job, distinct from the three tables (`knowledge_items`, `entity_knowledge`, `party_discoveries`) Phase 5 did pull forward.
8. **Party-navigation scenario** — the original exit-criterion evidence was a bare character moving between two dungeon areas, with no campaign, party, or party membership. **Fix:** no schema change; `tests/scenario/test_dungeon_navigation.py` builds the full chain (world → timeline → campaign → party → character → membership → three-room dungeon → connections) and moves the character through it, checking history, current location, resulting dungeon state, and one case the database actually forbids (a party member occupying two rooms at once).

None of the eight findings were caused by a wrong architectural decision — all were places where a rule was enforced on the happy path (insert) but not revalidated on mutation, or where a documented requirement was quietly dropped instead of built or deferred explicitly. The same class of gap Phase 4's corrections and closeout passes found and fixed.

## Deliberate Scoping Decisions

- **`world.area_spawn_definitions` was not built**, despite being named in PLAN.md §9.2 and (a prior revision of) DATABASE_MODEL.md §9.2. No creature-instance or stat-block model exists anywhere in this schema — `rules.creature_types` is a bare classification lookup — and Phase 9 (encounters) is the natural first consumer. Both docs corrected to record the deferral; see DATABASE_MODEL.md §26.
- **`world.settlements` and `world.buildings` are minimal**, matching Phase 4's `character.npcs` pattern: settlements carry `population` only (government/factions are Phase 8 organization concepts; economy is intentionally deferred per DOMAIN_MODEL.md §27; districts are plain child locations; control/damage state is timeline state); buildings carry free-text `building_use` (no documented vocabulary exists).
- **Six DOMAIN_MODEL.md §9.1 location kinds with no structured data** (plane, continent, nation, region, district, geographic_feature) are plain `core.entity_types` leaves under `location`, not separate CTI tables — the same pattern `character.characters` already uses for types needing no dedicated apparatus.
- **Knowledge items carry a single simplified subject reference**, not the plural "subject entities" association DOMAIN_MODEL.md §15.1 describes. Sufficient for Phase 5's one-item-one-concealed-thing use case; Phase 7 should promote to a junction table if a real requirement for multiple subjects appears.
- **`knowledge.knowledge_versions`, `.information_transfers`, `.expertise_domains`/`.character_expertise`, and `.public_knowledge` remain deferred to Phase 7** — only the three tables Phase 5's exit criteria actually needed were pulled forward.
- **No event-linked history on any of the five new timeline-state tables**, for the same reason Phase 4's three character-state tables have none: `narrative.events` does not exist until Phase 6. Each is a single mutable current row per `(timeline, target)`, enforced by its primary key.
- **`campaign.character_state` was not given a `current_location_id` column.** DATABASE_MODEL.md §17's example prose lists "current location" among tracked state, but `campaign.character_location_history`'s open row already serves that purpose (same "`NULL` end = current" convention `campaign.party_memberships` uses), so no change to the already-shipped Phase 4 table was needed.
