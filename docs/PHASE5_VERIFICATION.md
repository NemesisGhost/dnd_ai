# Phase 5 Verification Checklist

Records the verification performed for Phase 5 (Locations and dungeon play) per [PLAN.md §23](PLAN.md#23-delivery-phases) and the exit-review process in [§23.1](PLAN.md#231-phase-exit-review). Phase 5 also pulled a minimal slice of the knowledge domain forward from Phase 7 to satisfy its own exit criteria — see "Preceded by a scope decision" below and [DATABASE_MODEL.md §26](architecture/DATABASE_MODEL.md#26-reconciliation-notes-phase-5) for the full account. This document covers the original build (revisions 038–042) and two pre-merge corrections passes (043–047 and 048–051). The implementation and recorded suite were merged by PR #5, but the post-merge review found cases those passes did not close; [PHASE5_REMAINING_ISSUES.md](PHASE5_REMAINING_ISSUES.md) is the open completion gate and supersedes any closure claim below.

## Exit Criteria

- [x] A party can enter and navigate a multi-room dungeon — `campaign.character_location_history` records arrival/departure per timeline under the full ADR 0010 interval contract (revision 043, `location_period` made `NOT NULL` by revision 050), with the open (`departed_at_world_time_id IS NULL`) row as current location. `tests/scenario/test_dungeon_navigation.py::test_a_party_can_enter_and_navigate_a_multi_room_dungeon` proves this at the level the exit criterion actually describes: a campaign, a party, a party membership, and a three-room dungeon, with the character moving room to room and the resulting history and current location verified — not a bare character with no party involved.
- [x] Hidden connections remain distinct from party knowledge — `world.area_connections.is_hidden` (and the equivalent column on features/hazards/interactables) is a structural fact with no party reference anywhere in its table; discovery is recorded separately in `knowledge.party_discoveries`, scoped per party. `test_knowledge_domain.py::test_a_hidden_connections_own_row_never_reveals_party_knowledge` asserts both structurally (`world.area_connections` has no `discover`/`known`-named column) and behaviorally (two parties on the same timeline have independent discovery records for the same connection, which itself stays `is_hidden = true` throughout); the navigation scenario above checks the same thing in context.
- [x] Actions can alter dungeon state — all five typed state tables (`campaign.location_state`, `.area_connection_state`, `.area_feature_state`, `.hazard_state`, `.interactable_state`) support in-place transitions, exercised by `test_dungeon_timeline_state.py` (e.g. a connection moving from locked to open, a hazard from armed to disarmed) and correctly maintain `updated_at` on every change (revision 046), now proven by mutating a real state column across genuinely separate transactions rather than only by overriding the column directly (`test_dungeon_state_updated_at.py`).

The listed criteria and tests were verified against the deployed AWS `dev` RDS instance, per [§23.0](PLAN.md#230-aws-verification-policy): upgrade to `head` through all 14 revisions (038–051), downgrade/upgrade round trips covering both corrections passes, `alembic check` clean, and the full test suite (1,066 tests — 13 unit, 1,052 database, 1 scenario) passing twice in direct succession, including a from-scratch `upgrade head` against a fresh ephemeral database. That evidence does not cover the concurrency, deep/corrupt hierarchy, populated upgrade, and non-space-whitespace cases in [PHASE5_REMAINING_ISSUES.md](PHASE5_REMAINING_ISSUES.md), so it is not yet phase-closure evidence.

## Preceded by a scope decision

PLAN.md's Phase 5 deliverable list names "discovery records" and its exit criteria require hidden connections to stay distinct from party knowledge, but the documented shape of discovery (`knowledge.party_discoveries`, DATABASE_MODEL.md §15) is tied to `knowledge.knowledge_items` — a table DATABASE_MODEL.md's own implementation order (§23) places in Phase 7, after locations, interactions/events, and quests. This was surfaced and discussed with the user before writing schema (matching the process CLAUDE.md §7 asks for) rather than resolved unilaterally. The decision: pull the minimal slice of the knowledge domain forward — `knowledge.knowledge_items`, `knowledge.entity_knowledge`, `knowledge.party_discoveries`, plus the two lookups they need — using their documented Phase 7 shape, rather than invent a smaller Phase-5-only table Phase 7 would need to reconcile later. `knowledge.knowledge_versions`, `.information_transfers`, `.expertise_domains`/`.character_expertise`, and `.public_knowledge` remain genuinely deferred to Phase 7. See DATABASE_MODEL.md §26 for the full reconciliation note, including the simplified single-subject shape used on `knowledge.knowledge_items` in place of the plural "subject entities" DOMAIN_MODEL.md §15.1 describes.

## Bugs and Gaps Found

1. **A trigger function's error message masked a CHECK constraint.** `knowledge.enforce_party_discovery_world()` originally looked up a recipient's world unconditionally; when both `party_id` and `knower_entity_id` were `NULL` (violating `ck_party_discoveries_exactly_one_recipient`), the `BEFORE INSERT` trigger ran first and raised its own "mixes worlds" error before the `CHECK` constraint got a chance, since PostgreSQL evaluates `BEFORE ROW` triggers before per-row constraints. Fixed by having the trigger return early when both recipient columns are `NULL`, letting the `CHECK` constraint report the more specific error. Found by `test_a_discovery_needs_exactly_one_recipient`.
2. **Two `TEXT` column defaults needed an explicit cast in `tables.py`.** `knowledge.knowledge_items.sensitivity` and `knowledge.entity_knowledge.awareness_level` both declare a string `server_default`; PostgreSQL normalizes a literal-string default on a `TEXT` column to include `::text` in `information_schema.columns.column_default`, so `tables.py` had to declare `text("'public'::text")` / `text("'aware'::text")` rather than the bare literal to match, caught by `test_metadata_server_default_matches_live_schema` (the same test class that caught a Phase 4 corrections-pass bug in `rules.default_canon_status_id()`).
3. **A `Column(...)` comment was declared in the migration but not mirrored in `tables.py`.** `world.area_connections.is_one_way` had its `COMMENT ON COLUMN` in the migration but the corresponding `tables.py` `Column()` call had no `comment=` argument, caught immediately by `alembic check` before any test ran.
4. **A flaky test, found by re-running the full suite rather than trusting one green run.** `test_a_valid_transition_between_adjacent_non_overlapping_locations_is_accepted` (added in this exit-review pass) ordered its result rows with `ORDER BY arrived_at_world_time_id` — a `UUID` primary key with no relationship to chronological order (`gen_random_uuid()` output is random, not sequential), so the assertion's row order depended on UUID-generation luck rather than the actual sequence of events. Passed on first write, failed on a later full-suite run once the random UUIDs happened to sort the other way. Fixed by ordering on `location_period` instead, which sorts by the range's actual lower bound. A reminder of exactly why the exit review's "do not rely only on the existing green CI run" instruction matters — this bug would have shipped invisibly in a single "run once and move on" pass.

None of these were schema-design defects — three were test/tooling-parity bugs caught before they could hide a real one (the same class of finding every prior phase's verification pass recorded), and one was a test itself asserting on a non-deterministic ordering.

## First exit review corrections (2026-08-03)

A review of the branch before merge found seven blocking gaps across integrity, mutation safety, and completeness that the original exit criteria above didn't happen to exercise. Closed by five forward-only revisions (043–047); revisions 038–042 were not touched.

1. **Character-location temporal integrity** — `campaign.character_location_history` had same-world checks but not the rest of the ADR 0010 interval contract `campaign.party_memberships` already implements: no overlap prevention beyond "one open row," no ordering check, and endpoints that discarded a client-supplied range only by accident (there wasn't one to discard). **Fix:** revision 043 reused the party-memberships pattern exactly — required `arrived_at_world_time_id`, a trigger-derived `location_period INT8RANGE`, `EXCLUDE USING gist (timeline_id, character_id, location_period WITH &&)`, and endpoint `ON DELETE RESTRICT` instead of `SET NULL`. **Tests:** `test_character_location_temporal_integrity.py`, 26 cases covering every scenario the review listed (closed history, adjacent transition, open current location, wrong-world arrival/departure, equal/reversed endpoints, overlapping closed/open/mixed periods, update-introduced overlap, and that `core.world_times`/`core.entities`/`campaign.timelines` immutability (revision 030) already prevents a referenced scope row from being mutated out from under existing history).
2. **Dungeon structural mutation safety** — revision 039's rules validated only at insert time (or, for dungeon areas, only from the `dungeon_areas` side). **Fix:** revision 044 made connection endpoints and feature/hazard/interactable area assignments immutable via the existing `core.enforce_immutable_columns()` (no new mechanism), and added a cycle-of-any-length guard plus a dungeon-parent revalidation trigger to `world.locations` for the columns that must legitimately stay mutable. **Tests:** `test_dungeon_structural_mutation_safety.py`, 14 cases (immutable endpoints individually and both-together-cross-world, immutable area assignments including cross-world, non-identity columns staying mutable, reparenting a dungeon area to a non-dungeon/clearing its parent both rejected, valid reparenting accepted, two-node and three-node cycles rejected, valid non-cyclic reparenting accepted, direct self-parenting via UPDATE rejected).
3. **Knowledge event timestamps** — `learned_at_world_time_id`/`discovered_at_world_time_id` were unchecked. **Fix:** revision 045 extended (`CREATE OR REPLACE`) the two existing trigger functions rather than adding new ones. **Tests:** `test_knowledge_event_timestamp_validation.py`, 9 cases (accept/reject/update for both columns, immutability of a referenced world time proven in this context specifically, and a regression check that the malformed-recipient early return still lets the CHECK constraint fire).
4. **Dungeon-state `updated_at`** — declared but never maintained on all five revision-040 tables. **Fix:** revision 046 attaches `core.set_updated_at()`, same construction and naming as everywhere else. **Tests:** `test_dungeon_state_updated_at.py`, 5 cases (one per table), using the deliberately-wrong-value-gets-overridden pattern from `test_core_lookups_and_security.py` rather than a sleep-and-compare (which would pass against a broken trigger too, since `now()` is transaction-start time).
5. **Completeness — `realm`** — DOMAIN_MODEL.md §9.1 names it, revision 038 omitted it. **Fix:** revision 047 registers it the same way the other six no-subtype-table location kinds are registered. **Test:** `test_locations.py::test_a_realm_location_can_be_created`.
6. **Completeness — conditional routes** — named in this phase's own deliverable list, not built. **Fix:** revision 047 adds `is_conditional`/`condition_description` to `world.area_connections` — the descriptive half only. Evaluation is explicitly deferred, not silently dropped: PLAN.md's Phase 6 first-time obligations now name the missing dependency (interaction/check resolution, and quest state for quest-gated conditions) and what Phase 5 does/doesn't support. **Tests:** `test_dungeon_structures.py::test_a_connection_can_be_marked_conditional_with_a_description`, `::test_a_connection_defaults_to_unconditional`.
7. **Completeness — knowledge Phase 5/7 boundary** — documentation only; nothing to fix in schema. DATABASE_MODEL.md §15 now states explicitly that temporal validity of knowledge items and real discovery source/provenance are NOT built, distinct from the three tables (`knowledge_items`, `entity_knowledge`, `party_discoveries`) Phase 5 did pull forward. (Correction from the second exit review below: this entry originally assigned both gaps to "Phase 7." Temporal validity genuinely is Phase 7's — but real discovery provenance depends on `interaction.interactions`/`narrative.events`, both Phase 6 deliverables, making it Phase 6's obligation instead; PLAN.md and DATABASE_MODEL.md §15 now say so unambiguously.)
8. **Party-navigation scenario** — the original exit-criterion evidence was a bare character moving between two dungeon areas, with no campaign, party, or party membership. **Fix:** no schema change; `tests/scenario/test_dungeon_navigation.py` builds the full chain (world → timeline → campaign → party → character → membership → three-room dungeon → connections) and moves the character through it, checking history, current location, resulting dungeon state, and one case the database actually forbids (a party member occupying two rooms at once).

None of the eight findings were caused by a wrong architectural decision — all were places where a rule was enforced on the happy path (insert) but not revalidated on mutation, or where a documented requirement was quietly dropped instead of built or deferred explicitly. The same class of gap Phase 4's corrections and closeout passes found and fixed.

## Second exit review corrections (2026-08-03)

A second review of the branch before merge, after the first corrections pass above had already gone green on CI, found four further gaps a purely sequential, single-transaction test suite could not have exercised — plus documentation drift including the Phase 6/7 provenance ambiguity corrected in finding 7 of the pass above. Closed by four more forward-only revisions (048–051); revisions 038–047 were not touched.

1. **Parent-side entity-type-change protection** — `core.enforce_entity_subtype()` (revision 004) validates only from the subtype side: `UPDATE core.entities SET entity_type_id = ...` touches no subtype table, so nothing stopped retyping a dungeon (or any other subtyped entity) away from its type while its subtype row — and, for dungeons, its `world.dungeon_areas` children — remained. **Fix:** revision 048 adds `core.entity_types.required_subtype_pk_column` (explicit, paired with `required_subtype_table`, not derived by string manipulation) and `core.enforce_entity_type_change()`, a generic `BEFORE UPDATE OF entity_type_id` trigger on `core.entities` walking both the OLD and NEW type's ancestry and rejecting a change that would strand an existing subtype row — protects every registered subtype (character/npc/player_character, location/settlement/building/dungeon/dungeon_area, knowledge_item) through one mechanism. A second, dungeon-specific trigger (`world.enforce_dungeon_type_change_preserves_areas()`) closes the deeper case: `world.dungeons` is deletable (conventions §7.5), and once deleted the generic trigger has nothing left to check, but `world.dungeon_areas` children may still depend on the parent staying dungeon-typed. A review of every other Phase 4/5 subtype relationship found no equivalent "child requires parent to remain a specific type" rule, so no further dedicated trigger was needed. **Tests:** `test_entity_type_change_protection.py`, 9 cases (dungeon → region, dungeon → building, dungeon_area → region, a same-type no-op update, an ordinary rename, a bare-location correction before any subtype row exists, the marker-already-deleted-but-areas-remain case rejected, the marker-deleted-and-no-areas case accepted, and an NPC → bare-character rejection proving the Phase 4 coverage).
2. **Containment-cycle prevention was not concurrency-safe** — revision 044's ancestry check read the hierarchy with no lock, so two concurrent transactions (A placed under B; B placed under A, both starting from the same acyclic snapshot) could each observe no cycle and both commit — write skew, since the two writes touch disjoint rows and nothing else serializes them. **Partial fix:** `CREATE OR REPLACE` on revision 044's `world.enforce_location_no_cycle()` (the function, not the trigger attachment, which revision 044 still owns) now takes a per-world `pg_advisory_xact_lock` before reading the ancestry, keyed on both the mover's and the target parent's world and acquired in sorted order so two transactions naming the same pair of worlds can never deadlock. **Test:** `test_dungeon_structural_mutation_safety.py::test_a_concurrent_containment_swap_is_serialized_and_rejected` — two genuinely independent connections (`postgres_engine`, not two statements on one connection), transaction 1 moves A under B and stays open, transaction 2 attempts B under A under a 2-second `lock_timeout` and is proven to block (not merely fail immediately), transaction 1 then commits, and the identical swap retried afterward is rejected outright by the cycle check. This closes the tested write skew, but the added depth cutoff silently truncates at 10,000 rather than detecting repeated nodes or raising on cutoff; arbitrary-depth and corrupt-hierarchy safety remain open in [PHASE5_REMAINING_ISSUES.md item 2](PHASE5_REMAINING_ISSUES.md#2-make-containment-cycle-validation-complete-and-corruption-safe).
3. **`location_period` was not structurally `NOT NULL`** — revision 043 gave `campaign.character_location_history.location_period` a trigger that always derives it for new writes, but never declared the column itself `NOT NULL`, unlike `campaign.party_memberships.effective_period`. **Partial fix:** revision 050 asserts zero existing NULLs, then runs `ALTER COLUMN location_period SET NOT NULL`, and corrects both the column and table `COMMENT`s. It does not derive ranges for rows that existed when revision 043 added the nullable column, so a populated upgrade can stop before reaching head; [PHASE5_REMAINING_ISSUES.md item 3](PHASE5_REMAINING_ISSUES.md#3-repair-the-populated-revision-042043-upgrade-path) owns that gap. **Tests:** `test_character_location_temporal_integrity.py`, 4 new final-schema cases (catalog introspection confirms `is_nullable = 'NO'`; insert-then-close-out derivation still produces correct ranges under the tightened column; an explicit client-supplied `NULL` is overwritten by the trigger rather than surviving; an explicit client-supplied decoy range that looks non-overlapping is overwritten too, so the exclusion constraint still catches the real, derived overlap). None seeds a row before revision 043 and upgrades it through revision 050.
4. **`updated_at` tests only ever set `updated_at` directly** — proving the trigger overwrites a supplied value, never that it fires from an ordinary state-changing write. **Fix:** no schema change; five new tests extend (not replace) `test_dungeon_state_updated_at.py`, one per dungeon-state table, each inserting a row, capturing `updated_at`, mutating a real state column (`is_searched`, a status lookup FK, `is_destroyed`, ...) in a genuinely separate committed transaction, and asserting `updated_at` advanced. Genuinely separate transactions were required, not a sleep: `core.set_updated_at()` uses `now()`, which is *transaction start* time in PostgreSQL, so two statements inside one transaction (the `db_connection` fixture the original five tests use) would show no advance even with a correctly firing trigger — the fix reuses `postgres_engine`'s real, separately-committed transactions, the same mechanism the concurrency test above needs and for the identical underlying reason.
5. **Cross-world mutation coverage was incomplete for features and interactables** — the hazard immutability test already covered a cross-world reassignment attempt; the feature and interactable tests only exercised same-world reassignment. **Fix:** no schema change; added `test_a_feature_cannot_be_reassigned_to_an_area_in_another_world` and `test_an_interactable_cannot_be_reassigned_to_an_area_in_another_world`, matching the existing hazard test's shape, and all three (hazard included) now additionally assert the rejected row's `dungeon_area_id` and `is_hidden` are unchanged after the failed UPDATE — proving the rejection doesn't leave the original record corrupted, not just that it raised.
6. **Conditional-route columns permitted contradictory states** — `is_conditional = true` with no description, and `is_conditional = false` with one, were both silently allowed. No design document establishes a deliberate use for either. **Partial fix:** revision 051 adds `ck_area_connections_conditional_description_paired`: a conditional route requires a non-null description containing something after ordinary spaces are trimmed; an unconditional route must have `NULL`. **Tests:** `test_dungeon_structures.py`, 5 new cases (conditional without a description rejected, conditional with ordinary spaces rejected, unconditional with a description rejected, the same rejection on UPDATE not just INSERT, and the valid way to make a route unconditional — both columns changed together in one UPDATE — accepted). Tab/newline/carriage-return-only values are not trimmed and remain open in [PHASE5_REMAINING_ISSUES.md item 4](PHASE5_REMAINING_ISSUES.md#4-treat-all-whitespace-only-conditional-descriptions-as-blank).
7. **Documentation drift, including the Phase 6/7 provenance ambiguity** — DATABASE_MODEL.md §15 said real discovery provenance was "still Phase 6/7 work" in the same sentence that had just attributed it to Phase 6; PLAN.md's Phase 7 section separately listed that same provenance fix as something "Phase 5 explicitly left for this phase," directly contradicting Phase 6's own first-time-obligations entry for it. **Fix:** DATABASE_MODEL.md §15 and PLAN.md's Phase 7 section both now say Phase 6 unambiguously (`interaction.interactions`/`narrative.events` are Phase 6 deliverables; the replacement has no dependency on Phase 7's quest or knowledge-versioning work). The one place "Phase 6/7" legitimately remains (DATABASE_MODEL.md §9.2 and PLAN.md's Phase 6 obligations, on conditional-route *evaluation*) already distinguishes the two deliverables explicitly — general interaction/check resolution (Phase 6) versus quest-gated conditions specifically (Phase 7) — so it was left as-is rather than flattened. Also corrected: this file's own stale claims (no corrections CI run yet; test/revision counts; the `character_location_history` table comment now describes the derived range and exclusion constraint rather than the superseded index design — carried through from finding 3's migration into this file too), plus a repo-wide grep for other stale phase-status statements, test totals, and revision heads.

## Deliberate Scoping Decisions

- **`world.area_spawn_definitions` was not built**, despite being named in PLAN.md §9.2 and (a prior revision of) DATABASE_MODEL.md §9.2. No creature-instance or stat-block model exists anywhere in this schema — `rules.creature_types` is a bare classification lookup — and Phase 9 (encounters) is the natural first consumer. Both docs corrected to record the deferral; see DATABASE_MODEL.md §26.
- **`world.settlements` and `world.buildings` are minimal**, matching Phase 4's `character.npcs` pattern: settlements carry `population` only (government/factions are Phase 8 organization concepts; economy is intentionally deferred per DOMAIN_MODEL.md §27; districts are plain child locations; control/damage state is timeline state); buildings carry free-text `building_use` (no documented vocabulary exists).
- **Six DOMAIN_MODEL.md §9.1 location kinds with no structured data** (plane, continent, nation, region, district, geographic_feature) are plain `core.entity_types` leaves under `location`, not separate CTI tables — the same pattern `character.characters` already uses for types needing no dedicated apparatus.
- **Knowledge items carry a single simplified subject reference**, not the plural "subject entities" association DOMAIN_MODEL.md §15.1 describes. Sufficient for Phase 5's one-item-one-concealed-thing use case; Phase 7 should promote to a junction table if a real requirement for multiple subjects appears.
- **`knowledge.knowledge_versions`, `.information_transfers`, `.expertise_domains`/`.character_expertise`, and `.public_knowledge` remain deferred to Phase 7** — only the three tables Phase 5's exit criteria actually needed were pulled forward.
- **No event-linked history on any of the five new timeline-state tables**, for the same reason Phase 4's three character-state tables have none: `narrative.events` does not exist until Phase 6. Each is a single mutable current row per `(timeline, target)`, enforced by its primary key.
- **`campaign.character_state` was not given a `current_location_id` column.** DATABASE_MODEL.md §17's example prose lists "current location" among tracked state, but `campaign.character_location_history`'s open row already serves that purpose (same "`NULL` end = current" convention `campaign.party_memberships` uses), so no change to the already-shipped Phase 4 table was needed.
