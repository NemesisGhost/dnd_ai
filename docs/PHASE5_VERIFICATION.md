## Exit Criteria

- [x] A party can enter and navigate a multi-room dungeon — `campaign.character_location_history` records arrival/departure per timeline under the full ADR 0010 interval contract (revision 043, `location_period` made `NOT NULL` by revision 050 and genuinely backfilled for any pre-existing rows by revision 052), with the open (`departed_at_world_time_id IS NULL`) row as current location. `tests/scenario/test_dungeon_navigation.py::test_a_party_can_enter_and_navigate_a_multi_room_dungeon` proves this at the level the exit criterion actually describes: a campaign, a party, a party membership, and a three-room dungeon, with the character moving room to room and the resulting history and current location verified — not a bare character with no party involved.
- [x] Hidden connections remain distinct from party knowledge — `world.area_connections.is_hidden` (and the equivalent column on features/hazards/interactables) is a structural fact with no party reference anywhere in its table; discovery is recorded separately in `knowledge.party_discoveries`, scoped per party. `test_knowledge_domain.py::test_a_hidden_connections_own_row_never_reveals_party_knowledge` asserts both structurally (`world.area_connections` has no `discover`/`known`-named column) and behaviorally (two parties on the same timeline have independent discovery records for the same connection, which itself stays `is_hidden = true` throughout); the navigation scenario above checks the same thing in context.
- [x] Actions can alter dungeon state — all five typed state tables (`campaign.location_state`, `.area_connection_state`, `.area_feature_state`, `.hazard_state`, `.interactable_state`) support in-place transitions, exercised by `test_dungeon_timeline_state.py` (e.g. a connection moving from locked to open, a hazard from armed to disarmed) and correctly maintain `updated_at` on every change (revision 046), proven by mutating a real state column across genuinely separate transactions rather than only by overriding the column directly (`test_dungeon_state_updated_at.py`).

The listed criteria and tests were verified against the deployed AWS `dev` RDS instance, per [§23.0](PLAN.md#230-aws-verification-policy): upgrade to `head` through all 19 revisions (038–056), downgrade/upgrade round trips covering the four revision-bearing corrections passes (including the revision-052 splice point in both directions), `alembic check` clean, and the full test suite — see "Verification commands and results" under the fourth, fifth, and sixth corrections passes below. Deep/corrupt-hierarchy, populated-upgrade, complete-whitespace, and child-location-lock coverage are all included, and the concurrency suite proves resumed-waiter behavior with independent final-state assertions. The focused helper tests prove forced termination, cleanup-error reporting, startup-timeout handling, and failed-cancellation containment all leave no worker behind — see the sixth through twelfth exit reviews below for the sequence of hardening passes that closed each gap in the test-only helper in turn; none of them changed a production or migration file.

## Preceded by a scope decision

PLAN.md's Phase 5 deliverable list names "discovery records" and its exit criteria require hidden connections to stay distinct from party knowledge, but the documented shape of discovery (`knowledge.party_discoveries`, DATABASE_MODEL.md §15) is tied to `knowledge.knowledge_items` — a table DATABASE_MODEL.md's own implementation order (§23) places in Phase 7, after locations, interactions/events, and quests. This was surfaced and discussed with the user before writing schema (matching the process CLAUDE.md §7 asks for) rather than resolved unilaterally. The decision: pull the minimal slice of the knowledge domain forward — `knowledge.knowledge_items`, `knowledge.entity_knowledge`, `knowledge.party_discoveries`, plus the two lookups they need — using their documented Phase 7 shape, rather than invent a smaller Phase-5-only table Phase 7 would need to reconcile later. `knowledge.knowledge_versions`, `.information_transfers`, `.expertise_domains`/`.character_expertise`, and `.public_knowledge` remain genuinely deferred to Phase 7. See DATABASE_MODEL.md §26 for the full reconciliation note, including the simplified single-subject shape used on `knowledge.knowledge_items` in place of the plural "subject entities" DOMAIN_MODEL.md §15.1 describes.

## Bugs and Gaps Found

1. **A trigger function's error message masked a CHECK constraint.** `knowledge.enforce_party_discovery_world()` originally looked up a recipient's world unconditionally; when both `party_id` and `knower_entity_id` were `NULL` (violating `ck_party_discoveries_exactly_one_recipient`), the `BEFORE INSERT` trigger ran first and raised its own "mixes worlds" error before the `CHECK` constraint got a chance, since PostgreSQL evaluates `BEFORE ROW` triggers before per-row constraints. Fixed by having the trigger return early when both recipient columns are `NULL`, letting the `CHECK` constraint report the more specific error. Found by `test_a_discovery_needs_exactly_one_recipient`.
2. **Two `TEXT` column defaults needed an explicit cast in `tables.py`.** `knowledge.knowledge_items.sensitivity` and `knowledge.entity_knowledge.awareness_level` both declare a string `server_default`; PostgreSQL normalizes a literal-string default on a `TEXT` column to include `::text` in `information_schema.columns.column_default`, so `tables.py` had to declare `text("'public'::text")` / `text("'aware'::text")` rather than the bare literal to match, caught by `test_metadata_server_default_matches_live_schema` (the same test class that caught a Phase 4 corrections-pass bug in `rules.default_canon_status_id()`).
3. **A `Column(...)` comment was declared in the migration but not mirrored in `tables.py`.** `world.area_connections.is_one_way` had its `COMMENT ON COLUMN` in the migration but the corresponding `tables.py` `Column()` call had no `comment=` argument, caught immediately by `alembic check` before any test ran.
4. **A flaky test, found by re-running the full suite rather than trusting one green run.** `test_a_valid_transition_between_adjacent_non_overlapping_locations_is_accepted` (added in this exit-review pass) ordered its result rows with `ORDER BY arrived_at_world_time_id` — a `UUID` primary key with no relationship to chronological order (`gen_random_uuid()` output is random, not sequential), so the assertion's row order depended on UUID-generation luck rather than the actual sequence of events. Passed on first write, failed on a later full-suite run once the random UUIDs happened to sort the other way. Fixed by ordering on `location_period` instead, which sorts by the range's actual lower bound. A reminder of exactly why the exit review's "do not rely only on the existing green CI run" instruction matters — this bug would have shipped invisibly in a single "run once and move on" pass.

None of these were schema-design defects — three were test/tooling-parity bugs caught before they could hide a real one (the same class of finding every prior phase's verification pass recorded), and one was a test itself asserting on a non-deterministic ordering.

## First exit review corrections (2026-08-03)

A review of the branch before merge found seven blocking gaps across integrity, mutation safety, and completeness that the original exit criteria above didn't happen to exercise. Closed by five forward-only revisions (043–047); revisions 038–042 were not touched.

1. **Character-location temporal integrity** — `campaign.character_location_history` had same-world checks but not the rest of the ADR 0010 interval contract `campaign.party_memberships` already implements: no overlap prevention beyond "one open row," no ordering check, and endpoints that discarded a client-supplied range only by accident (there wasn't one to discard). **Fix:** revision 043 reused the party-memberships pattern exactly — required `arrived_at_world_time_id`, a trigger-derived `location_period INT8RANGE`, `EXCLUDE USING gist (timeline_id, character_id, location_period WITH &&)`, and endpoint `ON DELETE RESTRICT` instead of `SET NULL`. **Tests:** `test_character_location_temporal_integrity.py`, 26 cases covering every scenario the review listed (closed history, adjacent transition, open current location, wrong-world arrival/departure, equal/reversed endpoints, overlapping closed/open/mixed periods, update-introduced overlap, and that `core.world_times`/`core.entities`/`campaign.timelines` immutability (revision 030) already prevents a referenced scope row from being mutated out from under existing history).
2. **Dungeon structural mutation safety** — revision 039's rules validated only at insert time (or, for dungeon areas, only from the `dungeon_areas` side). **Fix:** revision 044 made connection endpoints and feature/hazard/interactable area assignments immutable via the existing `core.enforce_immutable_columns()` (no new mechanism), and added a cycle-of-any-length guard plus a dungeon-parent revalidation trigger to `world.locations` for the columns that must legitimately stay mutable. **Tests:** `test_dungeon_structural_mutation_safety.py`, 14 cases (immutable endpoints individually and both-together-cross-world, immutable area assignments including cross-world, non-identity columns staying mutable, reparenting a dungeon area to a non-dungeon/clearing its parent both rejected, valid reparenting accepted, two-node and three-node cycles rejected, valid non-cyclic reparenting accepted, direct self-parenting via UPDATE rejected).
3. **Knowledge event timestamps** — `learned_at_world_time_id`/`discovered_at_world_time_id` were unchecked. **Fix:** revision 045 extended (`CREATE OR REPLACE`) the two existing trigger functions rather than adding new ones. **Tests:** `test_knowledge_event_timestamp_validation.py`, 9 cases (accept/reject/update for both columns, immutability of a referenced world time proven in this context specifically, and a regression check that the malformed-recipient early return still lets the CHECK constraint fire).

## Sixth exit review corrections (2026-08-04)

A sixth review re-checked the fifth pass's `_BackgroundStatement` cleanup helper against the literal guarantee `PHASE5_REMAINING_ISSUES.md` required — that no worker, connection, transaction, or advisory lock survives the `with` block — and found it was still only best-effort:

1. **Termination was skipped when no backend PID was recorded**, since `__enter__` returned as soon as it started the background thread, without waiting for the worker to actually establish its connection. **Fix:** `__enter__` now blocks until the worker's backend PID is recorded (or the thread has already failed) before returning, and raises — after joining the thread, so nothing is left running — if that does not happen within a bounded startup deadline. A `with` block can no longer begin with a worker of unowned state.
2. **Termination errors and a false `pg_terminate_backend()` result were both suppressed**, so a failed termination attempt was indistinguishable from a successful one. **Fix:** `__exit__` now checks `pg_terminate_backend()`'s boolean result explicitly, falls back to `pg_cancel_backend()` if termination was not confirmed, and follows each attempt with a bounded join that verifies the thread actually stopped — not just that a signal was sent.
3. **The final bounded `join()` was not followed by an `is_alive()` check**, so a worker that failed to stop within the timeout was never detected. **Fix:** a final, independent liveness check backstops both termination attempts; if the thread is still alive, that is a cleanup failure, not a silent success.
4. **Cleanup failures had no reporting path.** **Fix:** if an exception was already propagating out of the `with` block, the cleanup failure is attached to it via `add_note()`, preserving the original failure as the reported cause; if nothing was already propagating, the cleanup failure is raised directly and becomes the `with` block's own failure.
5. **The forced-cleanup path had no focused regression test.** **Fix:** three new tests in `test_entity_type_change_protection.py` exercise the helper directly, against a plain `pg_advisory_xact_lock` rather than any production trigger — see `PHASE5_REMAINING_ISSUES.md § Sixth review` for the full description of each. Writing them also surfaced (a) a genuine PostgreSQL nuance — a lock holder's own connection retains a stale view of a terminated waiter's `pg_stat_activity` row until the holder releases its own lock, requiring the test's own verification to use a fresh connection, matching the existing independent-connection pattern — and (b) a race in the tests' own teardown, fixed by terminating the real worker deterministically before releasing the lock it depends on remaining blocked by.

One more, related gap surfaced and fixed while writing test 1: the worker's own connection was invalidated on failure but still returned to the pool via a plain `close()`. Some server-side disconnect conditions — notably `psycopg.errors.AdminShutdown`, which `pg_terminate_backend()` itself raises on its target — are not recognized by SQLAlchemy's own disconnect detection, so a `close()` without an explicit prior `invalidate()` risked silently returning a dead connection to the shared pool for a later, unrelated test to draw. The worker now always invalidates its own connection when its statement raises, before closing it.

## Ninth exit review: findings and corrections (2026-08-04)

A ninth review of commit `c9f13a7` accepted the eighth pass's diagnosis but found its fixes still did not deliver the containment the register requires. The production verdict is unchanged yet again: revision 056 is correct, all five concurrency invariant tests preserve and resume the original waiter with independent final-state assertions, and no schema, migration, or production-code change is needed. The review's scope, like the eighth pass's, is entirely `tests/database/test_entity_type_change_protection.py`.

### Findings

1. **`__enter__()` still raced its own worker's startup instead of owning it.** The eighth pass's `connect_timeout` genuinely bounded how long a stalled connection attempt could take, but the connection was still opened *inside* the background thread, with `__enter__` polling for a recorded backend pid and then joining with a timeout to find out whether startup had succeeded. That is a tighter bound than the seventh pass found, but it is still two independent things racing each other rather than one thing happening before the other by construction.
2. **`_force_stop()`'s only fallback was to report failure.** When both `pg_terminate_backend()` and `pg_cancel_backend()` failed, nothing else in the helper's control could reach the worker — `__exit__()` correctly reported that failure rather than hanging or returning cleanly, but "reports rather than hangs" is not the same guarantee as "the worker actually stops." The register asks for a deterministic fallback grounded in a resource the helper itself owns, not just faithful reporting of a dead end.
3. **The two termination-failure regression tests proved the reporting path by breaking the caller's contract with the helper, not the helper's own containment.** Both deliberately corrupted the tracked backend pid (`blocked.backend_pid[0] = 2**31 - 1`) so that `_force_stop()`'s SQL signals were guaranteed to miss. That is a real test of "the caller lied about which backend it owns and the helper reports the resulting failure honestly" — a narrower and less useful guarantee than "PostgreSQL's own termination signals genuinely failed against the correct backend and the helper still stopped it."

### Corrections

1. **Startup ownership is now established synchronously, before any worker thread exists.** `_establish_connection()` (a new, isolated method) connects through a private, single-use engine (the same driver-level `connect_timeout` as before), begins the transaction, sets a bounded `lock_timeout` on it (see #2 below), and reads the real backend pid — all in the calling thread, inside `__enter__()`, before `threading.Thread(...)` is ever constructed. If any of that fails, `__enter__()` raises directly and no thread is ever created; there is no longer an interval during which a worker of unknown or unowned state could outlive a failed context entry, because the entry and the worker's existence no longer race each other at all. `backend_pid` is now private storage (`self._backend_pid_value`) exposed only through a read-only property — there is no longer a way for a caller to overwrite it, closing finding 3's loophole at the type level rather than by convention.
2. **`_force_stop()` gained a two-layer fallback beyond the existing SQL signals, ending in a mechanism PostgreSQL itself guarantees.** After `pg_terminate_backend()` and `pg_cancel_backend()` (now issued through an isolated `_send_signal()` seam, so regression tests can inject a false result or a raised exception without touching the real, correct backend pid):
   - **Driver-native cancellation** (`_cancel_via_driver()`): psycopg's `Connection.cancel_safe()`, called directly on the worker's own connection handle. This is a resource the helper genuinely owns — unlike the SQL signals, it needs no second connection and no privilege to target an arbitrary pid — and psycopg documents it as safe to call from another thread while the connection is busy with a blocking operation. Confirmed empirically before relying on it here: a probe script blocked a worker on `pg_advisory_xact_lock`, called `cancel_safe()` on it from the main thread, and observed the worker's statement fail with `QueryCanceled` within 0.24s.
   - **The `lock_timeout` set during startup**: a deterministic backstop PostgreSQL itself enforces on the worker's own transaction, entirely independent of every mechanism above and of anything this thread does or fails to do. `__exit__()` simply waits out that bound (plus margin) rather than taking any further action; PostgreSQL guarantees the cancellation once the bound elapses. Confirmed empirically the same way: a worker blocked with `SET LOCAL lock_timeout = '2s'` and never signaled at all still failed with `LockNotAvailable` after 2.04s. The one statement this backstop cannot reach is one that was never waiting on a lock in the first place (`pg_sleep`, not `pg_advisory_xact_lock`) — exercised deliberately by the two regression tests proving `_force_stop()`'s reporting path still works in that genuine worst case, described below.
3. **Six regression tests replace the three that corrupted `backend_pid`,** none of them touching that value: the original real-signal-succeeds test (adapted to the new API); a parametrized test proving the fallback to `cancel_safe()` when both SQL signals are mocked to return `False` or to raise; a test proving the fallback to the `lock_timeout` backstop when every active mechanism (both signals and `cancel_via_driver`) is mocked to fail; and two tests — one with an original exception propagating, one without — using `pg_sleep` (not lock-bound, so the deterministic backstop cannot rescue it either) with every active mechanism mocked to fail, proving `_force_stop()` still reports the failure correctly, `__exit__()` still preserves or raises as appropriate, and the worker still terminates once its own fixed sleep duration naturally elapses.
4. **The refused-port startup test is replaced by a deterministic mocked slow-then-failing `_establish_connection()`,** proving `__enter__()` raises within a bounded wall-clock interval and — because ownership is now established before any thread is created — that `attempt._thread` stays `None` throughout, without depending on real network timing or topology. A second test keeps a real (unmocked) connection failure against a local port nothing listens on, confirming the same structural guarantee holds for a genuine driver error, whatever its exact type and message on the platform running the test.

## Tenth exit review: findings and corrections (2026-08-04)

A tenth review of merged PR #12 (commit `15c8b24`) accepted that the ninth pass's synchronous-ownership redesign and layered fallback were genuine improvements, but found the underlying architecture could still not deliver the register's literal requirement: `_BackgroundStatement` must never return or raise from `__enter__()` or `__exit__()` while an owned worker remains alive. The production verdict is unchanged once again: revision 056 is correct, all five concurrency invariant tests preserve and resume the original waiter, and no schema, migration, or production-code change is needed. The review's scope, like every prior pass since the sixth, is entirely `tests/database/test_entity_type_change_protection.py`.

### Findings

1. **No Python thread can be unconditionally, forcibly stopped.** The ninth pass's `lock_timeout` backstop rescues a genuine lock wait, and driver-native `cancel_safe()` rescues an ordinary query — but neither is a *general* mechanism, and nothing in a thread-based design can force a thread blocked inside a call that ignores both (`pg_sleep`, used deliberately by the two worst-case regression tests) to actually stop. The tests proved this directly: after the `with` block exited, the worker thread was still alive, and the tests' own `blocked._thread.join(timeout=sleep_seconds)` — code the tests ran themselves, after the context manager had already returned or raised — was what actually reclaimed it.
2. **Reporting a survivor is not the same as containing one.** `__exit__()` correctly raised or attached a note describing the failure in that scenario, satisfying the letter of "cleanup failures are never silently discarded" — but the register's acceptance criterion is stricter: the worker must actually be gone, not merely have its continued existence honestly reported.

### Corrections

1. **The worker now runs in an independently terminable OS process (`multiprocessing.Process`, the "spawn" start method on every platform), not a Python thread.** A real process has no analogous limitation: `Process.terminate()`/`.kill()` (SIGTERM/SIGKILL on POSIX, `TerminateProcess` on Windows) end it unconditionally, regardless of what it is doing — the property no thread-based design could ever offer. `_worker_main()`, a new module-level function (required for `multiprocessing`'s "spawn" start method to pickle a reference to it), owns the worker's connection, transaction, and statement execution entirely within that process.
2. **`__enter__()` performs an explicit startup handshake** — the worker connects, begins its transaction, sets the `lock_timeout` backstop, and reports its real backend pid back through a queue, all before `__enter__()` returns. `backend_pid` remains a private, read-only property, exactly as the ninth pass established. If the handshake fails or times out, `__enter__()` terminates and reaps the process — verified, not assumed — before raising, with every cleanup problem attached as a note.
3. **Partial-startup resource paths are now explicitly covered rather than implied.** `_worker_main()`'s own except block attempts rollback, close, and engine disposal independently for whatever was partially acquired, collecting every failure via a small `_attempt()` helper instead of a blanket `contextlib.suppress()` — replacing the broad suppression the ninth pass's `_establish_connection()` used. Six new/parametrized regression tests inject a failure at each stage (after connect, after transaction begin, after `lock_timeout` is set, after the pid lookup, and a case where the connection is deliberately made unusable so the cleanup attempts themselves genuinely fail too) and prove `__enter__()` still fails predictably with no process left alive.
4. **`_force_stop()`'s fallback chain gained a truly unconditional final layer.** After `pg_terminate_backend()`, `pg_cancel_backend()` (via the mockable `_send_signal()` seam, unchanged from the ninth pass), driver-native `cancel_safe()` (now relayed to a watcher thread running *inside* the worker process, since the controller no longer holds a live connection object once the worker's own connection lives in a separate process), and the `lock_timeout` backstop, a still-alive process is forcibly terminated — `terminate()`, escalating to `kill()` if needed — which cannot itself fail to end the process. That step is followed by one more, deliberately non-mockable `pg_terminate_backend()` call: killing the client process guarantees the process's own resources are reclaimed, but does not by itself guarantee PostgreSQL has noticed, since a backend blocked inside a call that never touches its client socket (`pg_sleep`) can keep running until it next tries to communicate. This was found empirically, not assumed: an early version of the fix that relied on process termination alone left the backend visibly present in `pg_stat_activity` for longer than a 5-second poll in the two worst-case regression tests, tracing to exactly this gap.
5. **The two `pg_sleep` regression tests no longer perform a manual join after the context manager exits.** Both now assert `not blocked._process.is_alive()` and query a fresh connection to confirm the backend is gone immediately after the `with` block — independent proof that containment already happened, not part of making it happen. Every regression test's safety-net cleanup (releasing a controlled advisory lock the test itself set up, in the two production-style tests that use one) remains in `finally`, as the ninth pass already established.

## Eleventh exit review: worker outcome protocol, controller cleanup, and process/IPC hardening (2026-08-04)

The tenth pass's process-based redesign correctly fixed the literal no-survivor guarantee, and its final pushed head passed CI. Review of that merged commit (`4ef78375d7dbf2c57341c12d4b8c5dd92572d00b`), specifically requested to happen *before* touching the helper itself, found the new token-reduction tooling's documented entry point was broken, and then found the redesigned worker could still report false success and silently discard cleanup failures.

**Tooling defect (found and fixed first, then used for the rest of this pass):** `scripts/verify.sh` was committed as `100644` (non-executable). `core.filemode=false` in this repository means a local `chmod +x` never propagates into the tracked git mode, so `scripts/verify.sh <mode>` — the exact form every new skill file and `docs/DEVELOPMENT.md` document — failed with `Permission denied` on a fresh checkout, even though the working tree's own copy happened to still carry the bit from before it was committed. `scripts/aws-db-allow-my-ip.sh`, which `verify.sh`'s `database`/`scenario`/`full`/`migration-round-trip` modes invoke directly and which `docs/DEVELOPMENT.md` §3 also documents as a bare command, had the identical defect. Both fixed via `git update-index --chmod=+x` (which sets the tracked mode regardless of `core.filemode`), then proved via a genuinely fresh `git clone` of this branch that `./scripts/verify.sh --help` (and the bare `scripts/verify.sh --help` form the docs use) now run without a permission error. Both the smallest supported mode (`quality`, no AWS) and a genuinely broader mode (`full`, real AWS: 1,081 database tests, 1 scenario test, `alembic check`) were run for real against `dev`, including confirming the security-group ingress the `full` mode opens is reliably closed by its trap even after a ~14-minute run. `scripts/verify.sh` itself was then used for every quality check for the remainder of this pass — see the verification table below.

**Findings, all confined to `tests/database/test_entity_type_change_protection.py`:**

1. **A statement's own commit failure could still be reported as `"committed"`.** `_worker_main`'s outcome tuple was assembled as `("committed", None)` immediately after the statement itself succeeded, before `connection.commit()` was ever attempted; a commit failure only appended to `problems`, which `resume_and_get_outcome()` only ever turned into a note *if the status was already `"failed"`* — so a commit failure (or a close/dispose failure after an otherwise-clean commit) was silently absorbed into an apparently-successful outcome.
2. **An outcome nobody explicitly consumed could be lost entirely.** `__exit__` only invoked `_force_stop()` when the process was still alive; a worker that finished (successfully or not) before the `with` block exited, without the caller ever calling `resume_and_get_outcome()`, left its outcome sitting unread in `outcome_queue` forever.
3. **A controller-side verification error could replace an already-propagating exception.** `_verify_backend_gone()`'s per-poll `with self._engine.connect() as checker:` block let a connection or query failure propagate straight out of `_force_stop()` and `__exit__` uncaught — silently replacing whatever exception the `with` block's body had already raised, rather than being collected like every other cleanup problem.
4. **The regression tests never exercised the final, otherwise-unconditional termination call failing.** Every prior pass's fault-injection tests left `_terminate_backend_unconditionally()` operational, so nothing proved that method's own failure was handled — nor was there a test for backend-verification itself failing.
5. **Process/IPC lifecycle gaps.** `Process()` construction and `process.start()` failures were unhandled; `_force_stop()`'s final "process survived forcible termination" case raised a bare `assert` instead of reporting a collected problem (the same replace-an-already-propagating-exception risk as finding 3); IPC queues and the `Process` object itself were never explicitly closed.

**Fix:**

- `_worker_main` now tracks `statement_error` and `commit_error` separately; `commit()` is only attempted after a successful statement, and the outcome is `"committed"` if and only if the statement succeeded, the commit succeeded, *and* no other cleanup step (rollback-after-commit-failure, close, dispose) reported a problem. A shared `_build_outcome_exception()` is used by both `resume_and_get_outcome()` and a new `_drain_unread_outcome()` (called unconditionally from `__exit__`), so an outcome nobody explicitly consumed is still surfaced rather than lost, and a cleanup-only problem after a genuine commit still fails the caller.
- A new `_with_isolated_connection()` helper guarantees every controller-side connection (`_send_signal`, `_terminate_backend_unconditionally`, the new `_query_backend_state`) is closed regardless of what the operation itself did, without letting a close failure replace the operation's own error. `_verify_backend_gone()` was rewritten around it to poll `pg_stat_activity.state`/`xact_start` (distinguishing gone / present-idle / present-active-or-in-transaction) and to *never itself raise* — a verification failure is always collected into `problems`, never conflated with "the backend is gone" and never able to replace an exception already propagating from a caller further up the stack.
- `__enter__` now wraps `Process()` construction and `process.start()` in their own failure-safe handling — `self._process` is left `None` on either failure (a `Process` object whose `start()` raised is never valid for `is_alive()`/`terminate()`/`close()`), and every IPC queue is closed via the same path. `_force_stop`'s bare `assert not self._process.is_alive()` became a collected problem like everything else. `_reap()` and `__exit__` both now close every IPC queue (bounding `Queue.join_thread()`, which has no timeout of its own, via a short-lived wrapper thread) and the `Process` object itself once confirmed not-alive — which in turn required a new `worker_confirmed_stopped` property, since `Process.is_alive()` raises `ValueError` once the object is closed, breaking the established `assert not blocked._process.is_alive()` idiom every test (old and new) used to confirm containment after `__exit__`/`_reap`.
- Eleven new regression tests (twelve collected items, since one is parametrized over two stages; see "Verification commands and results" below for the exact count) cover: a statement failing on its own; commit failing after a successful statement (found empirically that the follow-on `rollback()` attempt is itself a safe no-op once `commit()` has already failed against a closed connection — the same SQLAlchemy bookkeeping behavior the tenth pass found for the pre-`begin()` case, documented in the test rather than asserted as a second failure); a cleanup-only failure (`close`/`dispose`, parametrized) after an otherwise-successful commit; an outcome drained by `__exit__` that nobody consumed; the final termination call itself failing; backend verification itself failing; `Process()` construction failure; `process.start()` failure; `terminate()` not stopping the process with `kill()` escalating; and a queue/Process-object close failure. Writing the queue-close test surfaced one more real bug: `_close_queues` was unconditionally attempting `Queue.join_thread()` even when `Queue.close()` had already failed, violating `join_thread()`'s own documented precondition and leaking an unhandled-thread-exception warning instead of a reported problem — fixed by skipping `join_thread()` for any queue whose own `close()` failed, and by relaying an exception raised inside the bounded-wait wrapper thread back to the caller instead of only detecting a timeout.
- The five production concurrency-invariant tests were not modified; all pass unchanged.

## Twelfth exit review: verification-tooling correctness, worker outcome protocol totality, and Pipe-based IPC (2026-08-04)

Review of merged PR #14 (merge commit `7ec0945`, containing implementation commit `8c3a2cd` and documentation commit `e173c21`) accepted that the eleventh pass's outcome-protocol and controller-cleanup hardening were genuine improvements, but found the verification tooling's own `--help` claim did not hold up to its exit code, the worker outcome protocol still had a gap a naturally exited worker with an empty outcome channel could exploit, `_worker_main`'s cleanup `finally` block was not itself independently failure-safe, and the IPC design still relied on the exact class of abandonable-thread bug it was built to eliminate. The production verdict is unchanged yet again: revision 056 is correct, all five concurrency invariant tests preserve and resume the original waiter with independent final-state assertions, and no schema, migration, or production-code change is needed. The review's scope is `scripts/verify.sh`, a new `tests/unit/test_verify_sh.py`, and `tests/database/test_entity_type_change_protection.py`.

### Findings

1. **`scripts/verify.sh --help`/`-h` did not exit 0 when given as the first argument.** The eleventh pass's fix (restoring the tracked executable bit) was real and necessary, and its own verification correctly proved the permission error was gone — but `--help`/`-h` handling only ran inside the trailing-argument loop, after `MODE="$1"` had already consumed the flag itself. `scripts/verify.sh --help` alone fell through to the invalid-mode case and exited 2 with usage text, not 0 as every mode's own `-h`/`--help` handling already did. Nothing in the eleventh pass's verification table checked the exit code, only that the command ran without `Permission denied`.
2. **Ingress-revocation failure was silently swallowed.** `close_ingress`'s `scripts/aws-db-allow-my-ip.sh close >/dev/null 2>&1 || true` discarded both the failure and its output; an otherwise fully successful `database`/`scenario`/`full`/`migration-round-trip` run would still print `All requested stages passed.` even if the security-group rule it had opened was never actually closed.
3. **The worker outcome protocol was not total.** `_drain_unread_outcome()` returned `None` in three structurally different situations — the outcome was already consumed, the worker was deliberately terminated before it could produce one, or the worker exited on its own having never published one at all — and `__exit__` treated all three identically as "nothing to report." Only the second is a legitimate no-outcome case; the third is a worker that silently failed its one mandatory duty, previously indistinguishable from success.
4. **`_worker_main`'s cleanup `finally` block began with an unprotected `control_queue.put(None)`.** A failure signaling the watcher to stop would skip joining it, closing the connection, disposing the engine, and publishing the outcome — the exact "cleanup steps must be attempted independently" property the file's own `_attempt()` helper exists to provide elsewhere, missing at the one place a fresh failure was most likely to matter.
5. **`_bounded_join_thread()` wrapped an abandonable resource in another abandonable resource.** `multiprocessing.Queue.join_thread()` has no timeout of its own, so the eleventh pass wrapped it in a daemon thread to add one — but when that wrapper's own deadline expired, the wrapper thread itself remained alive, reproduced directly during this review. Bounding an unbounded wait by racing it against a thread that is itself unbounded relocates the abandonable-resource problem rather than removing it.
6. **Partial IPC construction was unhandled.** `handshake_queue`, `outcome_queue`, and `control_queue` were each constructed with a bare `ctx.Queue()` call before any of the three was stored on `self`; a failure constructing the second or third would leak whichever queue(s) had already been created, with no cleanup attempt and no `self` attribute even set to find them by.

### Corrections

- **`scripts/verify.sh`:** `--help`/`-h` is now checked as the first argument before `MODE` is assigned, printing usage and exiting 0. Ingress-close failure is captured explicitly (no `|| true`) and reported: `close_ingress()` returns whether it succeeded, and `cleanup()` — now invoked via `trap 'cleanup "$?"' EXIT` so it can see the exit code that triggered it — always attempts revocation, preserves an already-failed stage's exit code as primary while visibly reporting an additional revocation failure, and fails an otherwise-successful run if revocation alone fails. `All requested stages passed.` is now printed only from the one path where both conditions hold. Seventeen new deterministic tests in `tests/unit/test_verify_sh.py` exercise this against a stubbed `uv` (prepended to `PATH`) and a stubbed ingress script (`VERIFY_SH_INGRESS_SCRIPT`), never touching AWS or running the real quality/test suites — including a parametrized test that runs every invocation documented in the script's own header comment and confirms each behaves exactly as written.
- **Worker outcome protocol:** a new `outcome_protocol_state` attribute and `_finalize_worker_outcome()` method (replacing `_drain_unread_outcome()`) distinguish `"consumed"` (the ordinary case), `"unread"` (nobody explicitly consumed it, drained and reported here), `"missing-after-forced-termination"` (the one legitimate no-outcome case — the controller itself ended the worker before it could publish anything), and `"missing-after-natural-exit"` (a worker that exited on its own without ever publishing one — now a reported protocol failure, not silent success). A second outcome appearing after the first — whether the first was consumed via `resume_and_get_outcome()` or drained here — is also reported as a protocol failure; the worker's own cleanup contract guarantees at most one.
- **`_worker_main` cleanup independence:** the `finally` block now attempts signaling the watcher to stop, joining it, closing the connection, and disposing the engine as independent steps, none gated on an earlier one's success; a watcher still alive after its own bounded join is itself recorded as a cleanup problem, no longer silently ignored. Outcome publication is the one step that cannot itself be made failure-safe in the usual way — if the channel for reporting a failure is what failed, there is no second channel to report that failure through — so its own failure is instead detected by the controller's now-total outcome protocol (`"missing-after-natural-exit"`), matching the register's explicit requirement.
- **IPC redesigned around `multiprocessing.Pipe(duplex=False)`, not `multiprocessing.Queue`.** Three one-way pipes (handshake, outcome, and a controller-to-worker control channel used only for real cancel requests) replace the three queues; `Connection.close()` is a direct, synchronous close of an OS-level pipe handle with no background feeder thread at all, removing the class of bug finding 5 reproduced by construction rather than by bounding it further. The worker's own watcher-thread stop signal moved off IPC entirely, onto a local `threading.Event`: that signal was always same-process (the worker's main thread telling its own watcher thread to stop), never genuinely cross-process, so it never needed a `multiprocessing` primitive at all. `__enter__` now constructs all three pipes inside one try/except, closing whichever already-created pipe(s) exist and reporting every cleanup failure if a later one fails to construct — parametrized regression tests cover both the second and third pipe failing. A genuine cross-platform bug surfaced while proving this against AWS `dev` on Windows: `PipeConnection.poll()` raises `BrokenPipeError` once its peer has closed, rather than returning `False` or deferring to `recv()` raising `EOFError` the way POSIX does — both `poll()` and `recv()` are now guarded against `(EOFError, OSError)` in the shared `_poll_and_recv()` helper.
- **Test safety-net audit:** the six tests that call `__enter__()` directly (bypassing the `with` statement that would otherwise guarantee `__exit__` runs) gained a `finally`-scoped safety net that reaps a still-alive worker if `__enter__` ever unexpectedly fails to raise — a real, if unlikely, gap: without it, a broken assertion in the test's own primary path would leave a live worker process and its held PostgreSQL connection behind for later tests to inherit. ## Thirteenth exit review: accurate missing-outcome classification, universal backend verification, and Process.start() failure ownership (2026-08-05)

Review of PR #15 at commit `d0032dc` accepted that the twelfth pass's verification-tooling fix, Pipe-based IPC redesign, and worker-cleanup independence were genuine improvements, but found the twelfth pass's own worker-outcome-protocol and process-lifecycle fixes were themselves still incomplete. The production verdict is unchanged yet again: revision 056 is correct, all five concurrency invariant tests preserve and resume the original waiter with independent final-state assertions, and no schema, migration, or production-code change is needed. The review's scope is entirely `tests/database/test_entity_type_change_protection.py`.

### Findings

1. **The missing-outcome classification was not accurate.** `__exit__()` set `worker_was_forcibly_stopped = True` whenever the process was merely *alive* when cleanup began — not whenever this controller's own `terminate()`/`kill()` was what actually ended it. A worker gracefully stopped by `pg_terminate_backend()`, `pg_cancel_backend()`, driver cancellation, or the `lock_timeout` backstop still reaches its own outcome-publication step before exiting; if that publish then failed (deterministically reproduced via `_fault_injection_stage="outcome_publish_fails"` on a genuinely blocked, gracefully cancelled worker), the missing outcome was wrongly accepted as the legitimate forced-termination exemption instead of reported as a protocol failure.
2. **Backend verification ran only on the forced-stop path.** `_verify_backend_gone()` was called exclusively from inside `_force_stop()`; a worker that exited naturally (the process already not alive by the time `__exit__` began) skipped fresh-connection backend verification entirely, relying on the Python process having exited as an unverified proxy for PostgreSQL itself having noticed.
3. **A `Process.start()` failure was not always "nothing was spawned."** `__enter__` never stored the constructed `Process` object until after `start()` had already succeeded, and its except block's own comment asserted a raised `start()` always meant no OS process existed — true for the mocked-failure regression tests, but not a general guarantee: `start()` can fail after partial (or full) initialization, and the code never stored or closed the `Process` object in that case regardless.
4. **Startup-cleanup failures on the redundant controller-side pipe copies were silently discarded.** `__enter__` closes its own copies of `handshake_send`/`outcome_send`/`control_recv` immediately after a successful `process.start()` (the worker has its own duplicated copies). Failures doing so were collected into a local `startup_problems` list used only by the handshake-failure/timeout raise paths; if the handshake then succeeded, that list — and anything already collected in it — was simply discarded when `__enter__` returned.

### Corrections

- **`_force_stop()` now returns `(problems, containment_reason)`**, where `containment_reason` is `"graceful"` (a PostgreSQL/driver mechanism ended the process without this controller ever calling `terminate()`/`kill()`), `"forced"` (this controller's own `terminate()`/`kill()` is what actually ended it), or `"survived"` (even forced termination did not — the OS-level guarantee violation every prior pass already treats as a distinct reported problem). `__exit__()` derives `worker_was_forcibly_stopped` from this reason, not from whether the process happened to be alive when cleanup began. A new regression test blocks a worker on a genuine advisory lock, lets the real, unmocked `pg_terminate_backend()` signal gracefully end it, and proves the resulting missing outcome (via `outcome_publish_fails`) is still reported as `"missing-after-natural-exit"`, not misclassified as the legitimate forced-termination case.
- **Backend verification now runs exactly once on every `__exit__()` path, never redundantly.** If the process is alive when `__exit__` begins, `_force_stop()` verifies internally as its last step (unchanged). If it already exited on its own, `__exit__()` now calls `_verify_backend_gone()` directly instead of skipping it. Two new regression tests mock verification to fail for a worker that completes entirely on its own — one with no original exception (verification failure raised directly), one with the `with` block's own body raising first (verification failure attached as a note) — proving both branches of the existing raise-vs-attach logic now also cover the natural-completion path.
- **Ownership of the constructed `Process` object begins at construction, not only once `start()` confirms success.** `self._process` is now assigned immediately after `ctx.Process(...)` succeeds, before `process.start()` is even called. A new `_cleanup_process_after_start_failure()` method classifies what a raised `start()` actually left behind — `pid`/`is_alive()` are both safe to call regardless of whether the process ever started, confirmed empirically, rather than assumed — and either closes the `Process` object directly (genuinely never started) or terminates, escalates to `kill()`, reaps with bounded joins, and then closes it (a genuinely live child left by partial initialization). Four new regression tests cover: the never-started case (now additionally proving `close()` was actually attempted, via `is_alive()` itself raising `ValueError` afterward, not merely inferred); a partially started case, using a wrapped `start()` that calls the real implementation before injecting a failure, so a real child is genuinely spawned and must be genuinely reaped; the `Process` object's own `close()` itself failing during that cleanup; and an IPC channel's own `close()` failing during that same cleanup.
- **Startup-cleanup failures on the redundant controller-side pipe copies are now instance-owned lifecycle problems `__exit__()` always reports**, chosen over failing/reaping the worker solely because a copy the worker itself never uses failed to close on this side. `self._startup_cleanup_problems` is populated in `__enter__` and unconditionally folded into `__exit__`'s own `problems` list at the start of every call — the only place it is ever read. Three new parametrized regression tests (one per redundant copy) prove a successful handshake and statement still surface the earlier close failure through `__exit__`.
- **Test safety-net audit, per the review's explicit finding that the twelfth pass's `_ensure_background_statement_torn_down()` relied on `blocked.__exit__()` itself** — the exact implementation many of these tests exercise, meaning a genuinely broken `__exit__()` could make its own safety net silently do nothing. Replaced with `_emergency_teardown()`, which operates directly on the real `multiprocessing.Process` (`is_alive()`/`terminate()`/`kill()`/`join()`) and, when a backend pid was recorded, a fresh independent `pg_terminate_backend()` call — never `blocked.__exit__()`, `_force_stop()`, or any other method under test. Applied to every regression test that creates a process, backend, transaction, advisory lock, watcher, or IPC resource, including the five production-invariant concurrency tests (restructured to construct `_BackgroundStatement` as its own statement before the `with` block, so it remains reachable from the existing `finally: _cleanup_world(...)` block) — none of their assertions, evidence, or resumed-statement behavior changed.
- **Minor:** trimmed a docstring passage in `_worker_main` that duplicated the class docstring's own explanation of the outcome-publication contract almost verbatim, keeping only the worker-specific point (there is no second channel to report a publish failure through) and cross-referencing the class docstring for the rest.
