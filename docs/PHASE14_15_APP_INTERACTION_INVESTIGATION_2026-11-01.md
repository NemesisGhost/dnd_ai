## A. Executive assessment and baseline

The owner's completed First Campaign walkthrough identifies a combination of concrete defects, inconsistencies between existing workspaces, changes to the navigation product model, and new domain capabilities. These should not become one large UI cleanup. The strongest common causes are route-derived context being used as task navigation, inconsistent adoption of existing mutation/read-recovery primitives, and narrowly designed selectors being asked to serve different authorization purposes.

The repository already contains substantial reusable work: record headers, staged workspaces, validated return paths, unsaved-change guards, accessible confirmation dialogs, authoring fields and reference pickers, server-driven eligibility, idempotent authoring commands, and confirmed-write/read-failure recovery. Extend these with explicit contracts and migrate bounded groups of callers. A second generic form, navigation, or mutation framework would create competing behavior.

Source establishes several specific problems: World-time Cancel has an empty handler; account role changes refresh a table that unmounts while loading; New character has no breadcrumb; character routes use different enclosing workspaces; item-definition save success is announced to assistive technology without an equivalent visible success message. Other observations need narrower conclusions: the session-log link can target the already displayed section; authorized unpublished Knowledge already has backend support under compound campaign/world permissions; quest runtime already enumerates all active campaign parties. The timeline hover and empty Event Overview symptoms were not reproduced, and their causes remain unconfirmed.

Invitation roles, symmetric relative-time offsets, persisted quest outcomes/reward execution, and session-linked content are not frontend-only changes. They require separate contract decisions and, in several cases, migrations. The requested actor model must inform the character shell, but a wholesale PC/NPC/creature migration should not be smuggled into breadcrumb repairs.

The supplementary investigation reverified the nine summarized character findings at its stated historical baseline. Those findings are not all current: recheck source before implementation. Publication still does not itself grant character discovery; normal character readers still omit appearance/background; PC authoring still has a type-based exception, and portrayal still depends on an NPC subtype FK. A safe public-profile/revelation foundation must precede expanded character disclosure. The former encounter detail leak claim is superseded by the 2026-11-06 source-and-test review recorded in D6.4.

## D. Shared architecture and app-wide implications

### D1. Navigation, explicit selection and task ancestry

Decisive sources are `portal/src/context/WorkspaceHierarchyProvider.tsx:23–29,100–169`, `portal/src/components/HierarchyContextPanel.tsx:203–252`, `portal/src/components/PortalSidebar.tsx:184–200`, `portal/src/components/CampaignHomeNavGroup.tsx:22–25,128–153`, and `portal/src/hooks/returnState.ts:9–35`. Current hierarchy deliberately derives selected world/timeline/campaign from the route. Some sidebar destinations choose a route campaign, world-associated campaign, or last/startup campaign. Neither mechanism implements the proposed independent, explicit Infobox selection.

Separate three pieces of state: (1) validated execution scope from the route and server, (2) explicit selected context/perspective, and (3) the task's Navbar origin and bounded ancestor path. A viewed character ID is not automatically a selected perspective. All three are navigation/UI state; none authorizes a read or command. Do not display an old selected campaign as if it authorizes a route in a different campaign.

#### D6.5. Safe fields, legacy background and publication

The registry is a classification catalog, not an automatic response redactor or permission grant. Current omission of appearance/background is not a safe reason to start serializing both. The F4 instructions are direct evidence that at least some intended legacy background contains secrets. A blanket background-to-public migration is therefore unsuitable.

Recommended migration policy: preserve all original text and its authoring access; mark legacy background unreviewed/restricted for the new public projection; create separately named public appearance/background, restricted controller briefing and GM-secret fields or records with explicit source/provenance. Never infer safety from a marker's absence, the actor's old NPC/PC kind, existing publication status or a classifier. A legitimately authorized author/reviewer explicitly chooses/copies safe excerpts into a public profile and releases that profile. Consider legacy appearance separately, but require an explicit initial release before making it newly public. Do not move/delete the old background or claim secret material has been cleaned up merely by hiding a label. Preserve GM inspection of the original protected text.

Public-profile release needs a specified version contract. Recommended smallest safe design: immutable public-profile releases with an explicit currently released version pointer, while draft/private edits stay separate. A reveal grants access to that public channel; define whether it follows subsequent deliberate releases (recommended) rather than freezing each audience to a different version. This is narrower than redesigning all canon revision serving but still needs API/schema/review work. If the owner instead chooses live public fields after first release, label that policy explicitly: future saves to those fields become visible immediately. Do not call them “last approved” under that alternative. Existing canonical editing and archival history remain intact.

Campaign-local briefing/secrets and shared-world GM preparation also need distinct scope: the same actor controlled in two campaigns must not carry one campaign's briefing into the other. World-private secrets continue to need world authority; campaign-local GM secrets use explicitly defined campaign rights. Future player-private content remains excluded from both public profiles and GM/controller shortcuts under ADR 0016.

### E2. Relative world time and duration

Current model: `src/dnd_ai/domain/world_time.py`, `commands/world_time.py:164–230`, `api/world_time.py`, and DATABASE_MODEL:236–247 define immutable world-time points. Calendar sort keys are minutes since year zero, custom month lengths with a fixed 24-hour day/60-minute hour. Missing lower components normalize to the start of the parent for ordering. A day-qualified point can have precision `exact` without a minute being explicitly supplied; do not advertise minute precision merely from the enum. Approximate/partial/narrative precision must remain visible.

Narrative creation requires an after anchor and optionally an upper before bound. The server allocates a key between points, or adds 1440 when no later bound exists, under the world-time advisory lock. That allocation is ordering space, not evidence that the fictional event occurred exactly one day later. Anchor relationships/durations are not persisted. There is no implemented dynamic dependency graph to propagate anchor edits; points themselves are immutable.

Separate three operations in UI and API: choose an existing point; record a new immutable point; advance/correct the campaign clock. Recording a time does not advance Now. P07 can share the existing form in a dialog and fix Cancel without changing arithmetic.

P11 adds a relative specification: existing anchor ID, before/after direction, optional positive duration magnitude/unit, and explicit precision/provenance. No duration means relational order, not zero elapsed time. Before-only needs a symmetric allocation path; duration arithmetic must be server-authoritative. Preview and commit must use the same rules and commit must revalidate anchor/world/limits. Keep old sort keys immutable and backfill no invented anchors.

Recommended first arithmetic slice: whole minutes/hours/days under the current calendar model and only where anchor precision supports the requested exactness. Reject unsupported combinations or store an explicitly non-exact relation; do not quietly produce an exact calendar date from a narrative anchor. Define whether zero is permitted as “same moment” separately rather than accepting a contradictory positive before/after offset. Month/year offsets need variable-length/clamping policy and should be a later slice. Worlds with non-24-hour days require a separate calendar/domain migration, not just a wider hour control. Cross-calendar epoch alignment also needs a stated model before claiming exact conversions.

Relative provenance may use additive fields/table linked to the new immutable point. Existing-only anchors make cycles impossible by construction; if later edits/dynamic relationships are introduced, cycle validation becomes necessary. Tests cover negative years, month/year boundaries, range overflow, partial/approximate anchors, before/after equality/ordering, foreign-world IDs, no integer gap, concurrent allocation/idempotent replay, and preservation of existing interval/branch/clock semantics.

### E5. Sessions as linked preparation/play workspaces

Current sessions organize play rather than own world state (DATABASE_MODEL:321 onward). `persistence/tables/campaign.py` stores sessions/participants; `narrative.events` has session provenance; `persistence/tables/encounters.py:48` gives an encounter a single session. `commands/encounter_preparation.py:136–149` validates that owning session. 2. A link stores preparation metadata, ordering and permitted audience; it does not grant target discovery/read/control. Resolve each target through its canonical read model. Apply the owner-approved same-campaign encounter discovery check to character-detail `active_encounter_id` before exposing it through a link or backlink; full character tier does not override encounter audience. 4. Reuse existing runtime operations from the session workspace with optional session provenance validated against campaign/timeline and session state. 5. Preserve Sessions > session > Run > target ancestry and return to the same session section. A target's own page can show only authorized related sessions. Actor inspection within a session retains the actor shell while keeping Sessions origin.
6. Do not silently convert the existing encounter owning-session FK into many-to-many execution ownership. Initial cross-session references can be read/preparation links; continuing encounter operations across sessions needs a separate lifecycle/ownership decision. Completed/archived session links may remain readable under policy while new operational writes remain prohibited.

P15 first delivers GM link management and safe reads; P16 delivers operation provenance, member-facing links/backlinks and the full privacy matrix. Schema migration, link uniqueness/versioning, transactional attach/detach, replay, concurrent revocation and query pagination need tests. Sessions do not receive duplicate quest/dungeon state tables. Full automated combat, reward engines, and creature-template migration are outside these packages.
