# Phase 6 Verification Checklist

Records the verification performed for Phase 6 (Events and interactions) per [PLAN.md §23](PLAN.md#23-delivery-phases) and the exit-review process in [§23.1](PLAN.md#231-phase-exit-review). Delivered as five independently reviewed increments (revisions 057–064 plus `src/dnd_ai/commands`), then a correction pass (revisions 065–068) after a second, more critical exit review found production defects the first review missed — see "Correction Pass" below. **This document does not claim Phase 6 complete.** The corrected branch has not yet been merged, and its final-head CI run has not yet been confirmed; both are outstanding until that run succeeds (see "Verification status" at the end).

## Exit Criteria

- [x] **A player action can resolve into an event and atomic state changes.** `perform_interaction()` + `resolve_check()` (`src/dnd_ai/commands/interactions.py`) run the full vertical slice: a party member attempts to pick a lock on a conditional route, the check succeeds, `world.conditional_route_requirement_satisfied()` confirms the match, and `resolve_check()` records a `narrative.events` row, a `narrative.event_effects` row, opens `campaign.area_connection_state`, and resolves the parent interaction (status, `resulting_event_id`, a `state_change` consequence), all in one transaction — now under a row lock (revision 067/§ Correction Pass item 3) that serializes competing resolutions against the same route. `tests/scenario/test_resolve_conditional_route_check.py::test_a_successful_lockpick_check_opens_the_route_and_records_an_event` proves this through actual application code, not hand-written SQL.
- [x] **Current state and event history remain consistent.** The same test verifies `area_connection_state.last_event_id` points at the event that produced it, and `narrative.event_effects` records the same transition (`connection_status_id`, previous/new value) the state row now reflects. A failed or non-matching check (`test_a_failed_lockpick_check_does_not_open_the_route_or_record_an_event`) leaves no event and no state row — nothing is recorded that didn't actually happen. `campaign.enforce_state_event_timeline()` (revision 066) additionally guarantees `last_event_id` can never cite an event from a different timeline than the state row itself, on all eight `campaign.*_state`/`*_conditions`/`*_resources` tables that carry the column.
- [x] **A branch inherits parent events only through its branch point; a parent event after that point is absent from the branch's effective history, with a scenario test proving the exclusion.** `campaign.effective_events()` (revision 059), proven by `tests/scenario/test_branch_effective_history.py` with a three-level branch chain specifically built to exercise the case a single-level branch cannot (each ancestor bounded by its *immediate child's* branch point, not the target's own).
- [x] **A branch-event reference must identify an event from its parent timeline at or before the declared branch world time; cross-timeline and post-branch references are rejected by the database.** `campaign.timelines.branch_event_id` (revision 058) plus the extended `campaign.enforce_timeline_branch()`, proven by `tests/database/test_timeline_branch_event.py` (valid at-or-before reference accepted; wrong-timeline and after-branch-point references rejected).
- [x] **A failure partway through a multi-domain command leaves no partial write — proven by a test that forces the failure, not by inspecting the transaction boundary.** Proven twice, at two different points in the phase: `tests/database/test_event_state_atomicity.py` (increment 1) shows the *schema* supports it with a hand-written transaction; `tests/scenario/test_resolve_conditional_route_check.py::test_a_failure_partway_through_resolve_check_leaves_no_partial_write` (increment 5) re-proves it through the real `resolve_check()` command, injecting a fault after the check result and event have already been written inside the same transaction and confirming — from an independent connection — that neither survived. The correction pass adds a second, genuinely concurrent regression (`test_two_concurrent_successful_checks_open_the_route_exactly_once`, two real threads released together via a `threading.Barrier`) proving the lock added for item 3 actually serializes competing resolutions rather than merely appearing to in a single-threaded test.
- [x] **A recorded event cannot be edited directly** (docs/ENTITY_LIFECYCLE.md §22 acceptance test, added to scope by the correction pass — see item 1 below). `tests/database/test_narrative_events.py::test_a_recorded_event_cannot_be_edited_directly` proves it literally.

## Correction Pass

A second, more critical exit review of the five-increment implementation (commit `e3ce783`) found production defects the first review's own verification loop did not catch — this section documents them factually. **The claim in an earlier version of this document that "no defect surfaced afterward that required reopening a prior increment" was wrong and has been removed**; this pass is exactly that reopening, for six distinct issues:

1. **Recorded events were not actually immutable.** `docs/ENTITY_LIFECYCLE.md` §15/§20/§22 require it, and the acceptance test explicitly named ("a recorded event cannot be edited directly") was never written. `narrative.events`, its inherited `core.entities` metadata, and its four append-only satellite tables could all be freely `UPDATE`d or `DELETE`d after `event_status = recorded`. **Fixed** by revision 065: `narrative.enforce_recorded_event_immutable()` (content frozen once non-draft; only `recorded → voided`/`recorded → corrected` transitions permitted), `narrative.enforce_recorded_event_entity_immutable()` (freezes `core.entities.canonical_name`/`summary`/`canon_status_id`/`source_id`/`created_by_user_id` for a non-draft event; `lifecycle_status_id`/`archived_at` stay mutable, since archival is a separate, independent dimension), and `narrative.enforce_recorded_event_child_immutable()` (shared function, attached to `event_participants`/`event_locations`/`event_causes`/`event_observations`). `event_effects` is deliberately excluded — it has its own mutable `application_status` lifecycle by design. **Tests:** `tests/database/test_narrative_events.py`, 10 new cases, including the literal §22 acceptance test, the full status-transition matrix, draft-is-still-editable positive cases, and append-only enforcement on all four child tables (`UPDATE` and `DELETE`, each in its own `SAVEPOINT` — see "Bugs found while writing tests" below).
2. **`last_event_id` accepted an event from any timeline, not just the state row's own.** Revision 060's five dungeon-state columns had no check tying the cited event's `timeline_id` to the state row's own `timeline_id` — a state row on timeline A could cite an event that happened on timeline B, undermining "current state and event history remain consistent." `campaign.character_state`/`.character_conditions`/`.character_resources` also never received the `last_event_id` column `DATABASE_MODEL.md` §17 had already said they were owed once `narrative.events` existed — the original review closed that note for the five dungeon tables and missed the three character tables the same note named. **Fixed** by revision 066: one shared `campaign.enforce_state_event_timeline()` function (not five/eight near-duplicate trigger bodies) attached to all eight tables, plus the three new columns. **Tests:** `tests/database/test_dungeon_timeline_state.py` (10 new parametrized cases, one positive/negative pair per table) and `tests/database/test_character_timeline_state.py` (6 new cases).
3. **`resolve_check()` had no concurrency control.** It read `campaign.area_connection_state`, decided the route wasn't yet open, and upserted — all without a lock. Two concurrent successful checks against the same route could each reach that decision before either committed, each produce its own event/effect, and race to overwrite `last_event_id`; the `previous_value` an effect recorded could also be wrong (read before the other caller's write, not the true prior state). **Fixed** in `src/dnd_ai/commands/interactions.py`: `_lock_area_connection()` takes `SELECT ... FOR UPDATE` on the connection's own `world.area_connections` row (always exists, unlike the possibly-absent state row) before evaluating the check; `_area_connection_status()` re-reads the current status under that lock; if the route is already `open` by the time the lock is acquired, the call records its check result but produces no second event/effect/state-write. `previous_status_code` is threaded through to `_open_area_connection()` rather than re-read a second time. **Test:** `tests/scenario/test_resolve_conditional_route_check.py::test_two_concurrent_successful_checks_open_the_route_exactly_once` — two real threads, released together via `threading.Barrier`, both attempt a satisfying check against the same route; exactly one produces an event/effect and opens it.
4. **`resolve_check()` never completed the interaction's own resolution record.** `interaction.interactions.status` stayed `initiated` forever; `resulting_event_id` was never populated even when an event was produced; no `interaction.consequences` row was ever recorded for the state change. A failed or non-matching check also had no coherent terminal state. **Fixed**: `_resolve_interaction()` always transitions the interaction to `status = 'resolved'` (win or lose) and, only when this call produced an event, sets `resulting_event_id` (via `COALESCE`, preserving any value a different check on the same interaction already set) and inserts a `consequence_type = 'state_change'`, `status = 'resolved'` row linking it. Revision 067 separately makes `interaction.actions`/`.targets`/`.check_requests`/`.check_results`/`.external_messages` append-only once the parent interaction leaves `initiated` (a shared `interaction.enforce_interaction_locked(p_interaction_id)` helper, called by five small per-table trigger functions since each reaches its owning interaction through a different join depth). **Tests:** `tests/scenario/test_resolve_conditional_route_check.py` — extended the two existing outcome tests to assert `status`/`resulting_event_id`/consequence linkage, plus a new `test_structural_records_are_immutable_after_resolution`.
5. **The ruleset allow-list reverse guard had two known, undocumented-as-closed gaps.** `interaction.check_requests` and `world.area_connections.required_ability_id`/`required_skill_id` both validate against `rules.ruleset_allowed_for_world()` on write, but `rules.enforce_world_ruleset_still_in_use()` — the reverse guard blocking removal/repointing of a `rules.world_rulesets` row while something depends on it — had no usage clause for either, same as revision 037's own documented pattern for every other ruleset-scoped category. Revision 061's docstring already named the `check_requests` half explicitly as "a known, non-blocking gap"; the `area_connections` half (added later, revision 064) was never flagged at all. **Fixed** by revision 068, following the exact two-sided pattern revisions 027/031/037 established. **Tests:** `tests/database/test_world_ruleset_dependency_and_concurrency.py`, 4 new cases (DELETE + UPDATE/repoint, for each of the two new consumers).
6. **`test_role_grants.py`'s `MANAGED_TABLES` list silently stopped at Phase 4.** Its own comment claimed "every table the project has created so far," but every Phase 5 table (locations, dungeons, knowledge — 22 tables) and every Phase 6 table (narrative, interaction — 18 tables), 41 in total (plus `audit.change_log`, already and correctly excluded), had never actually been checked for correct ownership or grants. **Fixed**: all 41 added to `MANAGED_TABLES`, and a new schema-driven tripwire test (`test_managed_tables_covers_every_table_in_every_managed_schema`) added so this specific gap cannot recur silently — it compares `MANAGED_TABLES ∪ EXCLUDED_TABLES` against a live `pg_tables` query over the managed schemas and fails, by name, on any table either side is missing. `core.alembic_version` was found and added to `EXCLUDED_TABLES` by this new test on its first run (Alembic's own bookkeeping table, not project data).

### Bugs found while writing the correction-pass tests

These are test-writing/tooling issues, not schema-design defects, listed separately per this project's own convention of distinguishing the two:

- Three of the new tests in `test_narrative_events.py` initially issued a second expected-to-fail statement on the same `db_connection` after the first one's `pytest.raises` had already caught an error — PostgreSQL aborts the whole transaction on any statement error, so the second statement failed with a generic "current transaction is aborted" instead of the real assertion. Fixed with the project's own established `db_connection.begin_nested()` (SAVEPOINT) pattern, already used elsewhere (`test_dungeon_structural_mutation_safety.py` and others).
- The same scope-columns test picked `other_type = event_types WHERE code = 'other'` as the "different" `event_type_id` to update to, not noticing `make_event()` already defaults new events to `event_type_code = 'other'` — the update was a no-op against the row's actual current value, so nothing raised. Fixed by using `mechanism_activated` instead.
- The `event_locations` case of the append-only child-table test passed a bare `core.entities` row (any type) as the "other" location, but `event_locations.location_id` references `world.locations` specifically (a CTI subtype table, not `core.entities` directly) — the INSERT failed on an unrelated FK violation before the immutability trigger was ever reached. Fixed by using `make_location()` for that one case instead of a bare entity.
- The scope-columns test also originally reused `f.event_id` (which has `campaign_id`/`session_id` set) to test changing `timeline_id` alone; that trips `narrative.enforce_event_consistency()`'s own pre-existing "campaign still belongs to this timeline" check first, before the new immutability trigger gets a chance — a real guard, but the wrong one for what the test claims to prove. Fixed by using a bare event with no campaign/session for that specific case.
- Both `tests/scenario/test_resolve_conditional_route_check.py` and `tests/database/test_commands_record_event.py` create real, committed `recorded` events (via `postgres_engine`, not the rolled-back `db_connection` fixture) and clean them up in teardown by deleting `core.entities` — which now correctly fails under revision 065's new append-only protection, exactly the behavior under test. Fixed by having teardown issue `SET LOCAL session_replication_role = replica` for that one cleanup transaction, bypassing triggers for the single case that legitimately needs to remove locked test data anyway.

None of these five were schema-design defects — each was a test correctly exercising new production behavior it hadn't yet been written to expect.
