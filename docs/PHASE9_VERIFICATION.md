## Exit Criteria

- [x] **Item ownership and possession are distinct and independently queryable.** `campaign.item_ownership` (legal owner, nullable for unclaimed treasure) and `campaign.inventory_entries` (current holder/container/location) are separate tables, each with its own same-world guard and one-current-row-per-(timeline, item) uniqueness — proven by `tests/database/test_item_domain.py`'s ownership/inventory sections, and by `campaign.character_inventory` (a read view joining both) correctly reporting `is_owned_by_holder = false` when the two diverge (a borrowed or stolen item).
- [x] **Combat resolved through `resolve_combat_turn` updates persistent character state through a causal event, entirely through the command layer.** `tests/scenario/test_encounter_commands.py::test_a_damaging_combat_turn_updates_persistent_character_state` drives the real command end-to-end: `campaign.character_state.current_hit_points` changes, a `narrative.events` row (`combat_damage_dealt`) is recorded citing the encounter via `narrative.event_causes.cause_encounter_id`, and a `narrative.event_effects` row links the two — all in one transaction (CLAUDE.md rule 6). `test_a_miss_leaves_character_state_and_events_untouched` proves the companion claim from `DATABASE_MODEL.md §12.3` ("not every attack roll needs a permanent world event"): a miss updates only the turn/combat_action record, nothing persistent.
- [x] **An external system's identifier for a world entity, and a synchronization job's lifecycle, are representable and round-trip through `integration.*` without any client writing PostgreSQL directly.** `tests/scenario/test_foundry_sync_commands.py::test_an_inbound_foundry_combat_payload_updates_persistent_state` drives `apply_foundry_combat_sync()` — an adapter-facing command that itself calls the *real* `resolve_combat_turn()`, never a raw table write — and verifies the resulting `integration.sync_jobs` row (`completed`, `resulting_event_id` set), `integration.delivery_attempts` row, `integration.sync_state` row (`synced`), and the underlying character-state change all agree. `test_re_registering_the_same_external_actor_is_idempotent` proves `map_external_identifier()`'s upsert behavior.
- [x] ~~Foundry combat can update persistent character and world state~~ — moved to Phase 11 (Foundry MVP), where it is provable against a live deployment. The claim above is the same mutation, proven short of "live."

## Review Correction Pass (2026-08-09, after CI proof, before merge)

A review of the pushed PR (head `bcceb79`, CI run [`31312847929`](https://github.com/NemesisGhost/dnd_ai/actions/runs/31312847929) — see "Verification status" below for why that run's own result is not the relevant signal here) found four gaps in `apply_foundry_combat_sync()`/`resolve_combat_turn()`/`transfer_item_possession()`, none caught by the original exit-criteria tests because none of them exercised redelivery, a miss-with-damage combination, or a second transfer. **This correction pass is fully verified locally (see below) but has not been pushed** — the fixes are recorded here, in revision 079 and the affected command modules, on this branch, awaiting an explicit push/PR-update decision.

1. **`apply_foundry_combat_sync()` was not idempotent.** An external adapter redelivering the same operation (a documented at-least-once-delivery reality, `SYSTEM_ARCHITECTURE.md §15.1`) would create a second `interaction.actions`/`.combat_actions` row, a second `narrative.encounter_turns` row, a second `combat_damage_dealt` event, and apply damage a second time — nothing keyed the operation. **Fixed:** `integration.sync_jobs` gained a required-for-Foundry-jobs `external_operation_id` (caller-supplied idempotency key, unique per `external_system_id` — `ux_sync_jobs_system_operation`) and `resulting_encounter_turn_id` (lets a replay reconstruct its original result without re-executing the domain command). `apply_foundry_combat_sync()` now takes `external_operation_id` as a required argument, holds a session-scoped Postgres advisory lock keyed on `(external_system_id, external_operation_id)` for its entire duration (a side-channel connection, held across all of the function's own steps), and on a replay reconstructs and returns the original `ResolveCombatTurnResult` instead of re-executing the domain command. A concurrent second caller for the same operation blocks at lock acquisition until the first reaches a terminal status, then replays. A replay whose payload differs from the one originally recorded raises `ConflictingSyncPayloadError`, checked before status is ever consulted — see item 4 in the second correction pass below, which closed an ambiguity in how that ordering was originally documented. A prior `failed` (or crash-orphaned `in_progress`) job is retried under the same `sync_jobs` row, logging a second `integration.delivery_attempts` row rather than erroring. **Tests:** `tests/scenario/test_foundry_sync_commands.py` — `test_replaying_the_same_operation_returns_the_original_result_without_duplicating_work`, `test_concurrent_submissions_of_the_same_operation_apply_damage_exactly_once` (two real threads, one advisory-lock-blocked), `test_reusing_an_operation_id_with_a_conflicting_payload_raises`, `test_retrying_a_failed_operation_id_succeeds_and_adds_a_second_delivery_attempt`; `tests/database/test_integration_domain.py` — the new unique-constraint positive/negative cases.
2. **`resolve_combat_turn()` applied damage even when `hit=False`.** The damage-application condition checked only `damage_amount`/`target_entity_id`, never `hit` — a caller reporting both a miss and a rolled damage number (a submitted-but-not-landed roll) would still have it applied and an event recorded. **Fixed:** the condition now requires `hit is not False`; `hit=None` still applies damage when `damage_amount` is positive (preserving behavior for callers with no hit/miss concept — documented explicitly as the deliberate choice, not an oversight); `hit=False` is now a hard stop regardless of `damage_amount`. The submitted `damage_amount` is still recorded on `interaction.combat_actions` either way, since a submitted-but-missed roll is legitimate payload/result data. **Test:** `tests/scenario/test_encounter_commands.py::test_a_miss_with_a_submitted_damage_amount_still_never_applies_it`.
3. **A `resolve_combat_turn()` exception after the sync job was claimed left the job stuck `in_progress` forever**, with no error recorded and the caller's exception the only signal anything happened. **Fixed:** `apply_foundry_combat_sync()` now wraps the domain-mutation step; on any exception, it marks the job `failed` with the exception's message, logs a failed `delivery_attempts` row, creates no `sync_state` row, and re-raises the *original* exception — a failure in the bookkeeping itself (caught separately) can never replace it. The same never-mask-the-original-exception discipline was applied to the advisory-lock release in the `finally` block, found during this same review pass. **Test:** `test_a_failed_combat_sync_records_the_failure_and_leaves_domain_state_unchanged` (a non-participant actor triggers the domain command's own `ValueError`; asserts the failure bookkeeping and that no event/HP change survived the rolled-back domain transaction).
4. **`transfer_item_possession()` always recorded `narrative.event_effects.previous_value` as `NULL`**, even for a second/subsequent transfer where a real prior holder/container/location existed. **Fixed:** `_lock_inventory_entry()` now returns the existing row's `holder_entity_id`/`container_id`/`location_id` (not just its id), and `transfer_item_possession()` uses them to build `previous_value` in the same shape as `new_value` — `NULL` only for a genuine first placement. **Test:** `tests/scenario/test_item_commands.py::test_a_second_transfer_records_the_real_previous_location_in_the_event_effect`.

This pass's own verification (documented at the time as "fully verified locally") described a residual risk in item 1's design: if the domain mutation succeeded but the *separate* transaction completing the sync job then failed, the mutation stayed committed against a job stuck `in_progress`. That gap is what the second correction pass below closes — the risk note is removed rather than left standing once no longer true (see item 1 there).

No test-runner, fixture-framework, or CI-mechanism changes were made — every fix above is a production schema/command change, and every new test exercises production behavior directly.

## Second Review Correction Pass (2026-08-09, same day, before either pass was pushed)

A further review of the (still unpushed) correction pass above found that its own idempotency design had a real gap, reachable through ordinary concurrency rather than a rare crash: `apply_foundry_combat_sync()` committed the domain mutation (`resolve_combat_turn()`, which opens and commits its own transaction) and then ran `_complete_sync_job()` as a *second*, separate transaction. A failure completing the sync job — including the very race this pass closes in item 2 — left the combat mutation committed while the job was never marked `completed`. **This second pass is fully verified locally (see "Verification status" below) but, like the first, has not been pushed.**

1. **The domain mutation and its completion bookkeeping were not atomic.** **Fixed:** `dnd_ai.commands.encounters.resolve_combat_turn()` was split into a public convenience wrapper (unchanged signature and transaction semantics for direct callers) and `_resolve_combat_turn_impl()`, the same logic running on a caller-supplied `Connection` instead of opening its own transaction — the same composition pattern `_insert_event_row()` already established for cross-command reuse within one transaction. `apply_foundry_combat_sync()` now has three transactions instead of two, never overlapping in a way that can leave the mutation committed against an unfinished job: **(1) claim** — read or create the `sync_jobs` row, always committed before domain work starts; **(2) work** — `_resolve_combat_turn_impl()` and `_complete_sync_job()` together in one `engine.begin()`, so either both commit (turn, action, event, HP change, the successful delivery attempt, and the `sync_state` upsert all become visible together) or any exception rolls back every one of them, leaving the job exactly as the claim step left it; **(3) fail** — reached only once step 2 has fully rolled back, in a fresh transaction, marking the already-persisted job `failed` and logging a failed delivery attempt, then re-raising the original exception. **Test:** `tests/scenario/test_foundry_sync_commands.py::test_a_completion_failure_rolls_back_the_domain_mutation` — a fault injected into `_complete_sync_job()` via `monkeypatch` (the same fault-injection idiom `test_resolve_conditional_route_check.py` established for this project) after the combat statements in the same transaction have already executed; asserts the turn, event, and HP change all roll back, the job is recorded `failed`, and retrying the same operation once the injected failure is removed succeeds exactly once (one turn, `completed` status, two delivery attempts).
2. **`_complete_sync_job()`'s `integration.sync_state` upsert used SELECT-then-INSERT, which races.** Two different `external_operation_id`s completing concurrently for the *same* target (the advisory lock only serializes callers sharing one operation id, not different ones) could both observe no existing `sync_state` row and both attempt an `INSERT` — the loser violating `ux_sync_state_system_entity`/`ux_sync_state_system_encounter` *after* its own domain mutation had already committed under the old two-transaction design (item 1 above), or, once that was fixed, still spuriously failing the whole "work" transaction it now shares with the mutation. **Fixed:** the SELECT-then-INSERT was replaced with a single atomic `INSERT ... ON CONFLICT (...) WHERE ... DO UPDATE`, targeting whichever of `sync_state`'s two partial unique indexes matches the target actually set (`ck_sync_state_exactly_one_target` guarantees exactly one is — both the entity and the encounter path are implemented, per the schema's own support for both, though only the encounter path has a current caller). Postgres serializes the two upserts at the row level: the second writer blocks on the first's row lock until it commits, then applies its own update — `last_sync_job_id` deterministically ends up as whichever operation genuinely committed last, and exactly one current row exists for the target either way. The uniqueness constraints themselves were not weakened or removed. **Test:** `tests/scenario/test_foundry_sync_commands.py::test_two_different_operations_for_the_same_encounter_complete_independently` — two real threads, two distinct operation ids and combat turns (different actors, so no `encounter_turns` collision of their own) targeting the same encounter; asserts both complete, both HP changes applied exactly once, exactly one `sync_state` row exists afterward, and no job is left `in_progress`.
3. **The conflict-vs-retry ordering was correct in code but ambiguously documented.** The payload-conflict check already ran unconditionally before the status branch (so a failed job resubmitted with a different payload already raised `ConflictingSyncPayloadError` rather than silently retrying) — but the module docstring described "a replay whose payload differs raises" and "a prior failed attempt is retried" as if they were two independent, parallel behaviors, rather than making explicit that the payload check is a precondition for *both* the replay and the retry paths. **Fixed:** the docstring in `dnd_ai/commands/integration.py` and this file now state the ordering explicitly — payload match is checked first, unconditionally; only once it matches does status decide replay vs. retry. **Test:** `tests/scenario/test_foundry_sync_commands.py::test_reusing_a_failed_operations_id_with_a_different_payload_raises_conflict` — a failed job's operation id resubmitted with a different `damage_amount` raises `ConflictingSyncPayloadError` rather than retrying with the new value.

No test-runner, fixture-framework, or CI-mechanism changes were made — every fix above is a production schema/command change, and every new test exercises production behavior directly.

## Third Review Correction Pass (2026-08-09, same day, before any pass was pushed)

A further review of the (still unpushed) second correction pass found that its own atomic-transaction fix had introduced a connection-pool deadlock, and that its advisory-lock cleanup didn't account for an unlock that can't be confirmed. **This third pass is fully verified locally (see "Verification status" below) but, like the first two, has not been pushed.**

1. **The claim/work/fail steps each opened a second, independent pooled connection while the advisory-lock connection sat idle.** The second pass's `apply_foundry_combat_sync()` held `lock_connection` for the advisory lock, then used `engine.begin()` — a *different* connection checked out from the pool — for each of the three transactions. Under a small pool, a caller waiting on the advisory lock could consume the pool's remaining connections, leaving the lock holder itself unable to obtain one for its own steps and deadlocking permanently — a caller could starve itself out of the very connection it needed to finish and release the lock. **Fixed:** the claim, work, and fail transactions now run sequentially on `lock_connection` itself, via `lock_connection.begin()` rather than `engine.begin()` — `_find_existing_sync_job()`, `_insert_sync_job()`, `_resolve_combat_turn_impl()`, `_complete_sync_job()`, and `_fail_sync_job()` are all called with `lock_connection` as their `Connection` argument. No step ever requests a second connection from the pool while the lock is held, so one call to `apply_foundry_combat_sync()` never needs more than a single pooled connection for its entire duration. Replay, retry, conflicting-payload, and atomic-rollback semantics are unchanged — only which connection object each step runs on. **Tests:** `tests/scenario/test_foundry_sync_commands.py::test_a_small_pool_does_not_deadlock_a_single_call` (an engine with `pool_size=1, max_overflow=0, pool_timeout=5` — a single call must complete without ever needing a second connection) and `::test_two_operations_on_the_same_target_do_not_starve_a_small_pool` (two genuinely concurrent, distinct operation ids against the same `pool_size=1` engine — the pool serializes them and both complete, neither starves).
2. **Advisory-lock release didn't distinguish "confirmed released" from "unknown."** The prior cleanup executed the unlock statement and swallowed any exception, but never inspected `pg_advisory_unlock()`'s own boolean result, and always returned the connection to the pool regardless. If the unlock statement raised, or if PostgreSQL reported the session didn't actually hold the lock, the connection went back to the pool anyway — a physical connection that might still hold a session-scoped advisory lock could be handed to a future, unrelated caller, who would then silently block if it happened to need the same lock key. **Fixed:** the unlock logic was factored into `_unlock_advisory_lock(connection, lock_params) -> bool`, which executes the unlock statement, commits, and returns whether PostgreSQL confirms this session held (and released) the lock. `apply_foundry_combat_sync()`'s `finally` block now calls `.close()` (return to pool) only when that's confirmed `True`; on any exception or an unconfirmed result, it calls `.invalidate()` instead, discarding the underlying DBAPI connection rather than recycling it. Neither path re-raises, so this never masks an exception already propagating from the try block above. **Test:** `tests/scenario/test_foundry_sync_commands.py::test_an_unlock_failure_invalidates_the_connection_and_a_later_call_does_not_block` — `_unlock_advisory_lock()` is monkeypatched to raise; asserts `Connection.invalidate()` was actually called (via a spy), then removes the injected failure and proves a replay of the same operation id completes promptly on a fresh thread rather than blocking on an orphaned session lock.
3. **Revision 079's docstring contradicted the implementation on failed-retry conflicts.** It read "Only a payload mismatch under the same operation id is rejected; a differently-shaped retry of a job that never actually succeeded is exactly what delivery_attempts exists for" — worded as if a failed job's retry were exempt from the payload check, when the code (and `test_reusing_a_failed_operations_id_with_a_different_payload_raises_conflict`, added in the second pass) already rejects a payload mismatch under a failed job exactly as it does under a completed one. **Fixed:** the docstring in `database/migrations/versions/079_integration_domain.py` now states the actual contract plainly — a failed job may be retried under the same operation id only with the same canonical payload; every payload mismatch is a conflict, regardless of the prior job's status. No test change was needed; `test_reusing_a_failed_operations_id_with_a_different_payload_raises_conflict` (second pass) already proves the corrected wording.

No test-runner, fixture-framework, or CI-mechanism changes were made — every fix above is a production command/documentation change, and every new test exercises production behavior directly.

## Fourth Review Correction Pass (2026-08-09, same day, before any pass was pushed)

Two further items, closing out this correction cycle: a leftover half-step in the third pass's cleanup hardening, and a direct (but narrowly scoped) response to the CI anomaly recorded under "Before the review correction pass" above — the anomaly that originally prompted this whole review, not a Phase 9 domain defect, and not treated as one here. **This fourth pass is fully verified locally (see "Verification status" below) but, like the first three, has not been pushed.**

1. **The unconfirmed-unlock cleanup path invalidated `lock_connection` but never closed the wrapper.** `Connection.invalidate()` discards the underlying DBAPI connection so the physical PostgreSQL session can never return to the pool, but it does not itself finalize the SQLAlchemy `Connection` Python object — leaving that call unpaired can leave the wrapper's own pool-bookkeeping slot looking perpetually checked out. **Fixed:** the unconfirmed-unlock branch now calls `lock_connection.close()` immediately after `lock_connection.invalidate()`, each guarded independently with `contextlib.suppress(Exception)` so neither can mask an exception already propagating from the try block above, and a failure in one doesn't prevent the other from being attempted. **Test:** `tests/scenario/test_foundry_sync_commands.py::test_an_unlock_failure_invalidates_the_connection_and_a_later_call_does_not_block` was extended with a second spy (on `Connection.close`) proving `close()` is called exactly once, on the *same* connection wrapper `invalidate()` was called on — not just that invalidation happened.
2. **PR #21's CI anomaly (documented above, not a Phase 9 domain defect) is a real reliability gap worth closing in the test engines regardless of its exact cause, since the evidence is consistent with (though doesn't prove) a mechanism these settings directly address.** The GitHub Actions evidence — 2,278 tests passed, `SSL error: unexpected eof while reading` on a simple lookup ~40 minutes into a ~67-minute job, no assertion/schema/migration/constraint failure — proves the connection was interrupted; it does **not** prove whether that connection went stale while idle in the pool and was then reused, or was dropped while actively executing the statement. **Fixed:** `tests/conftest.py`'s `postgres_engine()` fixture now passes `pool_pre_ping=True` and `pool_recycle=1800` (30 minutes) on both engines it can construct — the preprovisioned `DND_AI_TEST_DATABASE_URL` path and the dynamically created per-session test-database path — via a shared `_test_engine_kwargs()` helper so both stay in sync. `pool_pre_ping` issues a lightweight liveness check on every checkout and transparently discards/replaces a connection that fails it — mitigating the *stale-at-checkout* mechanism specifically, a well-documented failure mode for long-lived pooled connections against RDS, and one plausible (not confirmed) explanation for what was observed; `pool_recycle` proactively retires pooled connections older than 30 minutes rather than waiting for pre-ping to catch them reactively. **This does not, and cannot, protect a connection that dies mid-statement while a test is actively using it** — there is no safe way to replay an interrupted statement, so that failure mode, if it was the actual cause, still surfaces as a real test error, exactly as before; nothing here silently retries or conceals a test failure of any kind. The two short-lived admin/cleanup engines (`CREATE DATABASE`/`DROP DATABASE`, created and disposed within the same few statements) deliberately did **not** get this treatment — they are never held open long enough to go stale, so the protection would add nothing. **Tests:** `tests/unit/test_conftest_guards.py` gained three cases against the new pure `_test_engine_kwargs()` helper (`test_test_engine_kwargs_enables_pre_ping`, `test_test_engine_kwargs_recycles_before_a_typical_ci_run_completes`, `test_test_engine_kwargs_has_no_unexpected_keys`) — deliberately asserting on the plain dict of kwargs this project's own code constructs, not on SQLAlchemy's own (partly private) `Pool`/`Engine` internals, so the coverage doesn't couple to implementation details outside this codebase. Nothing about the fixture's fail-loud configuration guards (`DatabaseConfigurationError`/`UnsupportedPostgresVersionError`) changed, and the full local suite (below) exercises `postgres_engine()` itself thousands of times across every `tests/database`/`tests/scenario` test, so the new kwargs are proven not to break engine construction, not just asserted as correct in isolation.

**Important scope note:** this pass changes test infrastructure only (`tests/conftest.py`, `tests/unit/test_conftest_guards.py`) — no Phase 9 database asset (a migration, a `persistence/tables/*.py` module, a command) was touched to address the CI anomaly, per instruction. `pool_pre_ping`/`pool_recycle` mitigate one plausible mechanism consistent with the evidence (a stale pooled connection reused at checkout); they do not, and cannot, prove that mechanism is what actually happened on AWS's side, or rule out a mid-statement drop instead — this file initially overstated that certainty and was corrected in the fifth pass below. Whether the anomaly recurs on a fresh CI run is something only a fresh CI run can answer — see "Verification status" below.

## Fifth Review Correction Pass (2026-08-09, same day, before any pass was pushed)

Two items: the last exception-safety gap in advisory-lock cleanup, and a documentation correction to the fourth pass's CI-anomaly language, which had overstated what the GitHub Actions evidence actually proves. **This fifth pass is fully verified locally (see "Verification status" below) but, like the first four, has not been pushed.**

1. **Advisory-lock cleanup was not exception-safe on two remaining paths.** The confirmed-unlock branch called `lock_connection.close()` unguarded — a close() failure there could replace an exception already propagating from claim/work/failure processing, exactly the class of bug the third and fourth passes closed everywhere else in this function. Separately, the unconfirmed-unlock branch's fallback was too weak: if `invalidate()` itself raised (not just returned an unconfirmed result), the code still fell through to an ordinary `close()` — but an ordinary close() on a connection whose invalidation was never confirmed to have discarded the DBAPI connection returns that (possibly still lock-owning) physical session straight back to the pool, exactly the outcome invalidate() exists to prevent. **Fixed:** the entire cleanup body was extracted into `_release_lock_connection(connection, lock_params)`, called from `apply_foundry_combat_sync()`'s `finally` block, with every step independently guarded so nothing in it can mask a propagating exception. Its state machine: confirmed unlock → guarded `close()`; unconfirmed unlock → try `invalidate()`, and if that itself raises, fall back to `detach()` (the documented SQLAlchemy mechanism for severing a `Connection` from its pool's rotation) followed by `close()`, which then physically closes the DBAPI connection — terminating the backend session and releasing any lock it held — instead of recycling it. **Tests:** `tests/scenario/test_foundry_sync_commands.py` gained two cases. `test_a_close_failure_after_confirmed_unlock_does_not_mask_a_domain_exception` forces both a genuine domain failure (non-participant actor) and a `close()` that always raises a different exception, and asserts only the domain exception ever surfaces. `test_an_invalidate_failure_falls_back_to_detach_and_a_later_call_does_not_block` forces both the unlock and `invalidate()` to raise, confirms via spies that `detach()`/`close()` both fire on the same connection object, then — rather than stopping at "the methods were called" — directly probes PostgreSQL with `pg_try_advisory_lock()` on the same key and asserts it succeeds, proving the backend session was actually torn down rather than merely believed to be; it then also proves (as the third/fourth passes' tests did) that a same-operation-id replay on a separate thread completes rather than blocking.
2. **The fourth pass's CI-anomaly language overstated what the evidence proves.** It described "a pooled connection going stale between checkouts" and "the signature of a pooled connection going stale mid-run" as the identified cause, when the GitHub Actions evidence — 2,278 tests passed, `SSL error: unexpected eof while reading` on an unrelated simple lookup ~40 minutes in, no assertion/schema/migration/constraint failure — proves only that the connection was interrupted, not which of two plausible mechanisms caused it (stale-and-reused-at-checkout, vs. dropped-mid-statement). **Fixed:** the corresponding language in `tests/conftest.py`'s pool-resilience comment and in this file's "Before the review correction pass" and "Fourth Review Correction Pass" sections above now describes both mechanisms as plausible and unproven, states plainly that `pool_pre_ping`/`pool_recycle` address only the stale-at-checkout mechanism and cannot help with (or claim to fix) a mid-statement drop, and does not claim the setting will resolve PR #21 until a fresh CI run on the corrected head actually passes. No code or test change was needed for this item — it is a documentation-accuracy correction only.

No test-runner, fixture-framework, or CI-mechanism changes were made — every fix above is a production command/documentation change, and every new test exercises production behavior directly.

## Sixth Review Correction Pass (2026-08-09, same day, before any pass was pushed)

One item: the final edge in the fifth pass's own `detach()` fallback, which itself assumed detach() would succeed once reached.

1. **A failed `detach()` still fell through to an ordinary `close()`.** The fifth pass's fallback — try `invalidate()`, and on failure try `detach()` then `close()` — called `close()` unconditionally after attempting `detach()`, regardless of whether `detach()` itself had actually succeeded. If both `invalidate()` and `detach()` raised, the connection was still fully attached to the pool at the point `close()` ran, so that `close()` would return a possibly still lock-owning physical session straight back into rotation for some future, unrelated caller — precisely the outcome every earlier step in this state machine exists to prevent, now reachable through the fallback's own fallback failing. **Fixed:** `_release_lock_connection()` now tracks whether `detach()` actually succeeded in a local variable and calls `close()` only when it did. If both `invalidate()` and `detach()` raise, **no** `close()` is called at all. **Test:** `tests/scenario/test_foundry_sync_commands.py::test_a_double_failure_after_invalidate_and_detach_fail_never_closes_the_still_attached_wrapper` (renamed in the seventh pass — see below) forced the unlock, `invalidate()`, and `detach()` to all raise, and proved via a `Connection.close` spy that it was never called.

This pass's own account of what omitting `close()` achieves was incomplete — see item 1 of the seventh pass below, which closes the remaining gap and corrects the "deliberately abandoned wrapper is sufficient" framing this pass originally used.

## Seventh Review Correction Pass (2026-08-09, same day, before any pass was pushed)

One item: the sixth pass's "abandon the wrapper" strategy assumed that simply not calling `close()` was enough to guarantee a double-invalidate/detach-failure connection could never return to the pool. It is not.

1. **An unreferenced, unclosed connection is still eligible for garbage collection — and SQLAlchemy's pooled-connection wrapper can implement a finalizer that returns a never-explicitly-closed connection to the pool on its own.** Once `apply_foundry_combat_sync()` returns, its local `lock_connection` variable goes out of scope; if nothing else references the object, it becomes eligible for GC, and finalization could reach the exact outcome the whole state machine exists to prevent — a possibly still lock-owning physical session handed back into the pool's rotation — just via Python's own memory management instead of an explicit `close()` call the sixth pass had already closed off. **Fixed:** added `_quarantine_lock_connection(connection, lock_params)` to `dnd_ai/commands/integration.py` — a private, thread-safe (`threading.Lock`-guarded), process-lifetime module-level list (`_QUARANTINED_LOCK_CONNECTIONS`). `_release_lock_connection()`'s double-failure branch now calls it instead of doing nothing: appending the connection gives it a strong reference that outlives the caller's stack frame for the rest of the process's life, so the garbage collector can never finalize it and no implicit return-to-pool can happen. This is logged at `CRITICAL` (via a module-level `logger = logging.getLogger(__name__)`) so the resulting leaked pool capacity is operationally visible rather than a silent, slow leak — the log includes only the already-non-secret lock identifiers (`external_system_id`, `external_operation_id`) and the running quarantine count, never credentials or the operation's payload. The quarantine is deliberately narrow: nothing retries, closes, or recycles a quarantined connection automatically — doing so would reintroduce the exact risk this mechanism exists to eliminate — and reclaiming the permanently leaked capacity requires a process restart or deliberate, informed operator intervention, never an automatic path inside this module. No private SQLAlchemy `Pool`/`Engine`/DBAPI internals are used; the quarantine list is this project's own code, and `invalidate()`/`detach()` remain the only two public SQLAlchemy mechanisms attempted before it. The quarantine call itself is wrapped in `contextlib.suppress(Exception)`, preserving the same guarantee every other step in `_release_lock_connection()` already has: nothing in cleanup can mask the operation's original result or exception. **Test:** `tests/scenario/test_foundry_sync_commands.py::test_a_double_failure_after_invalidate_and_detach_fail_quarantines_the_connection` (renamed from the sixth pass's version) forces the unlock, `invalidate()`, and `detach()` to all fail, then proves the *full* guarantee rather than just the absence of a `close()` call: `close()` is never invoked; the exact connection object is present by identity in `_QUARANTINED_LOCK_CONNECTIONS` after the call returns; and — after the test drops its own strong reference and runs `gc.collect()` — a `weakref` to the connection is still alive, proving the quarantine list itself, not an incidental leftover reference, is what keeps it alive. Cleanup runs in a `finally` block (so it still executes even if an assertion above fails): it restores the real SQLAlchemy methods via `monkeypatch.undo()`, removes the connection from the quarantine list, and genuinely invalidates and closes it — releasing the real, still-held session-scoped advisory lock and returning `postgres_engine`'s shared pool to its original capacity, so the test leaves no quarantined connection, leaked pool slot, or held lock behind for any other test.

No test-runner, fixture-framework, or CI-mechanism changes were made — every fix above is a production command change, and the updated test exercises production behavior directly (including its own cleanup, which is itself production-adjacent test infrastructure but touches no shared fixture or CI mechanism).
