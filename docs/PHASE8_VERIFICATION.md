# Phase 8 Verification Checklist

Records the verification performed for Phase 8 (Relationships and organizations) per [PLAN.md §23](PLAN.md#23-delivery-phases) and the exit-review process in [§23.1](PLAN.md#231-phase-exit-review). Delivered as a single revision covering this phase's full scope: the universal relationship model, specialized relationships, the organization/business/government/religious-organization/military-unit/political-faction CTI hierarchy, the religion/religious-affiliation distinction, and the two timeline-state tables (`campaign.organization_state`/`campaign.relationship_state`) `DATABASE_MODEL.md §17` had already named but no earlier phase built. Two application-layer commands (`src/dnd_ai/commands/relationships.py`): `evolve_relationship_reaction()` and `update_organization_status()`. The migration was originally numbered `075_relationships_and_orgs` (chained after `074_phase7_correction_pass`) and locally verified on that basis. Before it merged, Phase 7's own post-merge correction pass claimed revision `075` for an unrelated fix (`075_phase7_reparent_guards`, [docs/PHASE7_VERIFICATION.md](PHASE7_VERIFICATION.md)), and PR #18 was opened without rebasing onto it — creating a genuine two-head fork in the Alembic graph once both existed side by side. GitHub Actions run [`31212270434`](https://github.com/NemesisGhost/dnd_ai/actions/runs/31212270434) caught this: the empty-database `alembic upgrade head` step failed because two heads existed, and all database/scenario tests were skipped as a result. A deployable-integrity correction pass (below) renumbered the migration to `076_relationships_and_orgs`, re-chained it after `075_phase7_reparent_guards`, and closed three further gaps a review found alongside the graph fork. **Phase 8 is complete on this corrected basis.**

## Exit Criteria

- [x] **NPC and faction reactions can evolve from events.** `evolve_relationship_reaction()` records a `narrative.events` row (`relationship_changed`), updates `campaign.relationship_state` to match, and links the two through a `narrative.event_effects` row (`target_relationship_id`) — all in one transaction, per CLAUDE.md rule 6. `tests/scenario/test_relationship_reactions.py::test_an_event_changes_a_factions_subjective_reaction` proves this through actual application code: a criminal-organization faction's `affinity`/`trust`/`emotional_tone` toward the party changes in response to a recorded event, while the authored `world.relationship_perspectives` baseline (asserted separately) is left untouched — proving the definition/timeline-state split, not just the mutation. `update_organization_status()` proves the organization half of the same claim (`test_an_event_changes_an_organizations_operational_status` — a faction banned as a result of an event).
- [x] **Shared and subjective relationship data are separate.** `campaign.relationship_state` reuses `campaign.quest_state`'s nullable-dimension idiom: `perspective_holder_entity_id IS NULL` is the relationship's shared/objective status; set, it is one participant's own current reaction — enforced structurally by two partial unique indexes (`ux_relationship_state_timeline_relationship_no_holder`/`_holder`), not by convention alone. `tests/database/test_relationships_and_organizations.py::test_shared_and_per_holder_relationship_state_can_coexist` and `tests/scenario/test_relationship_reactions.py::test_shared_and_subjective_relationship_state_evolve_independently` both prove the two rows exist independently and can diverge (e.g. the shared status remains `active` while one participant's own reaction moves to `estranged`).

## Deployable-Integrity Correction Pass

A review of PR #18's failed CI run found four defects, none of which the original exit-criteria tests could have caught (all pre-date any application-layer command reaching the affected tables):

1. **Two-head Alembic graph.** `075_relationships_and_orgs` (`down_revision = "074_phase7_correction_pass"`) and Phase 7's own post-merge `075_phase7_reparent_guards` (also `down_revision = "074_phase7_correction_pass"`) forked the migration graph once both existed on the same branch. **Fixed**: the file was renamed to `076_relationships_and_orgs.py` and re-targeted — `revision = "076_relationships_and_orgs"`, `down_revision = "075_phase7_reparent_guards"` — making Phase 8 sequential after Phase 7's correction rather than a sibling of it. No merge revision; `alembic heads` reports exactly one head. Every `075_relationships_and_orgs`/`revision 075` reference in the migration's own docstring/comments, `src/dnd_ai/persistence/tables/*.py` comments, the test module docstring, and `docs/architecture/DATABASE_MODEL.md` was updated to `076`. The AWS `dev` database was not stamped at the obsolete `075_relationships_and_orgs` revision at the time of this fix (it was at `075_phase7_reparent_guards`, from Phase 7's own already-verified-and-merged correction pass), so no destructive downgrade of shared dev state was needed — only the file rename/re-target.
2. **`narrative.enforce_event_effect_target_world()`/`interaction.enforce_consequence_world()` were not extended when the migration added `target_relationship_id`/`resulting_relationship_state_id`** — the same class of gap Phase 7's own correction pass (revision 074) had already found and closed once for the quest-objective columns, repeated here for the relationship columns. Both columns accepted a cross-world/cross-timeline reference silently. **Fixed**: both functions `CREATE OR REPLACE`d to add the missing branch (world check via `world.relationships.world_id`; timeline check via `campaign.relationship_state.timeline_id`), preserving every branch revision 074 already added (the quest-objective checks are not lost). The migration's `downgrade()` restores both functions to their exact revision-074 bodies (quest-objective branch present, no relationship branch), not merely the original revision-057/061 bodies, so a downgrade leaves the database in the same state Phase 7's correction pass left it in. **Tests:** `tests/database/test_relationships_and_organizations.py`, 2 new cases (`test_an_event_effects_relationship_target_must_share_its_world`, `test_a_consequences_relationship_state_must_share_its_timeline`) — the positive cases already existed from the original draft, only the negative cross-world/cross-timeline cases were missing.
3. **No guard against reparenting Phase 8's own parent-scope identity columns** — the same class of gap Phase 7's reparent-guards correction pass closed for the quest/knowledge domain, present here from the start since Phase 8 was drafted before that precedent existed. `world.relationships.world_id` could change after participants/perspectives/state referenced it; `campaign.relationship_state.timeline_id` could change after `interaction.consequences` referenced it; and `world.relationship_participants` rows could be deleted or reparented (a different `entity_id`) out from under an existing `world.relationship_perspectives` row or holder-scoped `campaign.relationship_state` row, silently invalidating the "holder must be a participant" invariant both of those tables' own insert-time triggers enforce. **Fixed**: `world.relationships.world_id` and `campaign.relationship_state.timeline_id` reuse revision 030's `core.enforce_immutable_columns()` (the same mechanism Phase 7's reparent-guards pass used). `world.relationship_participants` needed a genuine reverse guard rather than blanket immutability — deleting or reassigning a participant is a legitimate operation right up until something depends on it — so a new function, `world.enforce_relationship_participant_removal()`, rejects an UPDATE that changes `(relationship_id, entity_id)` or a DELETE only when no other participant row would still cover that pairing and an existing perspective/holder-scoped state row still depends on it. The guard is skipped entirely once the parent `world.relationships` row no longer exists, so deleting an entire relationship (and letting its `ON DELETE CASCADE` children clean themselves up, in whatever order Postgres happens to process the sibling cascades) is never blocked. **Tests:** `tests/database/test_relationships_and_organizations.py`, 10 new cases — reparent-rejected/legitimate-update-still-works pairs for both immutable columns, a no-dependents-can-still-be-deleted baseline, delete-blocked-by-a-dependent-perspective, delete-blocked-by-a-dependent-state-row, reparent-blocked-by-a-dependent-perspective, a role-only update (no identity change) passing through unaffected, one of two role rows for the same entity being deletable while the other still covers it, and — the case most likely to have been broken by cascade ordering — deleting an entire relationship with a participant, a perspective, and a state row all still attached succeeding cleanly.
4. **`world.employment_relationships` validated employer/employee world agreement but nothing about `effective_from_world_time_id`/`effective_to_world_time_id`**, and carried both an `is_current` boolean and the `effective_to_world_time_id IS NULL` signal with no agreement enforced between them — two current-records patterns (conventions §12.4) where the convention requires choosing one. **Fixed**: `is_current` was dropped; `effective_to_world_time_id IS NULL` is now the table's only currentness signal (documented in the table comment, matching character_builds' revision-028 precedent of removing a redundant flag outright rather than reconciling it). `world.enforce_employment_relationship_world()` was extended with the same validity-window shape `world.enforce_relationship_validity()` already uses for `world.relationships` itself: both world_time columns must belong to the relationship's world, and a new `ck_employment_relationships_end_requires_start` CHECK (mirroring `ck_relationships_ended_requires_started`) rejects an end without a start structurally, before the trigger's own strictly-after ordering check would even run. `world.ownership_relationships` was left untouched — it has no temporal validity columns at all (only an unrelated `is_public` flag), so the original docstring's claim that both tables "use a single is_current/effective_from/effective_to shape" was itself inaccurate; the docstring was corrected to say so. **Tests:** `tests/database/test_relationships_and_organizations.py`, 7 new cases — valid chronology, start/end each rejecting a foreign world, end-without-start, equal endpoints, reversed endpoints, and a direct query proving `effective_to_world_time_id IS NULL` alone distinguishes current from ended rows.

No test-runner, fixture-framework, or CI-mechanism changes were made — every fix above is a production migration/schema change, and every new test exercises a production constraint or trigger directly.

## First-Time Obligations ([§23.1](PLAN.md#231-phase-exit-review))

- **First CTI chain rooted at a non-entity table.** `world.organization_memberships`/`.employment_relationships`/`.ownership_relationships`/`.family_relationships`/`.political_relationships` share their primary key with `world.relationships`, not `core.entities` — the same class-table-inheritance mechanism used everywhere else, applied for the first time to a structural (not entity-rooted) parent. `world.sync_organization_membership_period()`'s world-agreement checks resolve the shared world through `world.relationships.world_id` rather than `core.entities`, since the parent row itself has no entity to look up.
- **First `EXCLUDE USING gist` outside `campaign` schema.** `world.organization_memberships` reuses the exact ADR 0010 interval-overlap pattern `campaign.party_memberships`/`.character_location_history` established (ck_..._open_ended_agrees/lower_bound_finite/period_not_empty CHECKs, a derived `INT8RANGE`, an exclusion constraint), proving the pattern generalizes beyond the tables that originated it.
- **First two-tier organization classification.** `world.organizations.organization_type_id` (a lookup covering all nine domain-model subtypes) and the five CTI leaf tables it optionally sits alongside are deliberately independent — an organization can be fully described by the lookup value alone (guild/criminal_organization/secret_society/other) or additionally specialized into a typed leaf table when one exists. `core.enforce_entity_subtype()` (unmodified — it already worked generically off `core.entity_types` ancestry) enforces which combinations are valid; `tests/database/test_relationships_and_organizations.py::test_a_business_subtype_requires_the_business_entity_type` proves the negative case (a bare 'organization'-typed entity cannot receive a `world.businesses` row).
- **Deferred items coming due:** `interaction.consequences.resulting_relationship_state_id` and `narrative.event_effects.target_relationship_id` — both explicitly documented as "Phase 8's job" by revision 073's own comments (Phase 7). Closed here, extending the at-most-one-target `CHECK` to seven columns, and — closing the correction pass's own gap — the two world/timeline-agreement guard functions that reference them.
- **First cross-phase migration renumbering.** No prior phase had two independently-developed branches claim the same revision number before either merged. The resolution (rename + re-target, no merge revision, re-verify from a from-empty database) is the template for any future recurrence — see item 1 above.

### Bugs found while verifying the original revision 075 draft

Distinguished from schema-design defects per this project's own convention:

- **Six missing FK indexes** (conventions §19.1): `world.relationships.started_world_time_id`/`.ended_world_time_id`, `world.organizations.founded_world_time_id`/`.dissolved_world_time_id`, `world.employment_relationships.effective_from_world_time_id`/`.effective_to_world_time_id`. Caught by `test_every_foreign_key_is_indexed` on first run. Fixed in the migration and the matching Python metadata; reverified.
- **`_organization_subtype()`'s local migration helper did not escape embedded apostrophes when interpolating a table comment into `COMMENT ON TABLE ... IS '{comment}'`.** Two of its callers' comment text (businesses', governments') contain a possessive apostrophe, which would have produced invalid SQL. Caught by code review before running against the database. Fixed by escaping (`comment.replace("'", "''")`) before interpolation.
- **`tests/factories.py`'s `make_organization()` always resolved `core.entities.entity_type_id` to the bare `'organization'` type**, regardless of the `organization_type_code` argument. `core.enforce_entity_subtype()` correctly rejected the resulting mismatch, causing five test failures. Not a schema defect — the database enforced its own invariant correctly; the test factory was wrong. Fixed: `make_organization()` now resolves the entity type to the same code as `organization_type_code` when it names one of the five CTI-leaf subtypes, and to `'organization'` otherwise.
- **Four unrelated `ConnectionTimeout` test failures** during a ~30-minute single pytest session, consistent with this project's own documented experience of transient AWS-RDS connection faults. Not reproduced on rerun; no code changes made for these.

### Bugs found during the deployable-integrity correction pass

- The migration graph fork itself, and the three schema-level gaps it was fixed alongside — see "Deployable-Integrity Correction Pass" above for all four.
- The `interaction.consequences` comment-drift `alembic check` failure described in "Comments and FK indexes" above, caught on the first `alembic check` run after renumbering and fixed immediately.
- The original draft's own docstring claim that `world.employment_relationships`/`.ownership_relationships` "use a single is_current/effective_from/effective_to shape" was inaccurate — `ownership_relationships` has no temporal validity columns at all. Caught while writing item 4's fix (not by a test); corrected in the docstring rather than left standing.
