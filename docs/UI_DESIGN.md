# Persistent World Web Portal UI Design

## 1. Purpose

This document defines the first-class web experience for the persistent tabletop roleplaying world platform. The portal is the primary out-of-session interface for players, GMs, assistant GMs, and observers. FoundryVTT remains the primary in-session tactical client. Discord is deferred until demonstrated demand justifies a later thin-client integration.

This document is the product-level authority for portal behavior, information architecture, authorization boundaries, and screen responsibilities. [`UI_STYLE_GUIDE.md`](UI_STYLE_GUIDE.md) defines the shared visual language, card and detail-page anatomy, responsive presentation, theme-token usage, and component-level presentation standards used to implement this design.

The portal must let an authorized user:

- understand the current campaign quickly;
- browse permitted world and campaign details;
- request summaries or ask questions on demand;
- work with one or more characters;
- see facts, beliefs, rumors, quests, sessions, and relationships from an explicit perspective;
- administer canon, users, roles, access, and import proposals when authorized.

The defining authorization rule is:

> Roles provide defaults, but users and details are many-to-many. A user may relate to many characters, facts, and other resources; each resource may relate to many users through roles, characters, parties, groups, knowledge, or direct grants.

## 2. Product principles

1. **Perspective is always visible in campaign work.** The active campaign, timeline, role, effective time, and optional character perspective appear in the campaign context area. The authenticated global shell remains available without a selected campaign; labels describe context and never grant capabilities.
2. **No hidden-data inference.** Unauthorized resources do not appear in pages, search suggestions, counts, links, relationship edges, identifiers, errors, caches, or AI context.
3. **Filter before synthesis.** The server resolves authorization before sending records to the UI or an AI provider. The system never creates a GM answer and redacts it into a player answer.
4. **Truth and awareness remain distinct.** Canonical truth, belief, rumor, knowledge possession, user visibility, and administrative permission are separately represented.
5. **Roles are not ownership.** Player, GM, and observer roles establish defaults; semantic character relationships and resource grants determine detailed access.
6. **Every important answer is traceable.** Summaries and answers identify perspective, effective time, source records, and rules citations when applicable.
7. **The MVP is useful, not encyclopedic.** Begin with concise collection cards, route-based detail pages, links, and focused GM tools. Interactive maps, graph explorers, and a generalized CMS are later enhancements.
8. **Progressive detail is addressable.** Collection cards summarize authorized records; opening a card navigates to a refreshable, bookmarkable detail route that performs its own current authorization check. A visual “expansion” never depends solely on cached list data.

## 3. Users and roles

| Role template | Primary needs | Default experience |
|---|---|---|
| Campaign owner | Administration and continuity | All campaign configuration plus GM tools |
| GM | Canon, secrets, preparation, approvals | Full authorized canon, hidden state, visibility preview |
| Assistant GM | Delegated preparation or portrayal | Only assigned GM capabilities and resources |
| Player | Character and party play | Associated characters, permitted knowledge, quests, recaps |
| Observer | Curated view | Explicitly published or granted resources only |
| Import reviewer | Campaign-data review | Import proposals and promotion decisions |
| Rules curator | Reference-source management | Rules sources, editions, rights, retrieval status |

A person may hold multiple roles in one campaign and different roles in other campaigns. Authorization checks capabilities, not role-name strings.

## 4. Information architecture

**Status: delivered** (Phase 13 navigation and settings redesign; revision `109_user_portal_preferences` and the portal commits recorded in [PLAN.md §23.6](README.md)). This section and §4.2–§4.7 describe the delivered *single-navigation and settings* design. The authoritative frontend is the React/TypeScript/Vite application under `portal/`.

History: before this redesign the header carried duplicate Home/Campaigns navigation and the theme selector, the campaign sidebar was owned by `CampaignLayout` (so it existed only on campaign routes), `/home` was a global dashboard, and the bootstrap's `selected_campaign_id` was only the first authorized campaign by name, with no persisted preference.

### One authenticated navigation system

The portal has exactly one primary navigation system for authenticated work — a persistent sidebar owned by the authenticated application shell — plus a minimal header.

- **Header** (`PortalHeader`): portal identity/branding, the narrow-screen navigation-drawer control where required, and the User Account/profile control (§4.3). Nothing else: no Home/Campaigns links, no other primary navigation, and no theme selector (theme selection moves to Settings, §4.7). For an authenticated user the brand links to `/home`, which is an authenticated landing resolver (§4.2), never a duplicate dashboard. For a signed-out visitor the brand is plain text.
- **Sidebar** (one `nav` landmark labeled "Main"): rendered by `AuthenticatedAppLayout`, not `CampaignLayout`, on every authenticated route — campaign pages, `/campaigns`, `/settings`, `/account`, `/platform/accounts`, and future authenticated global pages. It never appears on public pages: `/login`, `/activate`, `/reset-password`, `/campaign-invitations/accept` (logged-out onboarding and the authenticated manual fallback alike, since it is a public-layout route), and the public not-found state. An authenticated visitor on a public route keeps the header's brand link and profile menu as the way back.

Rules:

- **One World group.** There is no separate singular "World" item beside the group; the campaign world page is the group's "Campaign world" child. World overview and Timelines are enabled only for a world the server has confirmed (`WorkspaceHierarchyProvider`: only once `GET /worlds/{id}` succeeds for the route's world, or for the authorized route campaign's world — campaign membership alone never enables World navigation, per ADR 0014; the campaign page's own context panel still uses the bootstrap names); otherwise they stay in place, disabled with "Select a world first". Timeline overview is enabled only when a timeline is selected — a timeline route whose ID is in that world's authorized timelines, or the route campaign's timeline, in both cases only if that world response lists it — otherwise it stays disabled with "Select a timeline first". **Timelines is world-scoped:** it opens the collection of every timeline the server returns for the world, never just a campaign's timeline. An unknown route ID adds nothing and is never echoed. Disabled entries are non-links with `aria-disabled="true"`, no `href`, no active styling, and the neutral reason as their description; they keep icon, label, and position in expanded, collapsed, and drawer modes. "New world" follows `global_capabilities`, never a display role: without `world.create` (held only by an active platform administrator or an effective built-in GM, ADR 0018) it stays visible as a disabled non-link. Timeline overview, like the Timelines collection and the timeline trees on the World overview, is a read destination and follows `world.view`, not `world.manage` (§4.8.12): a world Viewer, Reader, Reviewer, Editor and an Owner without system GM can all open it, and only the callers the server offers actions to see management controls. With a selected world whose `world.view` is not known its reason is "Not available for your account", not "Select a timeline first". For a world the server returns as view-only, World overview and Timelines open read-only pages. The group starts open on a `/worlds` or campaign world route.
- **Campaign choices** come only from the current authoritative session bootstrap (`campaigns`). The sidebar never invents, guesses, caches, or carries forward a campaign from a previous bootstrap, from browser storage, or from a stored preference. Selecting a different campaign only navigates to `/app/{campaignId}/home` (Infobox Campaign select or the sidebar list): nothing is selected, cleared, refreshed or reloaded beforehand, so the departure guard (§5.11) decides first and Stay changes nothing. The new campaign starts with its own character-perspective state because the session provider is keyed on the campaign scope (`RouteSessionProvider`); no pre-navigation `selectCharacter(…, null)` exists (CTX-2). **Changing character perspective** is an ordinary departure that starts a new task (§4.8.4, decision PD-6), not a same-page change and not a session reload (CTX-1): the Infobox asks the router for one destination, the chosen character's Characters details (`/app/:c/characters/:id`, or `/characters/all` for none), with a fresh Characters task and the context stamp that destination commits under; it carries nothing of the page left, so no old `character_id`/`party_id` query can turn the accepted change back. Only after the navigation is accepted does `CampaignLayout` commit the selection from the location, remount the page content (keyed on campaign and perspective, never `location.key`, so every perspective-dependent page reads again under the new perspective), and start the existing ticketed background `refresh()` that revalidates `character_perspectives`; the shell, sidebar and Infobox stay mounted and "Loading portal" is never shown. A perspective the refreshed bootstrap no longer lists is cleared at once and without a discard decision, as an **explicit choice of no perspective**: it never falls back to the server default (not even a sole remaining character, and not a different default that the same refresh names), and re-authorization alone never restores it or any other, so a refresh cannot remount away work entered since. **Ownership.** A revocation owns the selection only while that selection still reads none because of it. An accepted location takes ownership in one step: the layout stores the accepted perspective, records it as the committed one and (next) stamps the entry with it, so a revocation of the previous selection that is still outstanding, including one published in the same render as the accepted location, has nothing left to clear; an accepted explicit none is likewise not reported as a loss. A selection that is in place by any other route (an adopted URL character) supersedes the lost one in the same way, and a proposed selection the bootstrap does not authorize never wins. If nothing newer is in place, the revocation still clears to explicit none. The bootstrap's `selected_character_id` only **initializes** the selection: once a perspective is in use, however it was reached, the layout stores it as the selection (idempotently), and a later bootstrap default never replaces it; an uninitialized start still uses the authorized default. The content remounts (old private content is removed without asking to keep it), an address that still names the lost character is cleaned first (`character_id` and `party_id` removed by one replacement of the current entry, other parameters and the record's path kept) so no request is made as the lost character. Permission loss never waits for an answer and is not held by the page it removes: the replacement runs under a narrow exemption in `runPermissionLossCleanup` (only a same-path REPLACE of that exact entry, only for the duration of the call, nothing else), and a navigation question that was open is cancelled by its owner as the page goes away (the blocker's own reset on unmount; the held departure is never approved). A newer navigation takes ownership: the cleanup is dropped and the destination validates its own address. The explicit clear then re-stamps the history entry with no perspective, and a polite status says "Your selected character is no longer available." (no name, since it is no longer readable). Choosing a perspective afterwards is the ordinary guarded selection. The destination page is unchanged. Choosing the already-selected perspective does nothing. **View all campaigns** always links to `/campaigns`, the full campaign-selection route (§5.2).
- **Campaign, World and Characters are split controls** (P02-4, §4.8.3), never one control that is ambiguously both a link and a toggle: a main control and a separate disclosure button, siblings and never nested. The main control is a link to the selected context's default details where that is a destination worth going to, and otherwise a button that toggles the menu (rule table in §4.8.3). The disclosure ("Show campaign menu", "Show world menu", "Show characters menu"; `aria-expanded`, `aria-controls`) always toggles, so expanding the menu is directly usable in every state. The Campaign menu lists the selected campaign's Home (a disabled "Campaign Home" entry when none resolves, see "Stable structure"), every authorized campaign, and View all campaigns. It starts open on `/campaigns` and closed elsewhere. The active campaign's entry carries `aria-current="true"`.
- **Resolved campaign for campaign-specific links** (`resolveNavigationCampaign`), by precedence: (1) the route's `:campaignId` when it is in the current bootstrap's `campaigns` — a route that names a campaign the bootstrap does not contain resolves nothing (no saved campaign stands in for it); (2) when the route names a world instead (`/worlds/{id}/...`), the **selected campaign** (the explicit selection this tab retains, §4.8.2), and only when it belongs to that confirmed world — and to the named timeline, when the route names one; otherwise nothing resolves. An explicit destination that is not confirmed resolves nothing and is never replaced by a retained campaign: a world still loading, unknown, denied, or failing its read, or a timeline that is unknown or not among the world's authorized timelines, leaves the campaign-specific entries disabled; (3) otherwise (the route names no campaign and no world: `/campaigns`, `/settings`, `/worlds`, `/worlds/new`) the selected campaign if the bootstrap still lists it; otherwise none. **There is no fallback to `last_visited_campaign_id`, `startup_campaign_id` or a world's only campaign (PD-2, P02-3):** those remain inputs of the `/home` landing only (§4.2), which enters a campaign, which then becomes the selection. The route always wins over the selection, so the sidebar and the hierarchy panel always describe the same context. A route campaign ID that is not authorized is never used or echoed. With no resolved campaign (including a person who has not selected one yet), the Campaign and Characters main controls are buttons, the menu entries that need a campaign (Campaign Home, Campaign world, Selected character, All characters) and Quests/Sessions/Knowledge/Ask/Access are not rendered as links — they remain in place as disabled entries (see "Stable structure") — so no link ever contains a guessed ID.
- **Stable structure.** Route context never adds, removes, or reorders sidebar entries; a missing prerequisite switches an entry to disabled instead. A disabled entry is never an anchor: it is a non-focusable element with the normal icon and label, `aria-disabled="true"`, no `aria-current`, muted styling, no navigation, and the prerequisite as its accessible description (`aria-describedby`) and tooltip (collapsed tooltips are "Label: reason"). Reasons are neutral — "Select a campaign first", "Select a world first", "No timeline available", "Not available for your account", "Unavailable for this campaign", or the server-provided feature reason for Ask — and never carry a name, ID, capability, or count. Capability-gated slots follow the caller, not the route: "New world" follows `global_capabilities`; the Access slot exists only for a caller with `access.manage` on at least one authorized campaign, and is enabled only when the resolved campaign grants it. The Knowledge slot is a plain link, except that it becomes an expandable group with **Claims** and **Member preview** children when the resolved campaign grants `access.manage`; Claims stays active on the collection and on claim pages, Member preview on its own routes, and the group opens on load when either is current. The sidebar presents server-computed state and never grants access; the server remains the enforcement boundary.
- **Ask** follows the server feature manifest exactly as before: a link only when `features.ask` is true, otherwise a visibly disabled item that is not a link and makes no request.
- **Access** is a disclosure button (not a link) over **Access Management** (`/access`), **Invitations** (`/access/invitations`), and **Audit History** (`/access/audit`). The group is shown only when the resolved campaign's server-supplied `capabilities` include `access.manage` — the capability each of those routes' APIs already requires — and is never shown with no visible child. Hiding it is presentation only; each route and API re-authorizes. The Access page's own tab strip remains as page-local navigation.
- **Items** is a disclosure button (not a link) over **Inventory** (`/items`, which also holds an item's workspace and its edit form) and **Definitions** (`/item-definitions` and its forms), built on the same expandable group as Knowledge and Access. It is shown only on a campaign whose `capabilities` include `canon.edit` (the capability both areas' APIs require) and is otherwise absent; with no resolved campaign it is the usual disabled entry. There is no separate top-level Item definitions link. **The selection follows the address alone:** an item opened from the World page lies under the Worlds group (**Campaign world**), never under Items, and router state never selects a destination.
- **Collapse/expand** stays the last item. Collapsed, the sidebar is an icon rail: every item keeps an accessible name (visible label hidden, `title` shown), each split control (Campaign, World, Characters) keeps both of its controls as two stacked icon controls (the main control with its `title`, and the disclosure with its chevron), and the disclosure opens the menu as a bounded flyout; activating the Access, Knowledge or Items button in the rail opens its children the same way, with their labels shown, so they stay keyboard-reachable. The collapsed/expanded choice is a per-viewer convenience persisted in browser storage (never authentication data), so it survives the scope-keyed remount.
- **Loading and refresh:** every campaign-scope change remounts the session provider and refetches the bootstrap (§4.5). During that loading state the shell keeps the header, the sidebar frame, the collapse/expand control, the drawer control, and the static **View all campaigns** destination; bootstrap-derived entries are replaced by a busy placeholder until the fresh bootstrap arrives. The previous scope's campaign list is never shown in the meantime. A session-check error keeps the same frame with no bootstrap-derived entries. Authentication expiry removes the authenticated shell and follows §4.2.

Landmarks: the header `banner`, the sidebar `nav` ("Main"), and page-local navigation such as the Access tab strip ("Access"). There is no global Home page; Campaign Home (`/app/:campaignId/home`) is the only Home. Role and perspective labels are contextual display data, never locally derived authorization. Changing perspective obtains fresh server-authorized data rather than filtering previously downloaded records.

`AuthenticatedSessionBoundary` remains the single authenticated session gate. `CampaignSessionBoundary`/`CampaignLayout` own campaign-specific context and authorization — the authorized-campaign lookup, perspective wiring, the campaign-not-found state, and the last-visited update (§4.7) — but no longer own navigation. `WorkspaceHierarchyProvider` (mounted in `AuthenticatedAppLayout`, shared by the sidebar and the context panel) derives the route's world and timeline from the route and confirms them against server data; it stores nothing. The person's explicit selection is held by a separate `SelectedContextProvider` mounted in `main.tsx` **above** `RouteSessionProvider`, so the scope-keyed remount does not lose it (§4.8.2).

### 4.1 Reusable presentation system

A small set of reusable `portal/src/components` primitives supports the screens below rather than each screen inventing its own layout. The exact component names may evolve, but their responsibilities remain separate:

- **`HierarchyContextPanel`** answers "where am I in World → Timeline → Campaign → Character, and which perspective am I using?" It is one compact, infobox-styled panel with four labelled sections — **World, Timeline, Campaign, Character**, in that order — rendered by `WorkspaceFrame` on every World and Campaign workspace page (`/worlds/*` through `WorldWorkspaceLayout`, `/app/:campaignId/*` through `CampaignLayout`), so it persists across All Worlds, World Overview, the Timelines collection, Timeline Overview, and Campaign pages. What a page reads is route-derived and the panel never stores anything; a campaign page always shows its own route campaign, and a World or Timeline page may additionally show the campaign this tab retained, labeled **Selected campaign**, only while it belongs to the confirmed world and timeline (§4.8.2). Per page: All Worlds selects nothing; World Overview and the Timelines collection select the world; Timeline Overview selects world and timeline; a campaign page selects world, timeline, and campaign, with an optional authorized character perspective. Each level is a labelled `<select>` whose options come only from authoritative data — the same deduplicated world choices All Worlds shows (`GET /worlds` merged with the bootstrap campaigns' worlds by `buildWorldChoices`, [ADR 0019](adr/0019-world-visibility-and-viewer-role.md); the list is identical on every page, and choosing a campaign-visible world opens that campaign's World Explorer), the selected world's timelines (`GET /worlds/{id}`), and the session's authorized campaigns for that world and timeline. A level with no actionable destination stays visible and disabled (`disabled` is exposed to assistive technology) with a visible reason it is described by; the empty "No selection" placeholder is never a choice. The options are built by one pure model (`navigation/contextOptions.ts`, §4.8.12): the Timeline level follows `world.view` and, for a caller without it, offers the timelines of their authorized campaigns (CN-1, with an inline campaign chooser where several campaigns share a timeline); every level follows the meaningful-choice rule with visible reasons and read-only retries (CN-2); explicit World entries are reconciled against newer world reads by when each read started. Choosing an option is an ordinary departure that starts a new task (§4.8.4: the existing guard decides first, nothing is committed ahead of the accepted navigation, and choosing a character perspective opens that character's Characters details), so lower levels clear because their routes unmount: changing the world clears timeline, campaign, and character; changing the timeline clears campaign and character; changing the campaign makes the new route campaign the selected campaign and uses only that campaign's server-authorized default (the previous campaign's perspective is replaced when the route's campaign is adopted, §4.8.2). While a newly chosen world is unconfirmed the panel shows no selection and no previous options. **Character perspectives are Campaign-membership and relationship scoped** — they come from the route campaign's bootstrap entry, never from World-scoped characters, and are not selectable outside a campaign. **Party memberships.** With a character selected, a native collapsed **Parties (N)** disclosure sits directly beneath the selector (nothing is shown without a character, as for the other character details). It lists, in a stable case-insensitive name order, every party the character currently belongs to in this campaign and timeline, from `GET /campaigns/{id}/characters/{character_id}/parties`: the complete membership (never paged), by the same rule as the bootstrap's `authorized_parties` and `resolve_party_perspective` (current membership, party attached to the campaign), with archived parties shown only to people who can edit canon. The request is made only for a character the caller holds `character.view_knowledge` for, in the campaign's own world; any other character, a revoked relationship, a denied character or a campaign the caller is not in is the same fixed not-found, which the panel shows as "Parties unavailable." with no count, name or identifier. Loading ("Loading parties…"), a failed load (with *Try again*), a loaded empty list ("Parties (0)" with "No party memberships.") and an unset campaign clock (no count and no empty message: "Party membership cannot be determined because the campaign time has not been set", with a Campaign Home link only for `canon.edit`) are distinct, the count is exactly the list shown, and the list is requested per campaign and character, so one character's parties never appear under another's and each character's disclosure starts collapsed. A party name is a link to the existing party page only when the server says the caller may open it (`can_open`, today editors); otherwise it is plain text. It is an affiliation list only: expanding it or opening a party never changes the Knowledge filters, the selected party or what any character knows. A route world or timeline the server does not authorize selects nothing and its ID is never rendered. It collapses behind a native disclosure control on narrow screens and sits in the right-hand column from 64rem.
- **`InfoBox`** answers "what are the important facts about the entity on this page?" It is a generic, Wiki-style label/value panel (title, optional subtitle/image/status, label/value sections, related links) with no built-in knowledge of any entity type; per-entity wrappers (e.g. `CampaignInfoBox`) translate an authorized domain record into the generic model and are responsible for authorization-safe field selection.
- **Collection-card primitives** answer "which authorized record should I open?" A responsive card grid presents concise, domain-mapped cards for world entities, knowledge, quests, campaigns, and other browsable collections. Cards use real links, expose only fields present in the audience-safe list contract, and do not fetch or imply inaccessible detail records.
- **Detail-panel primitives** answer "how is this authorized record organized?" A full-page detail layout composes stat cards, semantic fact groups, compact lists or tables, and bounded panels under one page heading. Domain-specific wrappers decide which authorized fields belong in each panel; a generic primitive never reflects over an arbitrary API object.

These concepts stay distinct: context describes the viewer's current vantage point; an infobox describes compact facts about a subject; a collection card supports discovery and navigation; and a detail surface organizes the complete authorized view. `InfoBox` remains available for compact subject summaries and the context panel retains its specialized structure. None infers access, filters hidden records, reflects over arbitrary fields, or exposes internal identifiers or authorization metadata — that remains the server's responsibility.

Activating a navigable card changes route and loads the detail contract for that campaign and perspective. The detail page may visually continue the selected card's category, title, status, and surface treatment so that it feels expanded, but correctness, deep linking, refresh, browser Back/Forward behavior, and authorization do not depend on animation.

### 4.2 Root, authentication, landing, and deep links

- `/` uses replacement navigation to `/login`. With a valid session, the login boundary replaces `/login` with the post-login destination below.
- **`/home` is an authenticated landing resolver, not a content page.** It renders no dashboard; once the bootstrap is authenticated it replaces itself (`<Navigate replace>`) with the landing destination, so Back never returns to `/home`. It stays a valid route for old bookmarks, the brand link, and the ordinary login default.
- **Post-login landing precedence**, evaluated after sign-in or on an authenticated visit to `/login`:
  1. An explicit security/onboarding continuation wins. A live campaign-invitation onboarding continuation keeps its existing explicit **Resume invitation** / **Continue** choice on the login page ([PHASE13E_ACCESS_CONTRACT.md §3n](api/ACCESS_CONTROL.md#3n-single-link-invitation-onboarding-delivered-checkpoints-8a-8d)); a validated protected-route return path (below) is the other explicit continuation. **Continue**, and every login without a continuation, goes to `/home`.
  2. `/home` then resolves: no authorized campaigns → `/campaigns`.
  3. Exactly one authorized campaign → its Campaign Home.
  4. Startup mode **Always open this campaign** with the preferred campaign still authorized → its Campaign Home.
  5. Otherwise, the last-visited campaign if still authorized → its Campaign Home.
  6. Otherwise → `/campaigns`.

  Steps 2–6 are computed by the server into the bootstrap's `startup_campaign_id` (§4.7) so the rule lives in one place; the client navigates to `/app/{startup_campaign_id}/home` when that ID is in the current `campaigns` list, and to `/campaigns` otherwise. The client never picks the first or alphabetically first campaign when several exist and no valid preference resolves. A stored campaign that is inaccessible, revoked, ended, archived, or deleted is never disclosed or navigated to.
- Successful logout revokes the server session, clears protected client context, and routes to `/login` with no continuation state. A failed logout shows a safe recoverable error and retry; it must not claim sign-out succeeded.
- **Delivered.** Known protected deep links without a valid session route to login using replacement navigation, carrying the intended destination in router history state (never the URL). `AuthenticatedSessionBoundary` sets `state={{from: pathname+search}}` (the hash is never carried); `LoginPage` resolves it through `utils/postLoginDestination.ts`'s same-origin, allowlisted-path check before navigating, and rejects anything else (including `/login` itself and other public routes) back to `/home`. `/settings` is on that allowlist. The destination still fully reauthorizes on arrival — this allowlist is a UX convenience, not a security boundary.
- `/campaign-invitations/accept` retains its public single-link onboarding and authenticated manual-token fallback. Inline sign-in/registration and the server-side onboarding session continue under [PHASE13E_ACCESS_CONTRACT.md §3n](api/ACCESS_CONTROL.md#3n-single-link-invitation-onboarding-delivered-checkpoints-8a-8d); the ordinary landing rule must not interrupt invitation completion, and its completion link to `/campaigns` is unchanged. Do not retain invitation secrets in a return path.
- Unknown routes display a proper not-found state, including unknown campaign sections; do not turn a wildcard into a login redirect. A known protected route still checks its session and authorization. Missing and unauthorized resources remain indistinguishable.

### 4.3 Profile (User Account) menu

One profile button in the header. Display the user's server-provided display name where space allows and initials in the avatar position by default. The fallback order is a future configured profile image, initials, the first usable account identifier already authorized for this viewer, then a generic account icon. Initials remain the default without a configured image. The current bootstrap supplies `user.display_name` and an opaque `user_id`, not a profile image or displayable login identifier; never show the UUID or fetch another account's identifier to fill an avatar. The generic icon covers an unusable display name until an authorized identifier is available.

Menu order:

1. Identity summary for the signed-in user.
2. **Settings** linking to `/settings` (§4.7).
3. **Account & Security** linking to `/account` — the existing self-service password-change and own-session page, renamed in the menu only.
4. **Platform Accounts** linking to `/platform/accounts`, only when the bootstrap's `global_capabilities` contains `accounts.manage` (§4.4), kept under its **Administration** group label; omit the group otherwise.
5. **Log out**, separated from navigation as an action.

Outside-click and focus leaving the menu close it; dismissal must not steal focus from an outside control the user activated. Close on navigation or logout. Hidden menu content is absent from keyboard and screen-reader navigation. Every action remains usable by keyboard and touch, with visible focus and no hover-only controls.

### 4.3a Scoped roles in the portal ([ADR 0020](adr/0020-scoped-system-world-and-campaign-roles.md))

Every gate reads server data (`global_capabilities`, a campaign's `world_capabilities`, a world's own `capabilities`) and never a role label.

- **Accounts with no campaigns** (`/campaigns`): a game master (`world.create`/`campaign.host`) sees "You are not in any campaigns yet." with **Create a world**, **Create campaign** and **Accept a campaign invitation**; anyone else sees "Ask a GM to invite you" and **Accept a campaign invitation**. An Administrator who is not a GM is offered neither creation link. The sidebar keeps its stable structure; campaign entries stay disabled with "Select a campaign first".
- **Worlds list:** each world shows the caller's roles ("Owner", "Editor · Reviewer", "Reader", "Can host campaigns").
- **World overview:** an Owner with the game master role sees the full overview plus **Sharing** and **Published canon**. Every other role (and an Owner whose system GM was revoked, with an explanation) sees the limited overview: their role, and only the links their capabilities allow (**Published canon**, **New timeline** for an Editor, **Host a campaign here** for a use-grant holder).
- **Sharing** (`/worlds/:worldId/sharing`, `world.share`): role holders and use grants with add, end and revoke, and ownership transfer (`world.transfer`) behind confirmation dialogs whose focus returns to the trigger. Non-Owners get a disabled sidebar entry, not a link.
- **Published canon** (`/worlds/:worldId/canon`, `world.canon.read`): the World Reader surface. Published definitions as cards; no drafts, GM-only fields, revisions, provenance or campaign data.
- **Campaign setup** (`/campaigns/new`): the world picker lists only worlds with `campaign.create`; the timeline step lists only the timelines the server marks eligible and explains the others ("already hosts a campaign. Ask a world owner or editor to branch a timeline for you.").
- **Authoring screens:** when the campaign's `world_capabilities` lack `world.canon.edit`, the create screens and the world page's creation links show "Editing shared world content requires the world Editor role. Ask the world owner." instead. World-time points, item instances and player-character identity are unaffected.
- **Per-record eligibility** (integration, CP-4c). A record's own read (the World Explorer location, religion, organization and item details, the character, knowledge and quest details, and the lifecycle read) carries `authoring: {campaign_originated, can_read_private, can_edit, can_review}`, resolved by the server with the resolver the commands use. The Edit link, the character Manage links, the lifecycle panel and the workspaces read these fields and nothing else; the portal never infers eligibility from a role name or a category. The lifecycle read offers only the actions the caller holds (submit, return to draft and delete a draft are editing; approve, reject, publish, supersede, archive and restore are reviewing; a Reviewer is never offered Edit and an Editor is never offered Approve). A response with no `authoring` grants nothing. The authoring option catalogs report `can_create` for the world Editor only.
- **Workspaces keep their structure** (World record, Knowledge claim, Quest, item). A campaign GM with no world role gets the published record, its GM-only fields, and the campaign's own operations (organization status, running an NPC, who knows a claim, quest progress, item instances, a player character's identity and lifecycle). The preparation, review and publication sections are listed as unavailable text with the reason, never as links, and their content is never mounted or requested: no lifecycle, provenance, revision, source or authoring read is sent, so a denied preparation section cannot blank an otherwise permitted record. An address that names an unavailable section falls back to the first usable one. A quest for a GM without a world role shows the published quest and its progress panel instead of the workspace. A player character's own lifecycle follows the campaign; its sources and relationships are shared world canon and follow the world. **Area now** (a dungeon area's runtime panel) is the campaign's: it reads `GET /campaigns/{id}/dungeon-areas/{area_id}/runtime`, a projection of only what recording state needs (the dungeon's name, the area's recorded state, the parts and connections with their recorded statuses and last-event tokens, the status choices and limits, and whether state may be recorded), authorized like the audience-safe area read (campaign `canon.edit`; an unpublished area or dungeon, a per-area `campaign.view` deny and a foreign campaign are the same 404 for a caller without the private-read capability; a connection to an area the caller cannot see is not listed). It returns none of the authoring read's descriptions, hidden flags, severities, dimensions, revisions or actions, and it grants no edit; recording state is its own command with its own authorization. The panel makes no private-authoring request; a failed optional read leaves the rest of the record usable with a read-only retry, and an unavailable answer says so. Contents (the area's structure) still reads the authoring view and needs the world's private side.
- **Losing permission while editing.** A save refused with `world_authority_required` (or a record that has become unavailable) stops all further writes, drops the form and everything the server's private read had filled it with, and shows back, read-only, only what the person changed (the fields that differ from what they were given, and the change note) so they can copy it. A plain 403 is not treated as loss: it is also what a stale CSRF token answers, and keeps the form with the session check. A network or server failure keeps the draft and its version as before.

### 4.4 Platform Accounts authorization

Platform Accounts is global platform administration, independent of campaign selection or campaign administration. Visibility derives exclusively from authoritative server-provided platform permission, such as an `accounts.manage` capability. Never infer it from GM, campaign owner, system-role labels, campaign roles, or campaign `access.manage`.

**Delivered contract ([ADR 0020](adr/0020-scoped-system-world-and-campaign-roles.md)):** the bootstrap carries the server-computed `global_capabilities` (`accounts.manage`, `system_roles.manage`, `system_roles.grant_admin` while the deployment enables the in-app Administrator grant, `world.create`, `campaign.host`, `world.administer`) and a display-only `system_roles` list; `is_platform_administrator` is gone. The menu item and the `/platform/accounts` route adapter gate on `accounts.manage` only. The page lists each account's system roles, offers a System roles editor (GM, Player and Observer checkboxes; the Administrator checkbox is disabled with "Granting Administrator is done by the operator script on this deployment" unless `system_roles.grant_admin` is present), a create-account form with the same role choice (default Player), and a notice on an account that owns worlds no one can currently manage.

Hiding a menu item is presentation only. The direct page route must enforce platform eligibility, and every list/mutation request must independently enforce backend authorization. Preserve the fixed non-disclosing not-found/unavailable behavior for unauthorized callers (currently server 404), without leaking account names, counts, identifiers, or diagnostics. **Delivered:** `/platform/accounts` is the browser route (its route adapter itself is the gate, so a non-administrator never mounts the page and triggers no list request), with `/admin/accounts` kept only as a redirect for existing bookmarks. The backend account APIs are unchanged and still live at `/api/admin/accounts*`.

### 4.5 Campaign discovery and switching

The full `/campaigns` page provides complete authorized campaign browsing and selection with the fuller audience-safe information available for each campaign (§5.2). The sidebar's Campaign Home campaign list is the quick switcher during campaign work and always ends with **View all campaigns** (`/campaigns`); the sidebar is present on every authenticated route, so it is never the only way out of a selected campaign. The former campaign-only context panel's switcher and its **Browse all campaigns** link are retired (§4); the hierarchy panel's Campaign selector lists only the authorized campaigns of the selected timeline.

Preserve these authoritative behaviors:

- Choices come only from authorized bootstrap/session data, never guessed IDs, stored preferences, or locally filtered role lists.
- Revalidate campaign authorization through fresh bootstrap and server checks when campaign scope changes, including browser Back/Forward. A missing, revoked, or unauthorized campaign is not disclosed.
- Reset or refresh campaign-scoped timeline, provider, perspective, character, party, detail, and preview context according to existing contracts. Do not carry one campaign's data under another campaign's URL. `RouteSessionProvider` remounts `SessionProvider` (and the application subtree beneath it) when its campaign route scope changes. The retained selection lives above that remount (§4.8.2), but it never crosses campaigns: arriving on a campaign route replaces any retained selection of another campaign before a page reads under it, so the target campaign starts at its own server default. Shell persistence must preserve those security behaviors: the sidebar's persistent state is limited to its collapsed/expanded presentation.
- **Delivered.** Switching always enters `/app/:campaignId/home`; section/detail preservation is not offered.
- Roles remain display information, not locally derived capabilities.

### 4.7 Settings and campaign startup preferences

**Status: delivered** (revision `109_user_portal_preferences`).

`/settings` is an authenticated global page (sidebar present, no campaign required) with one `h1` ("Settings") and these sections:

- **Appearance** — the existing theme selector, moved out of the header unchanged: the same supported themes (`System` plus the light and dark options in `portal/src/themes/themes.ts`) and the same behavior. The preference stays **client-side** in `localStorage` (`dnd-ai-theme`), applied by `ThemeProvider` before authentication/bootstrap completes so there is no flash of the wrong theme, and therefore it also applies on public pages and is per browser rather than per account. Nothing authentication-related (session, CSRF token, bootstrap) is ever stored alongside it.
- **Campaign startup** — a radio group:
  - **Resume my last visited campaign**
  - **Always open this campaign:** [selector of currently authorized campaigns from the bootstrap]

  Saving sends one explicit mutation (below); the selector is required when the second option is chosen. Only campaigns in the current bootstrap's `campaigns` list are offered. With zero campaigns the section explains that no campaigns are available yet and links to `/campaigns`; the radio group is not shown. With exactly one campaign the page notes that it always opens that campaign (step 3 of §4.2) while still allowing the preference to be saved. Save is an explicit button and shows pending, success (polite status), and safe retryable error states. A non-disclosing 404 for an unavailable campaign tells the user the campaign is no longer available and drops it from the selector without reloading the bootstrap (a reload would unmount the page and lose the explanation); a 401/403 says nothing was saved and offers **Check my session**, which re-fetches the bootstrap so an expired session redirects to sign-in and a stale CSRF token is replaced. The save never assumes authorization optimistically: after the PUT succeeds the portal re-fetches `GET /auth/session` and replaces the shared bootstrap in place (`useSessionBootstrap().refresh`, which does not pass through the loading state, so the page and its polite success status stay mounted). Success is reported only once that authoritative bootstrap is applied and the form shows the server's saved value; if the re-fetch fails, or is not applied because a newer session read decided first or the session ended, the user sees "Your preference was saved, but the latest settings could not be confirmed" with **Check my session**: the PUT was confirmed, so it is never reported as refused or as "nothing was saved" (only a rejected PUT is), the user's newer draft is kept, the PUT is never repeated to repair the read, and nothing local is treated as the saved value; a session that really ended removes the signed-in UI through the sign-in boundary. Because the shared bootstrap is fresh, `/home` and a remounted Settings page in the same session use the saved preference immediately.

**Persisted, user-scoped preferences.** Startup mode, preferred campaign, and last-visited campaign belong to the platform user, not to a browser or browser session, and are stored server-side in one row per user (`security.user_portal_preferences`, [DATABASE_MODEL.md §19.1](architecture/DATABASE_MODEL.md#191-identity-and-login)). Startup mode is not a separate column: a non-null preferred campaign means **Always open this campaign**; null means **Resume my last visited campaign**.

Authorization boundaries:

- Stored campaign IDs never grant access, are never copied into authorization decisions, and are never returned unless the campaign is currently in the user's authorized bootstrap campaign set (an active membership in an active campaign that currently carries `campaign.view` through an unrevoked, unexpired, active role — resolved through the same path as `campaigns`; a membership without it is never listed, selected, or accepted as a preference, [ADR 0019](adr/0019-world-visibility-and-viewer-role.md)). An unauthorized stored ID is ignored silently: no error, no name, no hint that it exists. If access is later restored, the stored preference applies again.
- The preference row stores only the user and the two campaign IDs plus timestamps — never roles, capabilities, memberships, or other authorization state.
- Writes re-verify that the campaign is currently authorized for the caller (non-disclosing 404 otherwise) and require the existing cookie-session `X-CSRF-Token` and allowed-`Origin` protections. They are idempotent set operations, so they take no `Idempotency-Key`. Preference changes are presentation state, not canon, typed campaign state, or permission changes ([DATABASE_CONVENTIONS.md §24.1](DATABASE_CONVENTIONS.md#241-what-to-audit)), so they write neither `audit.change_log` rows nor security-audit events.
- `GET /auth/session` never writes. **Last visited** is updated by an explicit client mutation sent only after `CampaignLayout` has confirmed the route campaign against the fresh bootstrap for that scope, at most once per campaign-scope entry and only when it differs from the bootstrap's current value; the server re-verifies authorization before writing. A failed or rejected last-visited write is silent and never blocks the page. The write is never aborted when the page is left, writes run one at a time in the order issued (`api/preferenceWrites.ts`), and `fetchSessionBootstrap` waits for the writes already issued before reading, so the bootstrap that follows a campaign switch cannot report the previous campaign as last visited.

**Bootstrap contract.** `GET /auth/session` replaces `selected_campaign_id` (whose "first authorized campaign" fallback is retired, not redefined) with:

- `startup_campaign_id: UUID | null` — the server-resolved result of §4.2 steps 2–6; always either null or an ID present in `campaigns`.
- `campaign_preferences: { startup_mode: "resume_last_visited" | "preferred_campaign", preferred_campaign_id: UUID | null, last_visited_campaign_id: UUID | null }` — each ID only when currently authorized; `startup_mode` reports the *effective* mode (`preferred_campaign` only when the preferred campaign is authorized).

Write API: `PUT /auth/preferences/campaign-startup` with `{ "preferred_campaign_id": UUID | null }`, and `PUT /auth/preferences/last-visited-campaign` with `{ "campaign_id": UUID }`; both return `204`; `401` without a valid session, `403` for a failed CSRF/`Origin` check or a delegated (Foundry) principal, a fixed non-disclosing `404` for an unknown or currently unauthorized campaign (identical for both), and `422` for a malformed body. Both are `PUT` set operations on the caller's own row and each writes only its own column, so recording a last-visited campaign never clobbers the startup choice.

Accepted limitations: last-visited writes from multiple tabs or rapid successive switches are last-writer-wins; the theme is per browser, not per account; `/home` costs one extra bootstrap request before landing; the sidebar shows a busy placeholder (never stale campaigns) during each campaign-scope bootstrap refresh.

| Layer | Question | Source today |
|---|---|---|
| **Execution scope** | Whose data does this route read and write? | Derived from the route's params (`campaignId` or `worldId`) and its route metadata (scope kind), validated by the bootstrap or the world read as before. None of them grants authority: every read and command is re-authorized by the server, a denied read fails closed, and a trail entry is never an access hint. They hold ids, route ids and whitelisted `?query` strings only; never labels, free text, drafts, URLs, capabilities, authorization outcomes or receipts, and nothing is written to browser storage or a URL.

- **Entry context stamp.** `state.ctx` is `{ v: 1, campaignId, worldId, timelineId, characterId }` (each an id or `null`). The campaign layout stamps every accepted campaign entry with all four levels. On a campaign route a versioned stamp that names another campaign, world or timeline than the route's is also "no stamp" (the owner commits `routeScoped`), for the layout and the guard alike. Unrelated router state (`task`, return keys) is carried beside the stamp, never replaced.
- **Route metadata.** One entry per production route pattern (91), with its scope, default and allowed task roots, kind, static label, viewed record and default parent. A test builds the production pattern list from `App.tsx` and fails if either side drifts.
- **Task resolution.** A valid `state.task` for the route's scope and an allowed root is used; otherwise a legacy key (`charactersReturn`, `reviewSearch`, `itemsSearch`, `definitionsSearch`, `worldSearch`, `returnTo`) is adapted by its existing validator; otherwise the route's default root and default ancestors. A trail holds at most 4 route references, and a longer one is treated as tampered. Every trail entry and the list state must also fit the destination: the route must allow the task's root (`allowedRoots`), and a persisted list is accepted only with the keys and values that list route actually produces (`navigation/listState.ts`; perspective and scope keys and return URLs are never list state). An invalid descriptor is rejected, not trimmed, in history and in the legacy adapters alike. Browse cursors are opaque, structurally checked only (the backend's unpadded Base64url alphabet `[A-Za-z0-9_-]` and its 2048-character bound; the backend's decoder stays authoritative), and the page trail is kept without a per-key cap. The only size policy is a finite resource bound on the whole persisted query, 524,288 UTF-16 code units (JavaScript `string.length`); over it the return falls back to the route default rather than being truncated, so browse position is preserved up to that bound and not beyond.

#### 4.8.2 Selected-context ownership (P02-3)

The core invariant: **on a campaign route, the route campaign governs execution and the displayed campaign context. A retained selection of another campaign never appears to govern that page and never causes a read under a mismatched scope.**

- **Ownership.** `SelectedContextProvider` (`main.tsx`, above `RouteSessionProvider`) owns one in-memory `SelectedContextStore`: `{ owner, campaignId, worldId, timelineId, characterId }`, ids only. `owner` is the signed-in user and browser session that made the choice; a different owner reads as an empty selection. `characterId` is `undefined` until a perspective is chosen or initialized (the campaign's server default then applies), `null` for an explicit choice of no perspective, or an id. The store is never written to `localStorage`, `sessionStorage` or a URL, and grants nothing: every consumer validates it against the current bootstrap, and every read is authorized by the server. A tree rendered without the provider gets a private store (isolated tests), so nothing leaks between such trees.
- **Execution scope, selection and viewed record stay separate.** Pages read the route's `campaignId` and never the store. `getSelectedCharacterId(campaignId)` returns a perspective only for the campaign it was chosen under, only for the owner that chose it, and only while the bootstrap still authorizes it. Opening a record never selects it.
- **Adoption (route wins).** When the campaign layout has a route campaign that is in the bootstrap it adopts that campaign into the store (`adoptRouteCampaign`) before the page content commits: a retained selection of another campaign, including its perspective, is replaced; the same campaign's own choice, including an explicit none, is kept; a campaign with no perspective chosen yet stays uninitialized so its server default initializes it, and an initialized default is stored so a later bootstrap that names a different default cannot replace it. A route campaign that is not in the bootstrap adopts nothing and is never echoed.
- **Rendering.** The Infobox on a campaign page shows the route campaign and its own perspective only. On a World or Timeline page it shows a retained campaign as **Selected campaign** (not "Campaign"), only while it belongs to the world, and the timeline when the route names one, that the server confirmed; an unconfirmed world shows nothing. The sidebar's campaign-specific links use the resolved campaign of §4 (route, else compatible selected, else none; no last-visited or startup guess).
- **Outside the campaign layout (`SelectedContextReconciler`, in the authenticated shell).** Sign-out, or a different user or browser session, drops the selection. A selected campaign the *authenticated* session no longer lists is cleared with everything that depended on it (a loading, refreshing or failed session never clears anything). A perspective the bootstrap no longer authorizes is cleared to an explicit none off the campaign route (on it, the layout does this with its notice), so neither the server default nor re-authorization brings it back. A confirmed world route commits its world and timeline, and keeps a retained campaign only if that campaign belongs to them; a different world therefore clears the campaign and perspective (no announcement yet: P02-5).
- **History (every authenticated route).** Every accepted in-app location, including its initial entry, mirrors the validated selected context into its own entry (`state.ctx`, `EntryContextV1`) by a same-entry REPLACE: no question, no remount, no new entry, no session refresh, scroll kept, unrelated state and the task descriptor carried over, and abandoned the moment a newer location exists (`navigation/replaceOwnEntry`, bound to the entry and to the router's own copy of it, so a render that lags a landed replacement cannot repeat or contradict it). Ownership is by route family and never overlaps: the campaign layout stamps and restores campaign routes (the route campaign governs, a stamp naming another scope is no stamp); `SelectedContextReconciler` stamps and restores World and unscoped routes in one ordered pass (restore, reconcile, mirror). On a reload, on Back/Forward, and on the first location the shell sees, a versioned stamp is validated against the *current* bootstrap and replaces the selection: its campaign must be listed, its world and timeline must be that campaign's own, and its perspective must be authorized or an explicit `null`. An explicit none is restored as none and is never replaced by the server default; an uninitialized perspective is recorded as what it resolves to. A stamp of nothing (no campaign, World, timeline or perspective) restores an empty selection, and the empty selection is not re-stamped as anything else. **A World with no campaign is a valid selection and survives** (a stamp with `campaignId: null` and a `worldId`). History ids are not authority and the bootstrap carries no World list, so a World-only stamp is held as a request: the shell asks the session's own World read (`GET /worlds/{id}`, the read a World route uses). Each such restoration is one **attempt** that owns one request and one result (never a shared or retained read, so an earlier attempt's success, failure or loading state cannot settle a later one), and records the history entry it was made for (key and state), the selection revision it was made against, and the user and session. Its result is applied only while all of that still holds, judged by one predicate: a newer entry on the same address (PUSH, or an unrelated REPLACE with other task state) never inherits it, a deliberate selection change invalidates it even if the store later returns to the same values, and a change of user or session ends it. Same address, same World id and an empty selection are not evidence of ownership, and abort only assists cleanup. Until it answers, the attempt governs nothing, displays nothing as an authorized selection, infers no campaign, timeline or perspective, and the entry keeps its record of it (nothing is mirrored over it). A readable World is committed (replacing the retained selection, as a campaign stamp does); an unreadable or failed one drops the attempt and, because it still owns the revision, clears a World-only selection of that World, then the entry is repaired to record what the shell holds. A World route confirms its own World, so it asks nothing more. **Timeline policy:** the recorded timeline is restored only if the confirmed World lists it; otherwise the World is restored alone (never a guessed timeline), and a timeline with no World, or a perspective with no campaign, makes the stamp unusable. Absent, malformed, wrong-version, partial, mistyped, foreign, unauthorized and older (perspective-only) stamps restore nothing, and the entry is repaired to record what the shell actually holds. Restoring changes only the retained selection, never an execution scope: a campaign route still reads its own address, and a World route still reads its confirmed world. A Link (a new entry with no stamp) starts from the current selection, and a campaign route from that campaign's default or its retained choice.
- **Transition ownership.** Stay changes nothing (selection, route, history, task, form, picker draft, unknown writes). An accepted transition commits the context before dependent reads, and a newer accepted navigation supersedes older cleanup and read work (reads and labels are owned by the authority under which they started, §4.8.1). Permission loss removes the inaccessible content at once and clears the choice without a question; re-authorization does not resurrect it. Entry-bound replacements never overwrite a newer entry.
- **Limits stated plainly.** (0) A retained World-only selection is verified when it is restored, not again while it is retained: a revocation after that is not noticed until the next read, as everywhere else, and when the World read of a World-only restoration fails for any reason (including a transient error), the attempt is dropped and a World-only selection of that same World is cleared (failing closed) **only while the attempt still owns its history entry (key and state), the selection revision, the user and the session**; a superseded result clears nothing, and a newer selection is never cleared by it. On a **World route naming a different World** than the stamp, two cases differ. When the route's own World read **succeeds**, the route-confirmed World is the stable reconciled result and the World the route displays (the panel takes its World from the route, not from the retained store): a route commit that actually changes the selection increments the revision and supersedes the stamped-World attempt, whereas a no-op commit leaves a still-owned attempt free to commit the verified stamped World into the retained store afterwards, and the resulting reconciliation restores the route World; no ordering between the two reads is guaranteed. When the route's World read **fails or is refused**, no confirmed World exists to supersede the restoration: the separately authorized stamped World may remain as retained context, but the route does not display it as its own confirmed World (the active World is set only once the route's World read is ready). Reload evidence in the tests is a simulated remount from the entry's state in jsdom; real reload, new-tab and bfcache behavior of `history.state` is unverified. (1) Three inputs are independent and none stands for another: the **route's scope** (campaign, World or unscoped), **what this tab already holds** (the in-memory selection store, which is empty in a tab that has not yet selected or adopted anything, and which a reload also empties), and **usable mirrored history state** (a valid `ctx` stamp on the entry). "No history state" is not a synonym for "fresh tab": a same-tab link creates an entry with no stamp while the store is full, and a reload has a usable stamp while the store is empty. Nothing is stored in the browser or a URL, and nothing is guessed. A **new tab** (empty store, no usable stamp): a campaign route adopts the route campaign and initializes the perspective from the authorized bootstrap default; a World route takes the world and timeline from the confirmed World read and holds no campaign; an unscoped route selects nothing (no last-visited or startup guess, PD-2). "Nothing selected" is the outcome only for an empty store with no usable stamp on an unscoped route. Same-tab navigation retains the held selection wherever the destination has no stamp (a campaign route keeps an already-held same-campaign choice, including an explicit none; a World route keeps a campaign compatible with its world and timeline; an unscoped route keeps any eligible selection). A **reload or first location with a valid stamp** restores the mirrored context after revalidating it against the current bootstrap, and any part that fails is dropped. A missing, malformed, wrong-version, foreign or unauthorized stamp is "no stamp": it is not an explicit none and not proof of authority loss. An explicit none in a valid stamp is restored as none and not replaced by the default; a perspective cleared because the bootstrap stopped authorizing it is not brought back by the default or by re-authorization. On a campaign route a Back/Forward to an entry with no usable stamp, after the campaign layout has processed a location, resolves to that campaign's bootstrap default (a context transition, guarded when dirty); the layout's first location with no usable stamp instead keeps what the session holds. The per-case table is the P02 reconciliation record §6.2. A history entry that survives a sign-out and a different sign-in in the same tab carries ids only and restores only what the new bootstrap authorizes. (2) The guard compares context only where the campaign layout is the committed owner; on World and unscoped pages a differing retained selection at the same path is not a guarded transition (those pages read nothing under it). (3) A background refresh and the client store cannot detect a permission change the client has not been told of; the server still refuses every read. (4) The reconciler clears a world and timeline together with a lost campaign. (5) The announcements and heading focus of a deliberate selection are not part of this (they are §4.8.4; the conditional Navbar controls are §4.8.3).
- **Manual checks still required (not provable in jsdom).** Reload and new-tab behavior of `history.state`; Back/Forward across campaigns and perspectives in a real browser; the bfcache; a second tab revoking access while the first is open; keyboard and focus order after Stay and Discard; screen-reader output of the **Selected campaign** label.

#### 4.8.3 Navbar split controls and the menu / drawer / focus lifecycle (P02-4)

**Implemented in P02-4 (automated jsdom tests only; real-browser keyboard, touch, focus, narrow/zoom and screen-reader checks are pending and are not claimed). Decision PD-11 is owner-approved: opening a menu by pointer or keyboard moves focus to its first enabled item.**

*Activation.* The destination is derived from the validated selection and the route metadata (`navigation/navbarDestinations.ts`), never from the record on screen and never from a last-visited, startup or sole-campaign guess. A viewed record does not become a selection.

| Control | Selected context (validated) | Default details | Main control |
|---|---|---|---|
| Campaign | The resolved campaign (the route campaign on a campaign route; else the retained one, only if compatible with a World route) | `/app/:c/home` | Link "Campaign: open ‹name›" |
| World | The route-confirmed world, else the retained World that is compatible with the retained campaign | `/worlds/:w` when `world.view` is known (the server's World read, or the bootstrap's `world_capabilities` for a campaign of that World); else `/app/:c/world` when a campaign of that World resolves; otherwise none | Link "World: open ‹name›" ("World: open selected world" when the name is unknown) |
| Characters | The perspective of the resolved campaign: the explicit choice for that campaign, or the bootstrap default only while none has been made; an explicit none and a character the bootstrap no longer lists are none | `/app/:c/characters/:id` (the record shell) | Link "Characters: open ‹name›" |

The main control is a **link** (an ordinary anchor: modified click and new tab stay the browser's, and it starts a task with root = the section, guarded like any departure) whenever an authorized selected destination exists and the page shown is a different one, **whatever task the person is in** (viewing character B in a Characters task with character A selected links to A; a Campaign page that is not Home links to Home; another world page links to the world's details). "The page shown is the destination" is decided by route and parameters (`isSameDestination`, over the route metadata), never by a string prefix and never by the query or hash: the record shell with `?section=notes` is still the shell, and its edit page, another record, or the list are different destinations. Otherwise the main control is a **button** ("Campaign menu", "World menu", "Characters menu"; `aria-expanded`, `aria-controls`) that toggles the menu and never navigates: with no applicable selection (menu offers Browse/Select) or already at the destination. The accessible name of the main control always begins with its visible label ("Characters: open ‹name›", "Characters menu"), and the disclosure is a different name ("Show characters menu"). The disclosure is always a button that toggles. A selection being validated is not a separate state: while the bootstrap loads the sidebar keeps its reduced frame (no group). The Characters menu offers **Selected character** (a disabled "Select a character first" entry when none) and **All characters**; it offers no create action until the create-action decision (PD-8) is made.

*Menu lifecycle (every sidebar disclosure and the drawer; `components/useSidebarMenu.ts`).*

| Event | Menu | Focus |
|---|---|---|
| Initial render, route in the section | Open | Unmoved (never steals focus on a remount) |
| Opened by pointer or keyboard, from the main button or the disclosure | Open; that control is recorded as the opener | The first enabled item (links and enabled buttons; disabled entries are skipped) |
| Closed with a control | Closed | Stays on the control |
| Escape in the menu | Closed (propagation stopped, so the drawer stays) | The recorded opener, or the group's first control if it is gone |
| Tab out, or a pointer-down outside the group | Closed | Unmoved: the new target keeps focus |
| …while a navigation question is on screen (page guard **or** a holder's own blocker) | Stays open | The question's dialog owns focus; it is not stolen |
| A child link or the main link is activated | Stays open until the navigation that click started arrives (next paragraph) | Accepted: the new page's heading. Stay: the activated control |
| Accepted navigation | The menu and the drawer close together | The page heading (`usePageArrival`) |
| Stay, with the original control unusable | Menu and drawer unchanged | `ConfirmDialog` falls back: activated control, then the group's opener, then the drawer toggle (the eligibility check is the one `FormDialog` uses, `utils/focusEligibility`) |
| Drawer Escape with no menu open | Drawer closes | The drawer toggle. Ignored while a question is on screen (Escape there means Stay) |

*Accepted navigation, not the click, and not any navigation to the same pathname.* A click records the full requested destination (path, query and hash) and the entry it left, and then owns *the router request it started* (`navigation/navigationAttempt.ts`). The mechanism is the installed router's own: each `navigate()` mints a location with its own key, which is visible while the request is held by the unsaved-changes blocker (`blockers`, `blocked`), while it is in flight (`navigation.location`), and when it commits (`state.location`, the same key). Nothing is written to history or router state to track it; the link's own task and context state are left as they were. The contract:

- *Arrival closes once.* The menu and the drawer close, once, when the owned request commits by PUSH or REPLACE at its destination. A request that commits without ever being seen in flight (nothing to wait for) is accepted on its first commit when that commit is the full destination and nothing else committed in between.
- *Leave.* A held request that is answered Leave (`proceeding`) is followed through its new navigation. *Stay* (the blocker returning to idle, also reported by the blocker as `reportQuestionAnswer("stay")`) cancels, and menu, drawer, drafts and focus stay as they were.
- *Redirect (what is and is not provable).* The router marks every redirect `state._isRedirect`, whoever asked for it, and gives the continuation a fresh key and no reference to the request that caused it (`createLocation` in `startRedirectNavigation`; installed 8.3.0 and 8.4.0 alike). The marker therefore proves a redirect, not whose. The attempt follows a marked location (in flight or committed unseen, never by POP) only while the router has been seen doing nothing but this one navigation: no fetcher loading or submitting and no revalidation running, at the click or at any state since (`isBusy`, read from `state.fetchers` and `state.revalidation`). With one navigation and no other work, nothing else can have produced the redirect. Once any other work has been seen the attempt stays ambiguous, and a redirect cancels it: the menu and the drawer stay as the person left them and no focus is restored on the click's behalf, even when the redirect leads to the very address the click asked for. A redirect made later by a component (`<Navigate>`) is a separate navigation after the arrival and neither re-closes nor leaves anything pending.
- *Redirect limits.* Elimination, not correlation: a fetcher or revalidation that ran during the click's navigation and finished without redirecting also makes the attempt ambiguous, so the click's own loader redirect then leaves the drawer open (the safe direction). Work the router does not expose (a fetcher on a different router, application code that calls `navigate` itself) is cancelled as an unrelated navigation, because it is not marked.
- *Not ours.* Another request that supersedes the in-flight one (another link, the same address asked for by someone else, a different query or hash on the same pathname), a POP, a commit during the question, a failed route (committed with route errors), a navigation that ends without arriving, and any REPLACE other than the stamp of the entry that was left, cancel it. The stamp (REPLACE of the left entry at its own address, written by the selected-context owners) is ignored. No cancelled attempt leaves a pending close or a registered focus fallback.
- *Without a data router* (an isolated test tree) only commits can be watched, with the same rules.
- A menu also closes by the Tab-out rule when a page that is not the owned arrival moves focus to its heading; the drawer is closed only by ownership. A modified click or a new tab is the browser's and starts no attempt.

A stamp-only REPLACE (the context stamps and task clean-ups the selected-context owners write) therefore neither closes anything nor moves focus; `usePageArrival` likewise ignores a REPLACE of the entry already arrived at, with the same address and nothing to announce. Opening a menu never asks the guard question, disposes input or changes the selection.

*Limits stated plainly.* The selected World is trusted as the store committed it (route-confirmed, or confirmed by the restoration read of §4.8.2); a World-only selection with no `world.view` evidence offers no link rather than a guess. The sidebar remounts on a campaign-scope change (existing behavior), so a menu whose section the new route is in starts open by the initial-render rule. One case is unobservable and accepted: a request that completes without any intermediate state and is preceded, in the same tick, by an unrelated REPLACE to the same address as the one it left cannot be told apart from its own (nothing else navigates inside that window; the stamp writers wait while a navigation is pending or held).

*Manual checks still required (not provable in jsdom).* Keyboard-only use of every control and menu (Enter, Space, Escape, Tab, Shift+Tab); a native keyboard activation (jsdom dispatches the click it produces); touch with no hover; focus visibility and sticky obstruction; the collapsed-rail flyout and stacked icon controls; the narrow drawer; 320 px and 400% zoom; NVDA/VoiceOver names, roles and states of the split controls; Safari/Firefox on macOS, where a clicked link or button does not take focus.

#### 4.8.4 Deliberate Infobox selection: an ordinary departure that starts a new task (P02-5, decision PD-6)

**Implemented in P02-5, with the announcement and heading-focus correction (automated jsdom tests only; real-browser keyboard, focus, screen-reader and owner checks are pending and are not claimed).**

**Decision PD-6 (owner-approved).** Choosing a different character perspective in the Infobox navigates to that character's Characters details (`/app/:c/characters/:id`) and starts a new Characters task there. It moves the person off Knowledge or Quests, which is intended. The alternative that was declined was to stay on the page with only a task reset. **Owner addendum (ordinary departure).** The change acts exactly like navigating away from the current page, with the same guards and operation-ownership protections, *including when the person is already inside the Characters route family* (another character's details, the list, an edit page). It is not a special "context switch" with its own rules, its own confirmation or a way around a hold.

| Choice | Destination | Task | Notes |
|---|---|---|---|
| A different character perspective | `/app/:c/characters/:id` (the id the person chose, and only an id the bootstrap authorizes for this campaign) | New task, root `characters`, scope the campaign, no trail, no list state | PUSH, even when the pathname would not change (choosing the character already on screen while another is selected): the committed context differs, which the guard already treats as a transition |
| No perspective ("No character perspective selected") | `/app/:c/characters/all` | New task, root `characters` | A character route is never built from `null` |
| A different campaign | `/app/:c/home` | New task, root `campaign`, scope the new campaign | The perspective is not carried (the scope remounts) |
| A different world | The destination the World control already opens (`/worlds/:w`, or the campaign's `/app/:c/world`) | New task, root `world`, scope of the destination | The selected campaign, timeline and perspective are cleared unless compatible (§4.8.2) |
| A different timeline | `/worlds/:w/timelines/:t` | New task, root `world` | With `world.view` the world route above. Without it (§4.8.12, CN-1), a timeline with one authorized campaign opens `/app/:c/home` as a campaign choice (PUSH, new task, root `campaign`), and one with several opens the inline campaign chooser instead of navigating |
| The value already selected | Nothing | Nothing | No question, no entry, no task change |

*What the request is.* One `navigate(destination, { state: { task, ctx } })` (`navigation/selectionTransitions.ts`). The state is built fresh: nothing of the page left is carried, not its query (`character_id`, `party_id`, `section`, filters), hash, trail, list state or any other router state, so the new task cannot inherit what belongs to the page it replaced. Nothing else happens first: no selection write, no task reset, no query cleanup, no bootstrap refresh, no unmount.

*Who decides.* The existing departure blocker, unchanged: a dirty page, any navigation hold (an open picker recording), and a page's own unresolved-write rule (pending, unknown outcome, confirmed-but-unread) ask the page's one question. **Stay** (`blocker.reset()`) leaves everything as it was: the route, the entry, the selection and the select's shown value, the task, history, entered values, the picker draft, the held request and its idempotency key, and the receipts; focus returns to the control. **Leave** follows the same policy as any ordinary navigation link: the page unmounts as it would for any departure, and a receipt or draft the page does not preserve across a departure is lost exactly as it is for any other departure. No separate confirmation exists, and no hold is bypassed.

*What commits, and when.* Only on the accepted location, in one step before any dependent page reads: the destination, the selection (committed from the entry's validated stamp, §4.8.2), and the task (from the same entry). The page content remounts under the new perspective, so every read the destination makes runs under it, and a background session refresh revalidates the perspective list. A newer accepted navigation supersedes older transition work: a read begun for a character who was replaced before it answered is ignored (the destination page is path-and-perspective keyed).

*What is not a deliberate selection, and so neither navigates nor resets a task:* a bootstrap refresh with the selection still authorized; loss of authorization (the perspective is cleared to an explicit none with the existing polite notice, without a question, and is not resurrected by re-authorization); Back or Forward to an earlier entry (the entry's own stamp and task are restored through the guard of §4.8.2, with no new departure); route reconciliation and the stamp-only REPLACEs. None is a PD-6 navigation.

*Three things that stay separate.* The **execution scope** is the campaign the route names; the **explicit selection** is what the Infobox holds; the **viewed record** is what the page shows; the **task origin** is where the task started. Opening the character the person chose is a destination, not a derivation: the client never infers authority from the selection or from the record on screen, and the server authorizes every read.

*Announcement and focus (P02-5 correction).* One owner, `SelectionArrivalProvider`, inside the authenticated shell, decides both from the same *arrival*: a PUSH the router accepted that carries a selection note (`state.selection`: the level and the id chosen, nothing else; never a name) **and whose note belongs to the address it arrived at**. The arrival is judged from the router's committed locations, not from what React rendered. A link, Back/Forward, a reload, any other REPLACE or a newer navigation ends it. A same-value choice, a Stay, a bootstrap refresh and a superseded attempt therefore announce nothing and move nothing.

- **The note must fit its destination** (`navigation/selectionChange.ts` `selectionScope`). A well-formed note is not enough: its level and id must be the ones the route names, and the campaign or world the address carries becomes the arrival's scope. Campaign: `/app/:id/home`. World: `/worlds/:id`, or `/app/:c/world` (a world opened through a campaign of it, which must be in the session, in that world, and the committed campaign). Timeline: `/worlds/:w/timelines/:id`, with the committed world equal to `:w`. Character: `/app/:campaignId/characters/:id`, or `/characters/all` for none. A valid note on any other route (copied, forged or stray state) is not an arrival: nothing is announced and no heading is focused, even when the selection store happens to agree with it.
- **One eligibility for announcement and focus** (`navigation/selectionEligibility.ts` `contextEligible`). Before an arrival is spoken or exposed to the destination as something that may take focus, the committed selection must be the one chosen AND agree with the route's scope: campaign = the chosen campaign; world = the chosen world, and for `/app/:c/world` also that campaign being in the session, in that world, and committed; timeline = the chosen timeline in the world the route names; character = the campaign and the chosen perspective (an explicit none included). The announcement and `ArrivalHeadingFocus` read the same predicate, so they cannot disagree: `/app/:c/world` with a marker naming another World neither speaks nor focuses. Whether a name is readable only changes the wording (generic text), never the eligibility. A legitimate arrival whose context has not settled yet stays pending (it is not discarded) and acts once the context settles; a superseded arrival is never revived.
- **Only the stamp writer's stamp keeps an arrival** (`navigation/entryStamp.ts`, `SelectionArrival.isOwnStamp`). The selected-context owners restate the accepted entry with a same-entry REPLACE written by one function (`navigation/replaceOwnEntry.ts`). That writer declares what it wrote: before it hands the router the new state it calls `markStamp(entry, state)`, which records, in memory, that this very state *object* is a stamp of a chain rooted at the first entry that was not itself a stamp. Observers ask `stampRoot(state)`. The mark is the object's identity (a `WeakMap` key), so no value can claim it: a copy, a spread, a structured clone, a history round trip (Back, reload) or any other navigation's state is never a stamp, however closely it resembles one. It is registered before the router can see the state, bound to the root it restates (an observer accepts it only for the chain it arrived at, so a stamp of an unrelated entry does not count and a batched render that skipped an intermediate stamp still recognises the last), and there is nothing to release: a stamp that is blocked, superseded or abandoned leaves an object nobody holds, with no flag, queue or counter that could suppress a later navigation. Two writers are identified this way, as different kinds of mark with different permitted changes. The **context stamp** (`markStamp`, `replaceOwnEntry`) restates the same address and writes only `ctx`. The **section normalization** (`markNormalization`, `components/staged/useStagedNavigation`, the staged record pages' replacement of a missing or invalid `?section=`) copies the entry's state into a new marked object and changes only `section` in the query (an unchanged address replayed, as StrictMode's second effect does, is the same write). An arrival survives a REPLACE only if its state object carries the matching mark for one of the arrival's own entries, at the same path and hash, and the write stays within its kind's changes (a stamp at another query, or a normalization that changes anything but the section or `ctx`, does not count). Everything else ends the arrival and a later look-alike does not revive it: an external REPLACE with exactly the same address and state, a replacement with the same `section` and state shape, a copy or spread of a marked state. There is no structural exception: StrictMode's replay is real behavior covered by the tests, not evidence of ownership. **Requirement and limit:** the mark lives on the state object the router was given, which the data router the app ships (`createBrowserRouter`, `main.tsx`) keeps for every location it commits. A location rebuilt from the browser's history (a reload, Back/Forward: a structured clone) or a plain `<BrowserRouter>` carries no mark, so nothing there is ever recognised as a stamp or normalization; selection arrivals exist only under the data router, and an ordinary page arrival there would treat a stamp as the operation it cannot prove it is not (it could repeat a message). No browser-history compatibility layer is attempted.

- **Announcement.** Polite, through the shell's one live region (`AnnouncerProvider`), once, and only when the selection the person chose is the committed one (the store names it): "Viewing as ‹name›." / "No character perspective selected." / "Campaign changed to ‹name›." / "World changed to ‹name›." / "Timeline changed to ‹name›." A world or timeline change that leaves no campaign selected adds " Campaign selection cleared." (judged from the campaign selected before the choice against the committed result, so a compatible campaign that is kept is not reported as cleared). The name is looked up at that moment from what the person may read now: the session's authorized lists, or the confirmed world read; a name that is not readable is left out and the wording is generic ("World changed."). The arrival keeps ids only. A choice whose destination is never committed (a perspective lost before the choice was accepted, a World the server refuses) announces nothing. The same arrival never announces twice, including across a campaign-scope remount of the shell. The Navbar menu's campaign choice (§4.8.3) carries the same note when it names a campaign other than the one in force, and is announced the same way ("Campaign changed to ‹name›."); the campaign already in force is only a link, and Stay, a cancelled or a superseded attempt announces nothing because nothing was accepted. Its focus stays with the menu and drawer lifecycle (P02-4); the arrival moves focus only from nowhere or from the Infobox.
- **Withdrawal.** The announcer owns the message (`useAnnounceOwned`): the announcement can be taken back out of the live region by whoever made it, and only while it is still the latest message, so cleaning up an old selection message never removes a newer save, error or recovery message, and a second cleanup does nothing. `SelectionArrivalProvider` takes its message back when the authority behind the words is lost: the session is gone, the person or browser session behind the bootstrap is replaced (a new authority generation, so returning to the earlier one does not bring the message back: A, B, A), or the name it spoke is no longer readable (a revoked character, a world that can no longer be read). It clears; it never re-speaks a generic rewording. A message that was already generic names nothing private and is left. This empties what the region still holds; it does not recall speech already given.
- **Heading focus.** Once, on the destination's `h1`, when the destination has actually rendered: a boundary that has stopped loading (`CampaignSummaryBoundary`, `CharacterBoundary`, `CharacterSheetBoundary`, in their settled, unavailable and failed branches) or a page that needs no read (`/characters/all`) asks the arrival (`ArrivalHeadingFocus`); a loading placeholder (`PlaceholderPage busy`, marked `data-page-loading`) is never focused because the loaded page is about to replace it. The Campaign World explorer (`/app/:c/world`, the destination of a World choice that is only reachable through a campaign of it) asks the arrival from `WorldEntitiesBoundary` the same way: its loading region is marked `data-page-loading`, and its settled, unavailable and failed branches ask for the `Campaign World` heading. The World and Timeline pages already focus through `usePageArrival`, which counts a refused or failed read as arrived, so the "not available" heading takes focus too (intentional, retained). An ordinary navigation that carries `state.announce` (a confirmed write) announces it once when the page is ready, including when the read-back then fails, and focuses the heading once; the same entry restated by the stamp owners neither repeats the message nor moves focus again. A restating is recognised by the stamp writer's mark (above), never by resemblance or message text: the page remembers the root of the chain it arrived at, and a REPLACE whose state object carries a mark for that root is skipped. A distinct success that REPLACEs the same address, even retaining the existing `ctx` and repeating the identical text, is a new arrival with its own announcement and heading focus, and the actual stamp that follows it is skipped. No operation identifier is needed and no producer changed. The claim is bound to the location being rendered (a page still showing under the previous location while React catches up does not take it), is used up whether or not focus moved, and so a later read, a remount, a bootstrap refresh or the history stamp never moves focus again. Focus is moved only when it is still on the Infobox control the choice was made with, on the very navigation control the request was made with (the Navbar menu link: the P02-4 `NavigationAttempt` already decides which committed location is its arrival, so when it accepts, `useAcceptedNavigation` binds its activated control to that location's key in `navigation/activationOwner.ts`; the arrival reads the binding by the key it was accepted at, so an unrelated arrival at the same path, another query or hash, or a request that was Stayed, cancelled, superseded or failed never gets it, and it is used up with the focus claim; the map is bounded and in memory), or nowhere (after Leave closes the question, or because the shell was remounted for the new campaign scope, which a campaign change always does); another menu link that happens to be focused is not the owner; a person who has moved focus elsewhere while the page loaded keeps it. Stay is not an arrival, so the existing return of focus to the select is unchanged. A same-path change (choosing none on `/characters/all`) re-mounts the page under the new perspective and focuses its heading the same way.

*Limits stated plainly.* (1) The loss notice exists for the perspective (§4.8.2); losing a selected campaign or World shows the existing states, not a new notice. What the live region still holds is withdrawn when the authority is lost (above); speech a screen reader has already given cannot be recalled, and nothing private is kept in router or history state. A name that becomes unreadable only because a read is refreshing (a re-read in flight) also withdraws the message. (2) The Infobox selects and the Navbar menu's campaign list are covered; the other Navbar controls are links and start tasks without a selection note. (3) A stamp is identified by the writer's in-memory mark, not by its shape; a REPLACE written by anything other than the stamp writer is never a stamp. No unmarked REPLACE is tolerated by a selection arrival. `ConfirmDialog` (and `FormDialog`) read, before the native `dialog.close()`, whether focus is held by a live control outside the dialog other than the opener (`focusHeldOutside`, `utils/focusEligibility`), because a native modal close itself hands focus back to the element focused before `showModal()` and would erase that evidence. After the close they put focus back on that control if the close moved it (`keepHeldFocus`), and only otherwise return it to the opener, then the registered fallbacks. The rule is focus ownership, not a close reason: nothing infers Leave from focus position, callers pass nothing, and Leave, Stay and Escape differ only in what the page does. A destination that arrives after the close takes focus from the opener through the activation hand-off, so no timer is involved; a held control that is gone, hidden or inert falls back to the opener as before, and an unmount restores nothing. Evidence is a jsdom model of the native rule (`test/nativeDialog.ts`), not a browser run: native-browser behavior of a modal dialog (which also keeps the page behind it inert, so a destination heading may not be able to take focus until the dialog closes) is pending the owner check in the ledger. (4) The Characters section pages other than the details and `/characters/all` (inventory, builds, edit) do not take this focus; the broader Characters shell is P02-6. (5) The world list on a campaign-less World route does not offer "no world", so there is no clear action for the world, timeline or campaign levels; only the perspective has an explicit none. (6) What a screen reader says for a changed focus plus a polite message, and in which order it is spoken, is not provable in jsdom.

*Manual checks still required (not provable in jsdom).* Keyboard-only use of the Infobox selects (a change by arrow keys can fire on every step); focus after Stay and after Leave; screen-reader output of the selects and of the destination; the two-tab revocation case; Back and Forward across perspective entries in a real browser.

- **`returnTo` is a back address, not an origin (P02-7d correction).** A lone `returnTo` resolves onto the route's default task with a `backTarget` and names no task. `hasTaskEvidence` (`navigation/resolveTask.ts`) is the one predicate for "this entry names an origin": the entry's own validated task, or a legacy key that adapts into a task (`worldSearch`, `reviewSearch`, `itemsSearch`, `definitionsSearch`, a characters return). `taskOf`, `outsideTaskOf`, `retainedState`, `useHasTaskOrigin`, `useTaskLinkState({ requireOrigin })`, the item and NPC edit pages' task readers all use it, so a record or edit entered with only `returnTo` keeps its single back link and forwards no synthesized task; a `returnTo` beside a valid key or an explicit task changes nothing (the task wins).

That write is `replaceOwnEntry` with the `normalization` writer mark (`useStagedNavigation`): it checks the router's actual current location against the entry it was computed for, waits while a navigation is pending or a blocker is blocked or proceeding, is abandoned by any newer PUSH, POP or unrelated REPLACE and by effect cleanup, and takes the query and state from the router's own copy of the entry (so the task, context and unrelated state are kept). After Stay the still-current entry is normalized; after Leave nothing is written over the destination. The mark only declares what the write is; it never authorizes one. Before the correction the hook wrote from the rendered entry (`setSearchParams`), and the new hook-level regressions reproduce that: a departure made before the read answered was overwritten with the old address, a newer same-address entry was rewritten with the older entry's state, a pending navigation was interrupted, and a normalization under a dirty guard re-asked or was lost. The reviewer did not reproduce the redirect-back in the browser; the hook-level reproduction is in jsdom, not a real browser.
- **Limits.** jsdom does not establish keyboard, zoom, screen-reader or native-dialog behavior; the recorded P02-5 limits remain.

#### 4.8.12 Context-navigation correction: read gates, destinations and meaningful choice (approved 2026-11-11; implemented)

**Contract as implemented** by the [correction plan](PHASE15_CONTEXT_NAVIGATION_CORRECTION_PLAN_2026-11-11.md) (slices CNC-1 to CNC-3). The earlier sections now carry the same rules; this section stays as their source. It is awaiting independent review and the real-browser checks below, and it is not owner-accepted. Nothing here changes server authorization, a route, a migration or the selection store's semantics (§4.8.2).

**Owner decisions (2026-11-11).**

- **CN-1, campaign-only Timeline navigation.** A caller without `world.view` on the selected world is offered the timelines represented by their authorized campaigns on that world. A timeline with exactly one such campaign opens that campaign; a timeline with several requires an explicit campaign choice; a campaign is never picked arbitrarily. No world-level timeline route is offered or inferred, and no sibling timeline is shown without independent authorization. The Campaign level's compatibility filtering and every existing route to an authorized campaign are unchanged.
- **CN-2, meaningful choice.** A level with no actionable destination is disabled; a level whose sole destination is already selected is disabled; a sole destination with nothing selected is enabled; several destinations are enabled while a meaningful alternative exists. No automatic selection and no clearing action are introduced. A display-only fallback for the current context is never an actionable option.

**Read gates (who may open what).** `world.view` is the gate for reading a world and its timelines: the Infobox Timeline level, the Timelines collection's tree, the read-only World overview's tree and the sidebar's **Timeline overview** follow it (the server's `GET /worlds/{id}/timelines/{t}` already requires exactly `world.view`). `worldAccess(...) === "edit"` means `world.manage` and keeps gating only the management overview it selects today. Timeline mutation controls (New timeline, Edit timeline, Create branch, archive/restore, New campaign) stay on the server's `available_actions` and `capabilities` (`timeline.manage`, `campaign.create`). So a world Viewer, Reader, Reviewer, Editor, and an Owner without system GM (who holds `world.view` and `timeline.manage` but not `world.manage`, ADR 0020 decision 4) can all open a timeline's overview; only those the server offers actions see them. Campaign membership still never grants `world.view` (ADR 0019 decision 2).

**Destinations per level.** Each level's options are built by one pure model from authoritative inputs only: the current session bootstrap (campaigns, each with `world_capabilities`), the `GET /worlds` list (first page, see the deferred limitation below) and the hierarchy provider's `GET /worlds/{id}` for the active world. One option per id; ids that come from nowhere else are never echoed.

| Level | Option source | Destination | Why |
|---|---|---|---|
| World | `buildWorldChoices` (ADR 0019 decision 3), reconciled below | Explicit world access: `/worlds/{w}`. Campaign-derived only: `/app/{c}/world`, `c` = the route campaign when it is on that world, else the first such campaign in bootstrap order | Unchanged ADR 0019 rule; explicit authority wins, so a mixed-access caller has one entry per world |
| Timeline, world readable (the active world's read is ready, so the caller holds `world.view`) | The world read's `timelines`, in server order | `/worlds/{w}/timelines/{t}` | Explicit authority wins (the ADR 0019 precedent); the world route's Campaign level then offers the compatible campaigns, so no campaign is chosen for the person and no chooser is needed |
| Timeline, not world readable (the bootstrap's `world_capabilities` for the route campaign lacks `world.view` so no read is sent, or the read was refused, or it failed transiently) | Distinct `timeline_id`s of bootstrap campaigns whose `world_id` is the active world, sorted by case-insensitive name then id; a campaign with no timeline adds nothing; a null name reads "Unnamed timeline" | One campaign on it: `/app/{c}/home`. Several: the **campaign chooser** (no navigation) | CN-1; only reached on a campaign route, because a World route is reachable only with `world.view` |
| Campaign | Bootstrap campaigns on the active world **and** timeline (unchanged compatibility filter), bootstrap order | `/app/{c}/home` | Unchanged |

While the active world's first read for this world is pending (no settled result), the Timeline level is disabled with "Loading timelines…" rather than offering campaign destinations that would change under the person when the read settles. A refetch that keeps ready data keeps the world-readable destinations.

**Actionable choices and states.** For each level, *selected* is the committed id at that level (the confirmed route world/timeline, the route campaign, or the **Selected campaign** of §4.8.2), and *actionable* are the options whose id differs from it. A selected id that the option source does not carry is shown as a display-only option and counted as nothing. The level is enabled when it is not loading and either nothing is selected and at least one option exists, or at least one actionable option exists. Every disabled, loading, empty and error state shows a visible reason under the control, referenced by the control's `aria-describedby`; reasons are neutral and carry no name, id, capability or count:

| State | World | Timeline | Campaign |
|---|---|---|---|
| Prerequisite missing | n/a | "Select a world first" | "Select a timeline first" |
| Loading | "Loading worlds…" (until the list settles; campaign-derived entries wait with it so a destination never changes under the person) | "Loading timelines…" | n/a (bootstrap is already loaded) |
| Transient failure | "Your worlds could not be loaded." + **Try again** (re-reads `GET /worlds` only); campaign-derived entries stay offered | "This world's timelines could not be loaded." + **Try again** (re-reads the active world only); campaign-derived timelines stay offered | n/a |
| No options | "No world available" | "No timeline available" | "No campaign available" |
| Sole option already selected | "No other world available" | "No other timeline available" | "No other campaign available" |

**Try again** repeats the failed read and nothing else: no navigation, mutation, bootstrap refresh or selection write. If it succeeds while it still holds focus, focus moves to that level's select when enabled, otherwise to the level's reason text (programmatically focusable); a failed retry leaves focus where it is. Retries are never automatic. The Character level keeps its §4.8.2/§4.8.4 contract (its explicit "No character perspective selected" is a real choice); its no-campaign placeholder gains the reason "Select a campaign first".

**The campaign chooser (CN-1, several campaigns on one timeline).** Choosing such a timeline in the Timeline select opens an inline, non-modal group directly beneath that select inside the Infobox's Timeline section. It is not a dialog and is never opened by a render, a refresh or history.

- *Content.* A `role="group"` labelled by its visible instruction "Choose a campaign to open ‹timeline name›", a list of links, one per authorized campaign on that timeline in bootstrap order, each named by the campaign, and a **Cancel** button. Each link asks for `/app/{c}/home` with a new `campaign` task and the `campaign` selection note (the same request as the Campaign select), so an accepted choice is announced "Campaign changed to ‹name›." and focuses the destination heading by the §4.8.4 rules (the chooser is inside the Infobox, so focus there counts as the origin).
- *What opening does.* Nothing else: no navigation, history entry, task, selection write or guard question. The Timeline select stays controlled at the committed timeline; while the chooser is open its `aria-describedby` also names the instruction. Focus stays on the select (a keyboard change on a closed select can fire on every arrow step, so focus is not pulled away); the chooser is the next Tab stop. Its instruction is announced once, politely, through the shell announcer as an owned message that is withdrawn when the chooser closes.
- *Dismissal.* **Cancel** or Escape inside the group closes it and returns focus to the Timeline select (Escape does not propagate). Choosing another timeline replaces it (a one-campaign timeline navigates; the committed timeline just closes it). Any location change closes it (state keyed to the location; never stored in history, a URL or browser storage). A REPLACE of the very same address is not a location change the person made, because it is the context stamp the selection owners write onto their own entry, so the chooser rides through it; a PUSH, a POP or another address ends it, and what ended is forgotten: going Back to the entry it was opened at does not reopen it. Choosing the committed timeline again closes it where the browser reports that choice. A pointer-down outside does not close it.
- *Departure guard.* Only a chooser link asks a question, through the existing blocker. **Stay** changes nothing and leaves the chooser open with focus back on the activated link (`ConfirmDialog`'s activated-control rule). **Leave** proceeds; the destination commits the context per §4.8.2 and the scope-keyed remount removes the chooser. Cancel never asks.
- *Access changing while it is open.* Its entries are derived from the current bootstrap on every render, never a snapshot. Campaigns added or removed update the list; if the focused entry is removed, focus moves to the instruction. One remaining campaign stays a link the person must choose (no automatic navigation). None remaining closes it, shows "That timeline is no longer available." in the Timeline level's reason, and returns focus to the select if it was inside (to the reason text when the select is disabled because nothing else remains to choose). If the active world becomes readable while it is open (a successful retry), it closes because the timeline now has a world destination. A campaign revoked after the click and before arrival reaches the existing campaign-not-found state.

**Revalidation and reconciliation.** Sources are compared by when their read *started*, never by when it answered; an aborted or superseded read contributes nothing (`useAuthoringResource` already guarantees that per path).

- *Bootstrap.* Campaign-derived destinations always come from the current authenticated bootstrap; a loading, refreshing or failed session clears nothing (unchanged).
- *Explicit World entries.* The `GET /worlds` list is positive evidence only (absence is not refusal, because the list is a first page). An explicit entry for world W is offered only while the list lists W with world access **and** no authoritative refusal (404 or 403) of `GET /worlds/W` started after the list read started. A world read of W that succeeds after such a refusal, or a newer list read that lists W, restores it. A refusal never removes a campaign-derived destination: W stays as a campaign-derived entry when the bootstrap has a campaign on it. A successful world read of a world the list does not carry adds no entry (the list stays route-independent; the current world is shown display-only).
- *Transient failures* (network, 5xx, timeouts) are not evidence: earlier verdicts stand, the affected level shows its retry, and independently valid campaign destinations remain.
- *Cached presence is not authority.* Timeline options read only the current settled world read for the active world (never `useKept` data or a previous world's response), and a refusal recorded after a list read outranks that list's entry.
- *Selections are not cleared by reconciliation.* Reconciliation only changes options and reasons. Committing, clearing and restoring the selection stay with §4.8.2, so a stale response can neither restore an invalid destination nor erase a newer valid selection.
- *Authority change.* The evidence belongs to one user and browser session (the owner key of the selection store) and is discarded with it.

**State transitions.** All choices are ordinary departures (§4.8.4): one PUSH with a fresh task, guarded first, nothing committed before acceptance.

|---|---|---|---|---|---|

| Chooser campaign | As the one-campaign row | | | | |
| Campaign | PUSH `/app/{c}/home`, root `campaign`, note `campaign` (unchanged) | `c`'s | `c`'s | `c` | `c`'s |

## 5. Core screens

### 5.1 Login and invitation

States:

- Sign in (local username/password against `POST /auth/login`).
- Account activation from an administrator-issued invitation link (`POST /auth/activate` — sets the account's first password; no temporary password is ever assigned or displayed). Before showing the passphrase form the page runs an advisory, read-only `POST /auth/activation-status` check (token in the JSON body only); an unusable link of any kind shows one generic message with no password fields, a transport failure shows Retry, and `POST /auth/activate` still repeats every check.
- Password reset from an administrator-issued link (`POST /auth/password-reset`). Like activation, the page first runs an advisory, non-consuming `POST /auth/password-reset-status` check (token in the JSON body only) and shows the new-passphrase form only for a usable link; every unusable reason shows one generic unavailable state with no password fields, a recoverable failure or rate limit shows a distinct message with **Try again** rather than an invalid-link claim, and `POST /auth/password-reset` still revalidates and atomically consumes the token.
- Accept campaign invitation, either through the manual authenticated-acceptance form or through single-link onboarding (Phase 13E checkpoints 8a-8d): opening a shareable `/campaign-invitations/accept#token=<one-time-token>` link begins a short-lived server-side onboarding session, then offers **sign in** (an existing account) or **create account** (invitation-authorized registration — the only public account-creation path in this codebase) before automatically accepting the invitation. The completion screen names the campaign by its audience-safe display name and explains that a GM may still need to assign a role, character relationship, resource grant, or access-group membership before campaign content becomes available — see `docs/PHASE13E_ACCESS_CONTRACT.md` §3n for the full delivered contract.
- First-time profile confirmation.
- No active campaign membership.
- Expired, revoked, invalid, or already-consumed invitation/onboarding/activation/reset token/session — every case collapses to one generic unavailable response, never a distinguishable cause.
- Password reset (self-initiated request plus administrator-issued reset — `POST /auth/password-reset`), and an account-disabled state distinct from a wrong-credential state (both still return the same non-disclosing sign-in error, per §12).

The portal does not expose campaign names or invitation details until the invitation token is validated. After login, the session-bootstrap response (`GET /auth/session`) is what the application uses to resolve the authenticated user and evaluate campaign membership — never an external identity mapping.

### 5.3 Campaign Home dashboard (`/app/:campaignId/home`)

The dashboard answers: “What do I need to know right now?”

Ordered sections:

1. Ask about this campaign.
2. Last-session recap.
3. Current location and situation.
4. Active quests and immediate objectives.
5. Recent discoveries and world changes.
6. Relevant NPCs, factions, and relationships.
7. Character-specific reminders, resources, or unresolved decisions.

**Recent events (implemented: list and detail).** The campaign-level “Recent events” section shows a compact list of events beside the selected event's detail panel.

- *Data:* the list is the campaign summary's `recent_events` exactly as the server returns it (its ordering, event limit, and draft/voided visibility filtering are untouched); there is no per-event fetch, no filtering, pagination, or character-perspective selection. Each event carries a server-formatted `world_time_display` (see *Time display*), its GM-only free-form `details` only for callers with `canon.edit` (null for every other member, so it is never sent or rendered for them), and, for the event families that have one, a typed `explanation` (see *Event explanations*).
- *Time display:* list entries and the detail panel show the server-formatted in-world time, which keeps every available part of the point. A calendar point reads “Calendar name: Year N (Epoch), Month D, HH:MM” (month, day, and clock appear only when recorded; year 0 is a real year), and a label on a calendar point is appended after an em dash (“… — Harvest feast”). A narrative point keeps its label. The World times page uses the same reading for calendar points. An event whose time has neither a label nor a year shows “World time unassigned”. Raw ids and the real-world creation timestamp are never shown as in-world time.
- *Selection:* the first event is selected by default and that choice is stored like an explicit click; each list entry is a real `button` (keyboard- and screen-reader-operable, visible focus ring) and the selected one carries `aria-current="true"` plus the accent border and muted-surface treatment. Selecting an entry updates the panel in place — no navigation. The stored selection is normalized against each new list: it survives prepends, reordering, and unrelated changes; if it disappears the first remaining event is adopted and the old choice does not return if its id reappears; an empty list clears it and shows “No recent events are available.” Campaign Home remounts when the campaign changes, so a selection never crosses campaigns.
- *Detail panel:* an `article` labelled by the event title, showing the time, the summary, and the fuller description only when it differs from the summary (“No event description is available.” when neither exists).
- *Narrow screens:* below 48rem the list stacks above the detail panel at full width; titles wrap, so nothing scrolls horizontally. From 48rem the list is the left column and the detail the wider right column. The list scrolls vertically past 20rem; it has inner padding and scroll-padding so the focus ring of the first, middle, and last entries is never clipped.
- *View all events:* intentionally omitted — no authorized all-events list route exists yet, and this change does not add one.
- Loading and failure states come from the Campaign Home summary boundary.

**Event explanations (Phase 15 checkpoint CP-9a, read side).** Recorded events explain what happened, to whom and when through one shared `EventExplanation` presentation (`components/events/EventExplanation.tsx`) backed by one server adapter set (`queries/event_explanations.py`, serialized by `api/event_explanations.py`). Nothing is stored for it: it reads the facts the originating command already recorded (participants, `event_effects` previous/new values, the effective `world_time_id`, `created_at`, `session_id`, `event_causes`, `event_corrections`). It writes nothing, adds no migration, backfills nothing and does not read audit logs or revision snapshots. The administrative first build activation and no-op commands record no event, so there is nothing to explain for them.

- *Families:* party join and leave (character and party), subsequent build activation (previous and new build label), campaign clock advance and correction (previous and new in-world time), and a recorded move or travel (the existing `session_travel` legs, reused, not copied). Any other event gets a generic explanation (times and links only) and is otherwise unchanged.
- *Surfaces and density:* the world event page (`explanation` on `GET /campaigns/{id}/world/events/{event_id}`, a "What happened" panel), the GM event page (`explanation` on `GET /campaigns/{id}/events/{event_id}`), the session log and wrap-up review (`explanations` beside `travel` on session detail; the event's title, link and GM notes stay) and Recent events (`explanation` on each summary event). Lists get one sentence plus the in-world time; Recent events rows get the sentence only, and the detail panel the sentence and any move legs. Event pages get the sentence with linked names, the labelled times, the before and after rows, the session link and the related events.
- *Time:* **In-world time** is the event's effective fictional time in the campaign calendar's formatter. **Recorded** is the real moment the event was written (`created_at`), shown in the reader's own timezone with its abbreviation. They are separate rows and never substitute for one another. A clock event's previous and new time are in-world readings; "not recorded" means the event stores no earlier time (the first clock setting).
- *Causality labels:* a clock event's existing chain row reads "Follows the previous clock change" (a correction: "Corrects the earlier clock change"; the earlier advance: "Later corrected by the clock change"). It is not claimed as the gameplay cause. Only a clock event's own chain row is read that way; any other event whose recorded cause is a clock event, and any other recorded cause event, reads "Recorded cause". Correction links read "Corrects", "Corrected by", "Replaces", "Replaced by". The correction **reason** is editor-only. Free-text cause descriptions, cause interactions and encounters are not shown yet.

**Clock cause and member-safe explanation (Phase 15 checkpoint CP-9b, write side).** The shared `CampaignClockCard` (Campaign Home and the Run Session bar are its only entry points) offers, in its Advance form only, an *Optional details* group: a **Cause** picker and an **Explanation for members** text area (500 characters). A plain manual advance sends neither field. The picker reads `GET /campaigns/{id}/clock/cause-choices?world_time_id=` (`canon.edit`; recorded, non-clock, non-correction events of the campaign's own timeline, newest in-world time first, at most 50, each labelled with its name and in-world time and filtered to events that take effect by the chosen time; an ancestor timeline's history is never offered, nor any event the editor holds a targeted `campaign.view` deny for; a guessed id of such an event is refused with the same generic `clock_cause_invalid` as a missing one, before the timing check, so neither eligibility nor timing is revealed). An empty list says so and a failed read is replaced by a note: neither blocks a manual advance. A cause the newly chosen time no longer offers is cleared with a visible hint rather than sent. The explanation field states its audience: it is shown to campaign members who can view the event, so it must not contain GM-only notes; it is stored in `narrative.clock_advance_details` (revision 140), never in the GM-only `details`, and the administrative audit record never holds it. A retry replays the captured request (same body and idempotency key); input is kept after a refusal (`clock_cause_invalid`, `clock_cause_after_target`, stale version). Readers see **Cause** ("Manual advance", or "A recorded event" with the linked cause when they may open it, otherwise "A recorded event that is not available to you" with no id or name) and **Explanation** rows on the event page and a compact line in lists; the "Follows the previous clock change" chain, the "Recorded cause" and the correction links keep separate labels. An older advance shows neither row. Event links remain independently visibility-filtered.
- *Access:* a character is named only when the reader may discover it (the World Explorer rule: roles, relationships, entity denies); otherwise it is "A character", with no id, name or count. A character name links only where the character page opens for the reader. Build labels need the full tier for that character (the GM, a controller or a `character.view_full` grant) and no entity deny (DR-6); everyone else reads "<Name>'s build changed." with no values. A build that does not belong to the event's character reads "not available". A party is named when it belongs to the campaign and is active (editors also see archived ones), otherwise "a party (not available)". A world time outside the event's world is "not available". Related events are limited to the campaign's own timeline, so a branch never names a parent's later history; a cause link to an event the reader cannot open is omitted, a correction link to one (such as the voided original) reads "an event that is not available". A session is linked only when the reader may view it (the world event response also nulls `session_id` otherwise).
- *Current labels:* names and build labels are the entity's current label, not a snapshot of how it read when the event happened. A renamed party or character reads with the new name; a deleted build reads "not available".
- *Verification:* `tests/database/test_api_event_explanations.py` (API and audience matrix), `EventExplanation.test.tsx` and the per-surface tests; scripted browser evidence is separate from human and screen-reader acceptance (docs/PHASE15_MANUAL_ACCEPTANCE.md).

Each card is assembled for the current user and perspective. A player using Character A may receive a different dashboard than the same user viewing Character B. Observers receive only curated content. GM briefing remains feature-gated; preview is limited to the effective-access explanation and per-resource quest/knowledge panels in §6.3, not a full-portal viewing mode.

### 5.4 World explorer

Browse authorized:

- locations and dungeons;
- NPCs and player characters;
- organizations, factions, governments, religions, and cultures;
- items and artifacts;
- historical events;
- relationships;
- approved lore and knowledge.

MVP presentation:

- type-filtered card collections;
- text search over authorized records;
- concise result cards showing only audience-safe list fields;
- campaign-scoped, route-based detail pages when an authoritative detail contract exists;
- related-resource links;
- breadcrumbs for location containment.

**Category browser.** The campaign World page (`/app/:campaignId/world`) is headed **Campaign World**, with a labelled search, the editors' create links and draft toggle, and a local **World categories** navigation beside (above, on narrow screens) a card grid that uses the full content width: one column, two once the results area is about 34rem wide. The groups map one-to-one onto the server's World Explorer categories, so no type is unreachable: **All entries** (every category), **Locations** (`location`: settlements, regions, buildings, dungeons and the rest), **People** (`character`: NPCs and player characters), **Organizations** (`organization`), **Faiths** (`religion`), **Items** (`item`) and **Events** (`event`). Each category, and All entries, shows its authorized total in parentheses, from `GET /campaigns/{id}/world/search/counts` (the same search `q` and, for editors, the draft/archived preview flags; never the selected category or page). The totals come from the same SQL visibility filter as the results, so a player's counts exclude what their results exclude, and a zero-count category stays listed with `(0)`. While the totals for the current search are loading or after a failure no count is shown (never a zero), and a superseded request's answer is ignored. Category, search, the page trail (`cursor`, repeated) and the editors' draft preview (`hidden=1`) live in the address (`?category=&q=&cursor=`), so Back/Forward and deep links work; an unknown category opens All entries. A card shows the name as the primary link, the readable type beneath it, and the summary only when one exists. Opening an entry passes the browser's query string as router state, and the entry's **Back to World** link returns to the same category, search and page. An empty search offers **Clear search**, which keeps the category.

World cards identify the entity's human-readable category/type, name, and authorized short summary. They do not infer containment, relationships, population, organization membership, visibility, or other details from identifiers or category codes. Converting a list to cards may proceed before detail support exists; a card becomes a detail link only after the server exposes a directly loadable, audience-safe detail contract for that category.

**Canon lifecycle (Phase 14, delivered).** A member whose bootstrap lists `canon.edit` sees a *Show drafts and archived* checkbox on the World list (it adds `include_noncanon`/`include_archived`; the server ignores the flags for anyone else, so the checkbox is only an offer). Rows that are not active canon carry a text-and-icon badge (Draft, In review, Approved, Rejected, Superseded, Archived) and the badge status is part of the card link's accessible name. On the detail page of a place, dungeon, area, organization, religion, NPC or player character, the same members get the **World record workspace** (§4.6), whose **Publication** section holds the lifecycle: the current status, exactly the actions in the server's `available_actions` (submit for review, return to draft, approve, reject, publish as canon, supersede, archive, restore, delete draft), and the server's reasons for the blocked ones, presented by the one lifecycle rule in [UI_STYLE_GUIDE.md §10a](UI_STYLE_GUIDE.md#10a-authoring-forms-dialogs-and-badges-phase-14) (the next step as the primary button and the rest under **More**; actionable reasons shown inline and the status-derived ones under a collapsed **Why other actions are unavailable** disclosure). Submit for review is immediate; every other action confirms in a modal dialog, with an optional reason (archive, reject, return to draft) or a required one (restore, delete draft). Supersede offers replacement candidates from the server (same world and type, canon, not the record itself) and never guesses eligibility. A stale version keeps the dialog open with *Load latest version*; success refetches the lifecycle view and the detail, then announces the result; deleting a draft returns to the World list. Players and members without `canon.edit` send no lifecycle request and see the read-only page, which is also what everyone gets for an event.

Detail pages display only sections the user may access. They use bounded panels for the authorized overview, current state, containment, relationships, known history, related resources, and provenance supplied by the detail response. Irrelevant or unavailable panels are omitted without suggesting that hidden sections exist. The page distinguishes established canon, knowledge in the current perspective, rumor/belief, uncertainty, and source provenance only where the current contract deliberately exposes those distinctions.

**Draft versus published (Phase 14).** Players see only published, active definitions in lists and search; archived and superseded definitions stay reachable from history (detail pages, relationship and event links) but are not offered in browse. A game master with `canon.edit` additionally sees, on lifecycle-managed definitions (places, organizations, religions), a lifecycle badge (Draft, In review, Approved, Canon, Superseded, Rejected, Archived — text plus icon, never color alone), a "Show drafts and archived" toggle that is backed by the URL and hidden for players, and a lifecycle panel that renders only the actions the server reports as available, with the server's reason for each blocked action (inline when actionable, otherwise in the collapsed disclosure; nothing is dropped). Restore and delete-draft require a reason; supersede offers only replacement candidates the server returns. After any transition the detail refetches rather than trusting its previous content.

### 5.5 Character workspace

The character selector shows every character related to the user for the active campaign and timeline. A user can have several characters; a character can have several users.

Tabs appear only when authorized:

- Overview
- Sheet
- Current state
- Inventory
- Knowledge
- History
- Relationships
- Quests
- Notes
- Access

Capabilities are independent:

| Capability | Example |
|---|---|
| Discover | Character may appear in search or links |
| View summary | Public profile and current summary |
| View full | Full sheet and ordinary history |
| View private | Private background, memories, or knowledge |
| Interact | Speak or act through the character where supported |
| Control | Submit play-state commands |
| Edit narrative | Update authorized descriptive fields |
| Edit mechanical | Update authorized mechanical fields |
| Manage access | Change user-character relationships or grants |

The screen labels why access exists, such as “Primary controller,” “Co-controller,” or “Viewer through Party A.”

The character Sheet view uses a responsive tabletop-inspired information hierarchy rather than one long sequence of tables:

- identity, build, ruleset, class, and level facts form the page header;
- hit points, proficiency bonus, movement, and spellcasting values use compact stat cards when present;
- every ability has its own card containing the score, prominent modifier, saving-throw modifier, and an explicit save-proficiency state;
- skills, other proficiencies, languages, senses, conditions, resources, features, and spellcasting profiles use separately headed panels;
- spells are grouped by level, preserve their contract-provided identity, and display known/prepared state without relying on color;
- sparse but valid characters retain character-level facts and deliberate empty states rather than losing the entire sheet.

The portal does not invent familiar sheet values such as armor class, initiative, hit dice, attacks, equipment, background, alignment, or personality traits until authoritative audience-safe contracts provide them.

**Browsing a character is not selecting a perspective.** The selector stays relationship-scoped: it lists only the characters the person has character access to (`character.view_knowledge` through a user-to-character relationship). The Characters browser and `/characters/:characterId` are separate: they show what the person may *view*, a GM with no character access can open any character's sheet, and a player can open a character they only view, but doing so never makes it selectable or controllable.

**NPC sheets.** An NPC's sheet is the same sheet component fed by the same contract; nothing is computed for it. The header eyebrow names the kind (**Player character**, **NPC**, **Character**), taken from `character_kind` on the character and sheet reads. A character created in the portal has only identity until a GM authors a build and a starting state, so its sheet is mostly deliberate empty states: **No class levels recorded** (the character level is then not shown, never `0`), **Not available** for the proficiency bonus, **Not recorded** for movement, hit points, exhaustion and death saves, and the empty panels for ability scores, skills, languages, senses and features. Monster-style values (armor class, challenge rating, hit dice, attacks and actions, legendary or lair actions, resistances) are not modelled for any character and are never shown or derived; adding them is a data-model extension (DATABASE_CONVENTIONS §37), not UI work. The sheet never shows GM notes, background, appearance, the portrayal profile or detail level.

**Stats versus portrayal and runtime.** The sheet shows what an NPC *is* (its build) and the effective runtime state (hit points, conditions, resources) as recorded. Changing it is elsewhere, each with its own page, eligibility and saves: **Edit** (identity and GM notes), **Builds and starting state**, **Run this NPC** (hit points, conditions, resources and moves, each an event), and **How this NPC is played** (portrayal profile and detail level, never shown to players or in the character read model). The sheet links to them for editors and embeds none of them.

### 5.5a Relationship concepts and where each is managed

Several different things are called a relationship or a member. They are different records with different owners; the interface keeps them apart and never derives one from another.

| Concept (interface name) | What it is | Managed in | Seen elsewhere |
|---|---|---|---|
| **Relationships** (fictional) | In-world connections between places, organizations, religions, NPCs and player characters: family, employment, ownership, political ties, routes, other connections. Each has roles, a start, can be ended (it stays in history), archived and restored, and each participant can hold its own view. They never change who can see or play a character | The World record workspace, **Relationships** section, on either participant (editors) | A character's page shows people without `canon.edit` a read-only **Relationships** section of the visible relationships (counterpart, type, direction, period, campaign-visible fields); other reader pages show only what the World API allows |
| **Members and offices** (organization membership) | A character's or organization's membership in an organization, with office, rank, visibility and period. It is the same record as a Membership relationship | The organization's **Members and offices** (add, correct, change office, end) | Listed read-only in both participants' Relationships, with a link here; Archive/Restore and how each participant sees it stay in Relationships |
| **Party members** | Which characters belong to a party in this timeline; every change is an event | The party's page (editors; a read-only roster for `campaign.view`) | **Parties (N)** in the hierarchy panel |
| **Character access** (user-to-character) | Which campaign member may see, play or portray a character, and how (owner, primary controller, co-controller, portrayer, viewer…). This is security, not story. It derives the perspective selector | Access, the member's **Character access** (give access to a character, change access type, remove access) | A player character's **Player** section links here (**Link a player**) |
| **Effective access** | A read-only explanation of the capabilities a member has and where each comes from | Access, **Effective access** | — |

The words are different on purpose: *Relationships* are about the story, *Character access* is about who may use a character, *Members and offices* is an organization's roster, and *Party members* is a party's roster. A fictional ownership never grants access and an access "owner" never creates canon. The domain term for the last is still *user-to-character relationship* (§8).

### 5.6 Knowledge

Views:

- Known facts
- Rumors and beliefs
- Recently discovered
- Character-private
- Party-shared
- Public lore
- Sources

Each item shows, when permitted:

- claim or summary;
- knowledge type;
- confidence or truth status appropriate to the viewer;
- who knows or believes it;
- discovery or transfer source;
- effective time;
- related entities and quests.

Public lore is part of every view by default, whether or not a character or party perspective is selected; choosing a perspective adds that audience's records and never removes public ones. Leaving public lore out is an explicit user choice ("Include public knowledge"), and the Public view shows public lore only. An item that is both public and known to the selected audience appears once, as that audience's own belief.

**Archived knowledge.** A **Lifecycle** filter (Active / Archived / All) appears only when the list response says `archive_browse_available` (baseline `canon.edit` and `world.canon.read_private`, see [ENTITY_LIFECYCLE.md §3.3](ENTITY_LIFECYCLE.md)); nobody else sees it, and the Member preview never does. The lifecycle, view, search and party filter live in the page address (`lifecycle=`, `view=`, `q=`, `party_id=`, each omitted at its default), so Back and a reload reproduce them; changing the filter starts again from the first page, and an address the server refuses falls back to the active list. Archived published history carries an **Archived**, **Superseded** or **Deprecated** badge; drafts and ordinary active claims carry none. A card opens the claim page, where Restore is offered only when the server's `available_actions` allows it.

**Perspective.** For a player, the character selected in the campaign information box is the Knowledge perspective; the page never asks for a second character, and a party is an optional filter, never a prerequisite. With a character and no party ("All parties"), Known and Rumors show what that character knows directly plus what its eligible parties know, Party shared shows those parties' knowledge, and Recent their discoveries. A party is eligible only when the player holds `character.view_knowledge` for the character, the party belongs to this campaign, and the character is currently its member on this timeline (the pairs the session bootstrap offers and `resolve_party_perspective` accepts); being in a party grants nothing else, and other parties' records never appear. Choosing a party narrows the party-derived part to that party and keeps the character's own knowledge; an unauthorized character/party pair is a non-disclosing "not available". With no character selected, only public lore is shown, and any leftover party is ignored. An item known both to the character directly and through a party appears once, as the character's own belief, on the card and the claim page alike. Changing the character clears the party filter and shows no results from the previous perspective while the new ones load. GM and owner views are unchanged: without a party they show canonical truth, and a selected character does not replace that. Member preview resolves the same perspective for the previewed member, so it shows what that member sees.

**Character knowledge on the claim page.** The list and the claim detail answer "does the selected character know this claim, and how?" from one server-side resolution, so a card in the list is never opened to "no recorded knowledge". The detail returns a `character_knowledge` block naming the path: `character` (the character's own record, shown with exactly the awareness, confidence and willingness to share it holds), `party` (an eligible party's record, identified as known through a party the character belongs to, with that record's values), or `public` (public lore with no personal record: only its awareness is shown, and confidence and willingness to share are never invented). The block is `null`, and the page says the character has no recorded knowledge, only when no path exists; being allowed to view a claim does not make the character know it, and a missing personal record does not mean the character does not. A GM or owner opening a claim still sees the canonical statement and truth, with the selected character's own answer shown alongside it. On the claim page and in Member preview this is one **Knowledge details** panel under the About block: Kind, Awareness, Confidence and Willing to share in that order (a perspective's values appear only when recorded, so a missing confidence is never 0 and a missing willingness to share is never No), with the origin explanation under the panel heading; the standalone Kind line is not repeated for readers. Awareness shown for public lore is the same record the list card shows. In the Party shared view an item with both a party and a personal record is listed as the party's belief, while the claim page reports the character's own record as the more specific path.

The UI never labels a player-facing claim “false” merely because the GM's canonical record says so. GM mode can compare canonical truth with character beliefs. Player mode shows only the belief state available to the selected perspective.

Knowledge collections use cards in a responsive grid wide enough (about 28rem) to read a sentence comfortably. The claim text is the card's content and its one link; the claim kind is a quiet secondary label; awareness, confidence and willingness to share appear only when meaningful for the current audience; and a labelled **About** area names the subject and its type, as a separate link from the card's own. Scope and canonical truth are not repeated on cards: they live on the claim page. Null values are omitted or neutrally described; they are never translated into a suggestion that hidden information exists.

Opening a knowledge card as a full detail surface requires an explicit detail route and an authoritative detail contract, or a documented API guarantee that the list item is the complete directly retrievable detail representation. The portal does not construct a refresh-dependent detail page from a collection page's in-memory record. Future detail panels may include discovery context, sources, related records, and GM truth comparison only when separately authorized.

**Subject (forward link).** Both the list (`GET /campaigns/{id}/knowledge`) and the detail (`GET /campaigns/{id}/knowledge/{id}`) return an optional `subject` summary — `entity_id`, `name`, `category` (a World Explorer category or `quest`) and `entity_type_code` — and the card and detail page render it as a labelled **About** area (a compact one on cards, a prominent **About this World entry** block on the claim page) showing *name* as a link and *type* whose link opens the subject's existing detail route: `world/:category/:entityId` for a World entity, `quests/:questId` for a quest. A quest link carries the Knowledge view's `character_id` + `party_id` pair only when both are present (the quest route honors only the pair); World links carry neither, since those routes do not read them. Knowing a claim grants nothing about its subject: the summary is returned only when the caller may open the subject itself — a World subject under the World Explorer discoverability rule (character discover tiers, per-entity `campaign.view` denies, unpublished definitions, event scope), a quest under the quest detail route's own contract (per-quest deny, lifecycle, and tracking on this timeline for the caller's authorized party perspective, or any party for a GM). Otherwise `subject` is `null`, exactly as for a claim with no subject, and the row is omitted — no id, name, type, or "hidden subject" hint. The list's `subject_entity_id` follows the same decision. The audience preview inherits it unchanged, because it calls the same detail resolver for the previewed member. Summaries are resolved per page in a fixed number of queries, never per card. Reverse panels (a World entity or quest listing the knowledge about it) and general entity-awareness records are not part of this and remain deferred.

### 5.7 Quests and quest detail

The quest collection uses concise cards. The current list contract supplies a quest name and status, so list cards do not invent descriptions, objective counts, rewards, participants, or locations from data absent from that contract. Each card links to the established campaign-scoped quest detail route.

Quest list and detail requests carry the selected character together with a party perspective, because the API honors a party only as an authorized `(character_id, party_id)` pair. The party comes from the selected character's `authorized_parties` in the session bootstrap: none when the character has none (campaign-wide quests only), the only one when there is exactly one, and only an explicit user choice when there are several — never a guess. Campaign-wide quests always remain listed; the party adds its own quests and statuses, and other parties' quests never appear. The chosen pair travels in the detail link's URL so the detail shows the same party's status and objectives, and it is dropped in favour of that derivation when the selected character changes.

The full quest detail surface visually continues the selected card and organizes the authorized contract into separately headed stage and objective regions. It preserves server-provided stage sequence and objective order; it does not alphabetize narrative progression. Stages are connected, independently collapsible cards whose collapsed summary counts the shown (audience-filtered) objectives that are complete, without claiming a whole-stage status ([UI_STYLE_GUIDE.md §12.3](UI_STYLE_GUIDE.md#123-connected-collapsible-stage-cards)).

Player/observer sections:

- visible description;
- known objectives;
- current status;
- relevant permitted NPCs and locations;
- discoveries and prior events;
- character-specific knowledge.

**Editors.** A member whose campaign grants `canon.edit` opens the Quest workspace at the same address ([§4.6](#46-route-model), [UI_STYLE_GUIDE.md §12.4](UI_STYLE_GUIDE.md#124-quest-workspace)). It separates the workflow phases, the authored stages and objectives, and in-game progress; shows the record's lifecycle status in the header and progress status only in Progress; and never treats publication as starting, revealing or completing a quest. A published quest is seen by a player only once it is activated for the campaign or for their party, and then only the objectives its visibility policy allows; the **Member preview** section (with `access.manage`) shows exactly that for a chosen member.

GM-only sections, when authorized:

- hidden stages and objectives;
- dependencies and failure conditions;
- secret participants and motives;
- possible outcomes and rewards;
- event mappings;
- visibility preview.

With the current read-only contract, the implemented detail surface may include only the quest title/status, stages, descriptions, and objectives with their requirement level, completion mode, quantity, and status. The richer sections above remain product goals and appear only after matching audience-safe backend fields exist. Hidden stages, objectives, sequence gaps, and aggregate counts are not exposed.

### 5.11 Authoring patterns (Phase 14)

Every authoring surface (worlds, timelines, campaign setup and settings, canon lifecycle) follows one set of patterns, implemented once in `portal/src/components/authoring/` and `portal/src/hooks/useAuthoring*.ts`. None of it is a form library or a state-management framework.

**Server-authoritative.** Capabilities, selectors, available actions, and blocked reasons come from the server (`global_capabilities` in the bootstrap, `available_actions` / `blocked_actions` on read models, `GET /rulesets`, branch-point lists, replacement candidates). The portal never infers an entitlement, never optimistically assumes success, and never trusts a previous lookup for a write: the server re-checks authority at mutation time. A page keys its loaded record by URL, so a record is never shown under another record's route while the next one loads.

**Unavailable destinations (ADR 0018).** One rule per surface: *persistent navigation* keeps an unavailable destination visible as a disabled non-link (`DisabledNavItem`); *contextual actions* (a page's "Create world", "Edit world", "Create a new world" in campaign setup) are omitted, never rendered as links that fail after navigation and never disabled by CSS alone; *direct URLs* to a guarded page (`/worlds/new`, `/worlds/:worldId/edit`, `/platform/accounts`) follow the destination policy below (an explicit denial or an explanation, never the not-found page, and never a mounted form or request the account may not make); and *the server* independently rejects every unauthorized mutation, so none of the above is a security boundary.

**Unavailable and unauthorized destinations.** One policy, one set of primitives (`TerminalState.tsx`: `TerminalContent`, `AccessDeniedContent`, `AccessDeniedPage`; `authoring/ReadState.tsx`: `ReadTerminal`, `ReadFailedNotice`, `ReadClosedNotice`, `ActionUnavailableNotice`; `hooks/useDocumentTitle.ts`). It supersedes the earlier rule that every guarded direct URL rendered the ordinary not-found page (ADR 0018 decision 7 and §3.1 of the navigation plan): that disguise hid *known static pages*, which the server never hid, and left a person unable to tell a missing capability from a typo. Server authorization, the HTTP disclosure contracts (404 for a missing or hidden record), the capability mappings and the request gating are unchanged; this is presentation only.

| Situation | Presentation |
|---|---|
| An address that is not a portal page, or an unknown campaign section | Not-found content (`NotFoundContent`; with its own `<main>` as `NotFoundPage` in the public layout) with a link to the portal home. |
| A **known static destination** the account lacks the capability for (`/worlds/new` without `world.create`, `/platform/accounts` without `accounts.manage`) | An explicit **Access denied** heading and sentence, links to Worlds / the portal home. The page's form and requests never mount: no `GET /rulesets`, no account list request. |
| A record the person **may read** that does not offer the action (a world, timeline or campaign setup step without `update`, `create_timeline`, `create_branch`, `create_calendar`, `create_campaign`) | `ActionUnavailableNotice`, built only from what the server sent the caller: the `blocked_actions` reason for that action (a lifecycle or state reason), otherwise the record's own archived status, otherwise "Your role on this … does not include being able to …". A capability gap, a lifecycle block and an archived record therefore read differently. |
| A record that is **missing or hidden** (404) | The same neutral "The … is not available, or you can no longer access it." with the same heading and title, and no name, identifier or other metadata. The two cases are byte-identical. |
| A refusal (403) on a read | "You do not have access to the …" with no retry. |
| A network or server failure on the **first** read | "The … could not be loaded." with **Try again**, which only reads again (it never repeats a command) and reports "Loading…" while it runs. A failed catalog read (branch points, rulesets, a world list) is this failure, never an empty successful catalog. |
| A 401, or authoritative loss of permission after the page was shown | Unchanged: the session reloads and the sign-in boundary takes over; protected data is cleared, and only what the person typed is kept, read-only, in the permission-lost panel. A refresh that fails after a successful read keeps the last data with the stale-read notice. |

When several reads back one page, the least revealing closed answer wins (404, then 403, then failure). **Landmarks.** Terminal content never adds a `<main>`: a page inside a workspace frame renders content only, a route outside one wraps it (`NotFoundPage`, `AccessDeniedPage`); the edit-world route keeps its heading and breadcrumb in its loading and error states. **Focus and announcement.** A terminal state's `<h1>` takes focus once per navigation (page headings already do through `usePageArrival`, which now fires when the read *settles*, not only when it succeeds); that move is the announcement, so a terminal state is not also a live region that would be read twice, and a re-render never moves focus again. The failure notice is a role=alert region the person reaches by its retry button, which stays focusable while it works (`aria-disabled`). **Document titles.** Only terminal states set one ("Access denied", "Not available", "Could not load", "Action unavailable", "Page not found", suffixed "· portal"), from fixed generic phrases that never contain a record name or identifier, and the previous title is restored when the state unmounts (navigation, retry succeeding, sign-out). There is no portal-wide title framework.

**Pages that read more than one thing.** Every required read that can fail has its own way back. The page's main read decides whether the page opens (404, then 403, then failure, across all the reads that back it); a secondary read the page can work without (the correction check behind an event's Void / Correct controls, the category options behind the item-definition filter) leaves the page open and is replaced by an explicit notice for that part, with **Try again** only when the failure is recoverable. A catalog that did not load is never shown as an empty one. **Try again** reads again only the reads that failed (`retryFailedReads`), never a read that answered, and never repeats a command. **Focus after a retry.** A retry control that the person used and that still holds focus when a successful read removes it hands focus to the heading of its page (`useRetryFocus`, used by the failure and stale-read notices); focus stays on the control while it reads and after a repeated failure, and it never moves if the person has moved elsewhere, if the control was not used (a background read answered), or on an ordinary re-render.

**Forms.** Every control has a visible label, an optional hint, and a plain-text error; an invalid control carries `aria-invalid` and `aria-describedby`. Structural limits (required, trimmed length, set membership) are mirrored client-side so errors show before submit; the server never reports a field location, so domain failures reach a field only through a stable error `code` (`ruleset_not_available` → rulesets, `branch_point_invalid` → branch point, `supersession_target_invalid` → replacement). A form has an explicit **Save** and **Cancel**. After a failed submit an **error summary** (one `role="alert"`) takes focus and links each message to its field. Entered values survive every recoverable failure (validation, conflict, denial, network, server) and are never written to browser storage — an expired session loses them, which is an accepted limitation.

**States.** Each page and mutation distinguishes loading, empty, denied (403), unavailable (404 — "does not exist or you cannot access it", never which), invalid (400/422), stale/conflict (409), pending, success, expired session (401 → re-authenticate), network, and server errors, each with safe copy, never raw response text. Retry (network/server) resubmits the same body with the **same Idempotency-Key**, so a lost response replays instead of duplicating; a changed body gets a new key.

**Write outcomes and refresh (Phase 15 CP-2).** `useAuthoringMutation` keeps three outcomes apart, and a page must not blur them. *Not confirmed* (`error`): the request did not succeed. A network or server failure may still have been applied, so the copy says "we cannot tell whether this was saved", keeps the input, and **Retry** repeats the request exactly as first sent (same body, same request closure, same key); edited input is a new request with a new key. *Confirmed and refreshed* (`success`). *Confirmed but the follow-up read failed* (`confirmed`): the `onSuccess` callback returns the refetch outcome (`"ok"`, `"failed"` or `"superseded"`, as `refetch()` now does) or throws, and either one makes the status `confirmed`, never `error`. Once a write is confirmed its key and body are spent and `retry` does nothing, so the only action is a read. The page shows `SavedRefreshFailedNotice` ("Saved. The latest … could not be loaded", a polite status, not an alert) whose button only reads again, adopts the returned `receipt` (its new row version) or holds further version-checked saves until the read succeeds, and keeps unrelated input. When another notice on the page already announces the failed read (the Run Session page's banner), the saved notice is text only, so a failure is announced once. Delivered for the character and party inventory panels, campaign settings (save and archive, with the bootstrap refresh and the settings re-read tracked separately), the archived-campaign reactivation, the Run Session participant add/remove, and the shared content edit page. CP-10 extends it to the quest (command hook, details, structure, progress), item (operations, definition edit), knowledge claim (edit, audience) and entity-sources writes: each returns its read-back outcome (`combineRefetchOutcomes` joins several reads into one), and none announces its own "done" message unless every read was applied. Return navigation shares `hooks/returnState.ts` (query-state readers and the `returnTo` allow-list), the World, quest and item headers share `records/RecordHeader`, and the six workspaces that move focus on a genuine section change share `useFocusOnSectionChange`; each domain keeps its own keys, wording and routes.

**Every other caller (DEF-001 fix).** The contract above applies to every portal write that reads its result back, not only the CP-10 callers; the operation-by-operation record is [PHASE15_DEF001_INVENTORY.md](PHASE14_15_COVERAGE_MATRIX.md). A caller returns the outcome of *all* the reads that show its write (`combineRefetchOutcomes`; a read that is not the caller's to make, such as a gated private read, is not part of the outcome), announces "done" only on `"ok"`, and keeps what it last read through a recoverable failure (`useKept`) instead of replacing the page with "could not be loaded" or "does not exist". `hooks/useConfirmedRefresh` gives the shared remainder: a `SavedRefreshFailedNotice` for a write that was confirmed but not read back, a `held` flag that withholds anything that would send the version or token still on screen (party, session, encounter, clock, dungeon and area commands, lifecycle steps, relationship and organization roster writes, world-time recording), a **Load latest** that only reads, a "done" announcement when a read completes, and recovery that is final for that write. A control that is replaced by the recovered read (an archived party's row, a started session's Start button, a re-keyed form) cannot announce for itself, so the page does (`useAnnounceWhenRead`). A denied or unavailable answer to the read-back is an authoritative result, not a failed read: the retained content is dropped, nothing is held, and the write is still announced (World Sharing after an ownership transfer). Two families keep their own shape on purpose: create-and-open / edit-and-return forms navigate to a destination that loads its own data, and the Phase 13 access, invitation and account pages reload through their loading state and show an explicit error page with **Try again**, so they never show a stale record as current.

**Unresolved attempts and request identity (Batch A review).** A request is identified by its operation, target, scope, expected version or token and serialized payload, and Retry or an unchanged resubmission sends exactly that, with its key: the hook keeps the *request closure* of the unresolved attempt, and a caller whose request needs a token prepares it **before** sending (the Award Item section reads the item token once, keeps the prepared award, and re-sends it unchanged; it never reads a new token under an old key). An attempt is *unresolved* after a network or server failure and stays so until it is confirmed or definitively refused, whatever happens to the form meanwhile. A write that creates a durable record the person cannot tell from a duplicate sets `holdUnresolved` (the Session Run log entry and travel): while an earlier attempt is unresolved, an edited body is not sent as a second write; `submit` re-sends the earlier attempt first (returning `"resolving-earlier"`), the form says so, and the later edit is kept — `onSuccess(receipt, body)` receives the confirmed body so a draft is cleared only if it still equals what was recorded. Other writes keep the ordinary rule: an edited body is a new request with a new key. A `"superseded"` refresh is not a completed read: it leaves the write `confirmed` (never `success`) and the form held, so a confirmed version-4 add cannot be followed by an add that still carries version 3 while a newer read is pending. A callback that throws also leaves the write confirmed; a caller that does not render its own notice gets a polite announcement from the hook (`ownsRefreshNotice` suppresses it where the page already has one).

**Settings after a confirmed save.** The settings form is not rebuilt when a newer version loads. It measures edits against what the server is known to hold (the loaded values, or the values of a confirmed save whose re-read has not arrived), so text typed after the save survives *Load latest* and is covered by the unsaved-changes guard (the guard is no longer released by the save itself). While the loaded version is older than the one the save returned, or the latest read failed, both **Save** and **Archive** (opening and confirming) are held; only a stale-conflict *Load latest* replaces the form with the server's values, keeping the draft in the read-only panel.

**Read states.** `ReadFailedNotice` (a network or server failure: "could not be loaded" with **Try again**, which only reads) and `ReadClosedNotice` (403 "no access", 404 "not available, or no longer accessible"; no retry) are distinct from a loaded empty list ("Nothing carried."). The inventory panels show a status while loading in a staged section and nothing on a page that is complete without them; a refused read is said plainly in a staged section and absent elsewhere (only the full character view is given an inventory); a failed read always says so. `useKept` holds the last good read through a recoverable failure only for the same record (`scope`), and drops it on denial, absence or another record, so a failure on the next record never shows the previous one. The Run Session page uses it for its last-loaded session (scoped to campaign and session, with its forms rebuilt per session), and `usePairedRead`, which serves the Dungeon and Area readers, scopes its two reads the same way. The content edit page keeps its form and typed values through a failed re-read, marks them possibly out of date, and holds Save until the read succeeds.

**Conflict.** A stale write (409 `stale_write`) explains that someone else changed the record and offers **Load latest version**: the form is replaced with the server's values and the user's previous unsaved values stay visible in a read-only panel (with "Re-apply my changes"), so nothing typed is lost. The old row version is never resubmitted.

**Unsaved changes.** A dirty form holds in-app navigation that changes the path (a data router's blocker) and sets a `beforeunload` prompt; a query-string-only change is not leaving **by default** (the New calendar steps, and the `?section=` of the staged workspaces, keep every editor mounted). A page whose query change would unmount its editor, change the data scope or perspective, or strand an unresolved operation declares it with `useUnsavedChangesGuard(isDirty, { disposingQuery })` and that change is held like any departure; the campaign setup wizard declares `worldId` and `timelineId`, because each step is another component, and it keeps the guard active after the server has confirmed the create until the bootstrap lists the campaign (a pending, failed or unapplied confirming read leaves the "Open the campaign" recovery action, and leaving then asks; Leave never resends the create). A caller that passes no option behaves as before. The Knowledge claim page declares `character_id` and `party_id` (`PERSPECTIVE_QUERY_CHANGED`), because a deliberate change re-reads the claim under another perspective and unmounts its editor; its own clean-up of a party that is no longer authorized is permission loss and runs under the narrow `runPermissionLossCleanup` exemption instead, so it is never held behind the question. The Quest workspace was inspected and does not declare them: its editor neither reads nor sends those keys. The per-caller classification, and what remains unaudited (writes held outside `isDirty`), is in [the guard audit](UI_DESIGN.md); no complete query-safety guarantee is claimed. A **change of character perspective** keeps the path but is a context transition, held by the same one blocker (`isGuardedTransition` in `navigationHolds.ts`, used by `useUnsavedChangesGuard` and `PickerRecordTime`'s own blocker): the entry's recorded context is compared with the committed one. Every accepted campaign entry, and the initial one, is stamped with the full context it committed under (campaign, world, timeline, perspective) by a same-entry REPLACE (no prompt, no remount, no new history entry, no refresh); the replacement belongs to its entry and is applied only while that entry is still the router's current location with nothing pending or blocked, so it can never overwrite a newer PUSH, REPLACE or POP, and a newer location stamps itself. An initial entry that already carries a valid, authorized stamp (a reload, or Back from another campaign) is honored before any page reads under the default; missing, malformed, wrong-version, foreign or unauthorized state keeps the default and is repaired by the stamp, so Back/Forward between same-path entries recorded under different perspectives is held too; the comparison reads recorded context, never a transient marker. A push or replace without a stamp (an ordinary link, a query-only change) keeps the committed perspective; only Back/Forward to an unstamped or invalid entry resolves to the bootstrap's default. Stay changes nothing (route, history position, selection, Infobox value, form and picker drafts, pending or unknown write records and confirmed-but-unread receipts); a picker's open recording suspends behind the page's single question. The prompt is a confirmation dialog ("Discard unsaved changes?"); a deliberate post-save redirect releases the guard first.

**Confirmation.** Destructive or consequential actions (archive, restore, reactivate, delete draft, supersede) use a native modal `<dialog>`: labelled, described, initial focus on **Cancel**, Escape cancels, focus returns to the invoking control, and the confirm button carries its verb ("Archive world"). A failure renders **inside** the dialog, which closes only on success; an optional reason field is shown when the action takes one (required for restore and delete draft).

**Focus and announcements.** On arrival at a page whose data has loaded, focus moves to its `<h1>`. A success message travels in navigation state and is announced through the shell's single polite live region **after** the destination's authoritative fetch resolves, so it survives the refetch that proves the write. After a write the destination refetches rather than reusing the pre-write record.

**Identifiers.** Raw UUIDs are never rendered; records are named by their human-readable name, and an unlabeled record is described in words.

**Guided workspaces.** A record with several meaningful working phases follows the one rule in [UI_STYLE_GUIDE.md §10a.1](UI_STYLE_GUIDE.md#10a1-guided-workspace-pages): what qualifies, when plain sections or a disclosure are enough, how to name a workflow phase apart from a domain stage, defaults, direct links, read-only behaviour, return context, drafts, focus and layout. The pages that follow it are the Run Session page, the Knowledge claim page, the item workspace, the World record workspace and the Quest workspace, described next. **Staged pages.** A page with several stages (the Run Session page, the Knowledge claim page, the item workspace, the World record workspace and the Quest workspace, whose "stages" are workflow phases) keeps the current section in the query string (`?section=…`), the stage following from it. Choosing a stage or section is a link that adds a history entry; correcting a missing or unknown value replaces it. Every other query parameter on the address (the character and party perspective) is preserved when the section changes. The record's real status is shown in the page header, never in the stage navigation. The section menu is a left column when the workspace itself is at least 48rem wide (a container query, so the sidebar and context panel are accounted for) and a wrapping row above that. Query-only changes are not "leaving the page" for the unsaved-changes guard. Sections stay mounted and the inactive ones are hidden, so form drafts persist across switches and are never written to browser storage.

**Layout.** Phone (< 40rem): one column, 16px gutters, full-width buttons, no horizontal page scroll. Desktop (≥ 64rem): the form column is capped at 40rem with an optional aside. Ultrawide (≥ 120rem): content is capped at 96rem and centered. A timeline lineage is an indented list whose only horizontal scroll is inside its own container. Every table scrolls sideways inside its own named, keyboard-focusable region, never the page. State is never conveyed by color alone (text plus icon).

## 9. Search, lists, and non-disclosure

- Search operates over an authorization-filtered index or query.
- Autocomplete never receives forbidden names or identifiers.
- Counts describe only accessible records.
- Pagination totals exclude inaccessible records.
- A paged list (**Next page** / **Previous page**) keeps the cursors of the pages already visited, since list APIs page forward only, so **Previous page** returns to the exact earlier results; it is disabled on the first page, and the pager stays in place so its position does not jump. On the campaign World page the cursor trail lives in the address (see the category browser above). Changing a filter, search, or other list input discards that history and starts again from the first page, so a cursor issued for the old inputs is never reused. The campaign World page follows this rule.
- Browsable collections default to responsive cards whose fields come only from the audience-safe list contract.
- A card uses a real link when a detail route exists; navigation is not simulated with a clickable `div`.
- Activating a card loads a campaign-scoped detail contract and performs a current authorization check; list data and client state are not proof of detail access.
- Hovering or focusing a card does not preload sensitive detail content unless a later reviewed design provides an equally strong authorization and cache-invalidation guarantee.
- Cards remain concise previews rather than miniature detail pages. Long descriptions, nested collections, and multi-section data belong on the routed detail surface.
- Relationship graphs omit hidden nodes and edges without leaving unexplained placeholders.
- Direct routes to inaccessible resources return the same non-disclosing result as nonexistent resources, except in authorized administrative diagnostics.
- Export and print actions repeat server authorization at request time.
- Browser caches and service workers must not retain data after logout, membership revocation, perspective change, or access revocation.

## 10. States and interaction behavior

Global (settings, campaign selection, account, platform), campaign, and boundary screens all define stable states. Preserve the authenticated shell — header and sidebar frame — while the session remains valid, including without a campaign or when campaign access is denied; expired/invalid sessions clear protected data and follow §4.2. Every major screen defines:

- initial loading;
- partial loading;
- empty but authorized;
- unavailable or non-discoverable;
- session expired;
- access changed while open;
- recoverable server error;
- stale data requiring refresh;
- successful save or command acceptance;
- background processing with resumable status.

Optimistic updates are limited to low-risk presentation changes. Canonical mutations show pending, accepted, rejected, or failed command status and remain idempotent when retried.

Collection and detail transitions additionally obey these rules:

- navigating to a different record never leaves the previous record's details visible beneath a new URL;
- loading preserves the application shell and current context without exposing stale subject content;
- empty states describe only the absence of accessible results;
- missing and inaccessible detail records share one non-disclosing unavailable presentation;
- recoverable errors display safe wording and a retry action without exposing internal diagnostics;
- browser Back returns to the collection, preserving URL-backed filters and search state where practical;
- a refreshed detail URL loads independently of the collection page that linked to it.

- Support desktop, tablet, and phone layouts.

The drawer is modal: it traps focus while open, Escape or the backdrop closes it and returns focus to the drawer control, and it closes after navigation. Hidden or off-canvas links are not focusable. The collapse/expand control and the drawer control always remain reachable; the profile button and **View all campaigns** are never removed at any width. Disclosure buttons (Campaign Home's campaign list, Access) use `aria-expanded`/`aria-controls`; current-route items use `aria-current="page"` (and the active campaign entry `aria-current="true"`).
- Keep perspective indicators visible near the page title even when the main navigation collapses.
- Reflow card collections and detail panels from multiple columns to one without page-level horizontal scrolling.
- Allow only inherently wide tables to scroll inside a bounded local container.
- Preserve meaningful source order when a multi-column detail layout becomes a single column.
- Use semantic headings, distinctly labeled navigation landmarks (one sidebar `nav` labeled "Main" plus labeled page-local navigation), tables, forms, and buttons. Preserve one page-level `h1` per route, logical `h2`/`h3` panel headings, and non-heading site-identity chrome as specified in [UI_STYLE_GUIDE.md §14](UI_STYLE_GUIDE.md#14-accessibility-requirements).
- Use semantic lists for card collections and native links for card navigation.
- Support keyboard navigation and visible focus in every theme, with profile-menu keyboard/screen-reader behavior as specified in §4.3. No essential control is hover-only; responsive name truncation must retain accessible names.
- Do not encode canon/rumor/secret/status distinctions by color alone.
- Do not encode proficiency, known/prepared state, confidence, or selection by color alone.
- Announce async answer completion, access errors, and validation errors to assistive technology.
- Preserve readable source citations and audit tables with responsive wrapping or bounded horizontal scrolling where necessary.
- Respect reduced-motion preferences; optional card-to-detail visual transitions are enhancements, never navigation dependencies.

## 12. Security and privacy requirements

The production browser UI and `/api/*` should share the `world` origin. Use `Secure`, `HttpOnly`, narrowly scoped authentication cookies; do not store long-lived application secrets or bearer tokens in browser code. Protect every cookie-authenticated state-changing request with CSRF tokens and origin checks. Exact hostnames are chosen at deployment time from the custom-domain-plus-No-IP or No-IP-only arrangements in ADR 0012.

- Browser login is local application authentication (PLAN.md §23.1/§23.4), not an OIDC authorization-code/PKCE flow: the portal submits a username and password to a same-origin FastAPI endpoint, which issues an opaque, server-side, PostgreSQL-backed session via a `Secure`, `HttpOnly`, `SameSite=Lax` cookie (`__Host-dnd_ai_session` in production). External OIDC bearer-token verification remains available only as an optional compatibility path for non-browser clients presenting their own `Authorization: Bearer` token — the browser client never performs an OIDC redirect/callback and never handles a token itself.
- Store no long-lived application secret in browser code — no bearer or refresh token in `localStorage`, `sessionStorage`, IndexedDB, a JavaScript-readable cookie, a URL, or application state.
- The session-bootstrap endpoint (`GET /auth/session`) is the single source of the current user, campaigns/roles/character-perspectives/capabilities, a CSRF token, and the Phase 12 feature manifest; the server recomputes every authorization-sensitive field from current database state on every call, so the client never infers permissions from a cached value or a display-role string.
- Protect every cookie-authenticated, state-changing request with the `X-CSRF-Token` header (validated against the current server-side session) and an allowed `Origin` — the selected token/session architecture is the one described above, not a placeholder.
- Avoid tokens and restricted content in URLs, analytics, logs, or client error reports.
- Reauthorize every command and sensitive query; UI state is not proof of permission.
- Audit role changes, grants, revocations, preview use, sensitive reads, proposal decisions, and canonical writes.
- Rate-limit login-linked abuse, search enumeration, and expensive Ask requests.

## 13. API-facing UI contracts

Portal responses should include:

- resource data already filtered for the current request context;
- permitted actions/capabilities for rendering controls;
- perspective and effective-time metadata;
- provenance/citation links the user may access;
- stable pagination and correlation identifiers;
- non-disclosing errors;
- command status and idempotency identifiers for mutations.

The UI may use permitted-action hints to choose controls, but the API must independently authorize the eventual request.

## 14. Capability boundaries

- Identity and access services provide login mapping, memberships, roles, character relationships, resource grants, centralized access resolution, and audience-filtered queries.
- Foundry uses the same user mapping, character-control, command, and query authorization rules as the portal.
- Assistant features synthesize only pre-filtered campaign context and return cited rules/reference results appropriate to the active perspective.
- The portal provides campaign and perspective selection, player and observer views, GM access management, audit history, and preview-as-user.
- Production ingress provides same-origin UI/API routing, HTTPS, secure cookies, CSRF protection, rate limits, and non-disclosing operational errors.
- Import review provides source/proposal inspection, matching, conflict resolution, approval, rejection, and promotion status without bypassing application commands.

## 15. Deferred experience

Defer until demonstrated need:

- Discord client;
- interactive geographic maps;
- free-form relationship graph editor;
- real-time collaborative editing;
- generalized page/layout builder;
- unrestricted administration CMS;
- offline-first mutation;
- broad notification center;
- bulk ACL editing beyond the first real campaign need;
- theming marketplace or user-authored themes.

## 16. MVP acceptance checklist

- A user can log in, accept an invitation, select a campaign, and log out.
- A user can hold multiple roles and switch among permitted viewing purposes.
- A user can access multiple characters, and a character can be associated with multiple users.
- A fact can be visible to multiple users through different authorized paths.
- Player, GM, and observer dashboards differ correctly.
- World, Knowledge, Quest, and similar collection screens use concise, responsive, keyboard-accessible cards where applicable.
- Navigable cards use refreshable detail routes, preserve browser navigation behavior, and perform fresh authorization rather than expanding cached list data alone.
- Character sheets use responsive ability/stat cards and separately headed information panels while retaining valid sparse-data states.
- Quest detail preserves server-provided stage/objective order and does not disclose hidden stages, objectives, counts, or sequence gaps.
- World and Knowledge full-detail navigation is enabled only when corresponding audience-safe detail contracts are available.
- Search, counts, links, errors, relationships, and Ask responses do not reveal inaccessible resources.
- Revoking a role, character relationship, group membership, or grant removes access on the next request and invalidates affected cached summaries.
- A player can request recaps, quest status, world details, character knowledge, and cited rules answers.
- A GM can request a preparation brief. **Partially met** — "preview the portal as a selected user/character perspective" is delivered only as the bounded §6.3 pair (an effective-access explanation plus a per-resource quest/knowledge audience preview), never a full-portal projection; see §6.3 and `docs/PHASE13E_ACCESS_CONTRACT.md` §3q/§3r for the delivered scope and D-1's reasoning for not building the rest.
- A GM can manage memberships, roles, user-character relationships, and resource grants with an audit trail.
- Authorized import reviewers can resolve matches and approve or reject proposals without bypassing application commands.
- All critical flows are keyboard-accessible, theme-compatible, and usable at phone, tablet, and desktop widths.
